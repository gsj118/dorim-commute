# HCI 프로젝트 RC1 — 기능 동결, 배포용 안정화, 자기평가 및 제출 준비

## 0. 이번 작업의 목표와 범위

현재 프로젝트는 6차 MVP까지 구현·검증했습니다.

이제 신규 기능을 계속 확장하지 말고, 현재 서비스를 제출·공유 가능한 후보 버전 RC1으로 정리하세요.

최종 목표는 다음과 같습니다.

- 현재 핵심 기능과 데이터의 의미를 보존한다.
- 제출·공유를 막는 중요한 결함만 찾아 수정한다.
- 개발 서버뿐 아니라 실제 프로덕션 빌드 결과물을 검증한다.
- 본인 1명의 실제 자기평가를 바로 수행할 수 있게 한다.
- 다른 사람이 실행하고 개발 과정을 확인할 수 있는 제출용 자료를 완성한다.

이번 작업에서는 로컬 코드 수정, 필요한 테스트, 빌드, 제출용 복사본·패키지 작성까지 수행합니다.

원격 저장소 생성·공개 전환·푸시, 공개 배포, 외부 서비스의 결제·유료 활성화는 별도 승인 없이 수행하지 마세요.

계획만 제시하고 끝내지 말고, 승인된 로컬 범위의 작업을 실제로 완료하세요.
단, 사람이 직접 수행해야 하는 자기평가와 미승인 외부 공개를 완료한 것처럼 처리하지 마세요.

## 1. 현재 상태를 필요한 범위에서 복원

프로젝트의 적용 지침과 현재 작업 트리 상태를 확인하세요.

우선 다음 자료를 사용하세요.

- README.md
- docs/verification/MVP6_REVIEW.md
- docs/verification/MVP6_DATA.md
- docs/verification/DEMO_CHALLENGE.md
- docs/verification/USABILITY_PROTOCOL.md
- docs/PROMPT_LOG.md
- 현재 app/src, app/tests, package.json, lockfile

파일 이름이나 위치가 달라졌다면 실제 구조를 따르세요.
다른 문서는 필요한 쟁점이 있을 때만 참조하세요.

이전 보고의 기준선은 다음과 같습니다.

- 기준 PDF 38편: 등교 19편, 하교 19편
- 앱의 정류장 관계 355개
- 참고 거리 비교 대상 160관계
- As-is와 To-be에 같은 운행 데이터 사용
- 단위/UI 75개, 브라우저 48개, 실제 Kakao 4사례 통과
- 시연 11과업 검증
- 데이터 청크 약 1.78MB 경고 잔존
- 공개 배포 미실행
- 도로변·당일 운행·일반 사용자의 사용성 효과는 미검증

위 수치는 이전 보고입니다. 현재 상태와 다르면 실제 결과를 우선하고 차이를 설명하세요.

원본 전체 재분석, Kakao 앱 재생성, 키 재발급, 기존 페르소나 평가의 전면 반복은 하지 마세요.

## 2. 기능 동결과 중요한 결함의 판정

기능 범위를 다음으로 동결합니다.

- 광주권 등하교 목록·상세 탐색
- 장소·주소 검색
- 공식 지도 표시점 기반 거리·시간 후보 비교
- 확인된 정보와 미확정 조건의 구분
- As-is/To-be 비교
- 기존 자기평가 도구

새로운 사용자 유형, 추천 점수 체계, 실시간 운행, 계정·DB, 전면 디자인 개편은 추가하지 마세요.

현재 남은 문제를 다음으로 분류하세요.

A. 반드시 수정
- 핵심 과업 중단
- 잘못된 운행·시간·위치 사실을 확정적으로 안내
- 상태 손실로 잘못된 결과 선택
- 중요한 접근성 결함
- 민감정보 노출
- 프로덕션 빌드에서의 기능 실패

B. 실익이 명확하면 수정
- 재현 가능한 탐색 불편
- 현재 결과의 범위를 오해하게 하는 문구
- 측정된 로딩 병목
- 제출·실행 재현을 방해하는 설정

C. 제한 사항으로 수용
- 확보할 수 없는 당일 운행정보
- 근거가 부족한 정류장 좌표
- 관찰되지 않은 사용자 행동 가설
- 효과가 불분명한 미관·구조 변경

C를 해결하려고 공식 사실을 생성하거나 프로젝트 범위를 확장하지 마세요.
모든 경고와 모든 미확정 항목을 제거하는 것을 완료 조건으로 두지 마세요.

## 3. 데이터 범위와 추천 표현 최종 정리

기존 38행 대조표와 데이터 검증 코드를 재사용하세요.
PDF 전체를 처음부터 다시 전사하지 마세요.

다음 집계의 의미를 확인하세요.

- 노선과 개별 운행편
- 고유 정류장 또는 표시점
- 운행편별 정류장 관계
- 좌표가 있는 관계
- 실제 거리 비교에 포함되는 관계

355관계를 고유 정류장 355곳으로 표현하지 마세요.
160/355를 곧바로 위치 확보율이나 서비스 완성도로 표시하지 마세요.

거리 비교에서 제외되는 이유를 가능한 범위에서 집계하세요.
예: 좌표 없음, 방향·관계 연결 미확정, 자료 충돌, 거리 비교 대상이 아닌 학교 노드.

사용자 화면과 README에서 다음을 구분하세요.

- 기준 PDF의 운행편 전체 목록 수록
- 위치가 확인된 일부 관계의 거리 비교
- 적용한 조건에서의 후보 제외
- 아직 정보가 부족해서 비교하지 못한 경우

검색 결과 0건을 “학교 통학버스가 없다” 또는 “오늘 운행하지 않는다”로 해석하게 만들지 마세요.

38편 수록은 해당 기준 PDF에 대한 범위임을 표시하세요.
현행 모든 운행정보나 실시간 운행을 보장한다고 표현하지 마세요.

이미 확인한 시간·위치 정보까지 불필요하게 불확실하게 표현하지 마세요.
미확정인 항목만 제한하고 기존 참고 후보 기능은 유지하세요.

## 4. 프로덕션 성능과 데이터 로딩 점검

현재 설치된 Vite와 의존성 버전을 기준으로 점검하세요.
성능 문제 해결을 이유로 불필요한 메이저 버전 업그레이드를 하지 마세요.

먼저 1.78MB 경고의 실제 원인을 확인하세요.

- 어떤 데이터와 코드가 해당 청크에 포함되는가
- 동일한 객체·출처 설명·검증 메타데이터가 반복되는가
- 최초 화면에서 실제로 필요한 정보는 무엇인가
- 지연 로딩된 파일도 초기 화면에서 즉시 요청되는가
- 원본 크기, 압축 크기, 실제 요청량과 로딩 동작은 어떠한가

실익이 확인되면 다음 중 적절한 방법만 적용하세요.

- 반복 객체와 출처의 ID 참조·정규화
- 화면 실행에 필요한 데이터와 상세 검증 이력의 분리
- 필요한 화면에서의 지연 로딩
- 불필요한 초기 모듈·데이터 로딩 제거

정규화하더라도 출처 추적, 사용자 확인과 공식 확인의 구분, 원문 충돌 이력은 보존하세요.

단순히 경고 임계값을 높이거나 여러 청크로 나누어 경고만 숨기지 마세요.
JSON 파일로 옮겼다는 이유만으로 전송량이나 속도가 개선되었다고 주장하지 마세요.

전후를 같은 환경에서 비교하고, 캐시·네트워크 조건과 측정 한계를 기록하세요.
복잡도 증가에 비해 효과가 작으면 과도한 최적화를 중단하고 잔여 경고를 설명하세요.

## 5. 개발 서버가 아닌 실제 빌드 검증

프로덕션 빌드 결과물을 로컬에서 제공하여 핵심 과업을 확인하세요.

검증 범위:

- 처음 진입 및 새로고침
- As-is/To-be/평가 화면 직접 진입
- 정적 데이터와 지연 로딩 모듈
- 장소·주소 검색과 지도
- 거리·시간 정렬과 금요일 대체 조건
- 후보 상세 왕복과 상태 보존
- 지도·통신 실패 시 목록 탐색 복구
- 평가 시작·종료·내보내기·삭제
- 모바일 레이아웃과 주요 키보드 조작

Kakao SDK 도메인 등록과 프로덕션 미리보기 주소의 관계를 확인하세요.
등록되지 않은 포트·도메인으로 발생한 오류를 앱 결함으로 단정하지 마세요.

기존 등록 주소를 활용하는 방안을 우선 검토하고, 다른 프로세스를 임의로 종료하지 마세요.
계정 설정 변경이 필요하면 기존 승인 범위를 확인하고, 미승인 변경은 보류하세요.

Kakao 검색·지도와 로컬 목록 기능의 장애 범위를 구분하세요.
인터넷 없이 제공할 수 없는 검색·지도까지 오프라인 기능처럼 홍보하지 마세요.

실제 API 검증은 필요한 대표 사례로 제한하고,
경계조건은 가능한 한 모의 테스트로 검증하여 불필요한 호출을 줄이세요.

## 6. 본인 1명 자기평가 마무리

실제 인간 평가는 프로젝트 작성자 본인 1명만 수행합니다.
외부 참가자를 추가 모집하는 것을 이번 완료 조건으로 삼지 마세요.

먼저 기존 실제 자기평가 기록이 있는지 확인하세요.

- 실제 기록이 있으면 실행 버전·과업·측정 조건을 확인하여 분석합니다.
- 없으면 기존 평가 도구와 절차를 사용할 수 있도록 준비하고, 결과는 미실행으로 남깁니다.
- AI·Playwright 실행을 인간 평가 기록으로 바꾸지 않습니다.

평가 전에 RC1 코드·데이터·과업 버전을 식별 가능하게 고정하세요.
기존 커밋 식별자가 없으면 적절한 버전 또는 파일 매니페스트를 사용하세요.

기존 A~D 과업이 현재 데이터로 판정 가능하다면 유지하세요.
As-is와 To-be의 시작 조건·성공 기준을 일치시키고, 정답 힌트를 한쪽에만 제공하지 마세요.

수행 순서와 사전 사용 경험을 기록하세요.
순서 조정만으로 개발자 본인의 숙련도나 학습 효과가 제거되었다고 주장하지 마세요.

여러 과업·반복 시행을 여러 참여자로 계산하지 마세요.
본인 기록은 개발자 자기평가 N=1로만 해석하세요.

시간 감소율을 계산할 경우 비교 가능한 시행, 실패·포기 처리, 분모를 명시하세요.
90% 성공률·30% 시간 감소는 실제 측정 전까지 목표값으로 유지하세요.

평가 후 수정이 발생하면 수정 전후 버전을 구분하고,
이전 기록을 수정된 버전의 결과인 것처럼 재사용하지 마세요.

이번 보고에는 사용자가 직접 해야 할 절차를 기존 평가 화면 기준으로 간단히 제공하세요.
평가 도구를 새로 만드는 작업으로 확대하지 마세요.

## 7. 제출·공유용 파일과 재현성

프로젝트 원본과 공개·제출할 복사본을 구분하세요.

기존 구조를 활용하여 제출용 폴더 또는 패키지를 실제로 작성하세요.
불필요하게 전체 작업 폴더를 그대로 복사하지 마세요.

포함할 핵심 항목:

- 실행 가능한 소스와 lockfile
- 환경변수 예시
- 재현 가능한 설치·실행·빌드 방법
- 프로젝트 설명과 주요 기능
- 데이터 기준과 현재 제한
- 실제 프롬프트 전문과 변경 이력
- 핵심 검증·시연 자료
- 실제 자기평가가 있다면 비식별 요약, 없다면 미실시 상태

원본 프롬프트는 보존하세요.
공유본은 민감정보만 표시 후 마스킹하고, 불리한 기록을 삭제하거나 실제 실행하지 않은 지시를 추가하지 마세요.

공유본에서 점검할 항목:

- .env.local과 인증정보
- Admin·REST 비밀키, 토큰, 쿠키, 로그인 기록
- 개인 주소와 불필요한 식별정보
- 브라우저 추적·스크린샷에 포함된 민감정보
- 절대 로컬 경로와 사용자 환경 의존성
- 공개 범위가 불분명한 자료·이미지
- node_modules, 임시 파일, 불필요한 대용량 산출물

원본을 삭제하지 말고 제출용 복사본에서 제외·마스킹하세요.
재배포 범위가 불명확한 원문은 자동 공개하지 말고 출처와 필요한 근거를 정리하세요.

Kakao JavaScript 키의 브라우저 노출 특성과 비밀 인증정보를 구분하세요.
.env 사용을 비밀 보장의 근거로 삼지 말고,
소스 제출본에는 키를 넣지 않으며 실제 배포에서는 도메인 제한을 확인하도록 정리하세요.

가능하면 깨끗한 임시 복사본에서 lockfile 기반 설치·빌드를 확인하세요.
현재 컴퓨터에 우연히 남아 있는 파일이나 설정에 의존하지 않는지 검사하세요.
로컬 환경·네트워크 제약으로 실행하지 못한 검사는 명확히 구분하세요.

## 8. 과제 평가 기준에 맞는 최종 설명

제출용 설명은 작업량이 아니라 다음 연결을 중심으로 작성하세요.

초기 문제 → 실제 발견한 제약 → 설계 결정 → 구현 → 검증 근거 → 남은 한계

제공된 평가 기준별로 실제 확인할 수 있는 파일·화면·증거를 연결하세요.

- 기획·구현 일치성:
  등하교 정보 탐색이라는 핵심 목적과 후보 비교로 조정한 이유

- 주요 기능:
  실제 검색, 후보 비교, 시간 필터, 지도, 목록 복구의 실행 근거

- UI·디자인:
  발견한 혼동·접근성 문제와 실제 수정 내용

- 프롬프트 및 개선 과정:
  실제 사용자 지시, 변경 이유, 수정 전후 검증

- 공유·제출 충실성:
  실행 방법, 소스, 프롬프트 전문, 결과물 접근 방법

AI 페르소나 수, 테스트 개수, 문서 분량만으로 품질이나 사용자 개선 효과를 주장하지 마세요.

실제 개발 도구를 기록하세요.
과제 원문의 Claude Code 요구를 보존하되,
사용하지 않은 도구나 확보하지 않은 대체 승인을 만들어내지 마세요.
사용자가 이미 결정한 개발 도구를 다시 묻느라 작업을 중단하지 마세요.

기존 DEMO_CHALLENGE.md를 재사용하여 핵심 시연과 장애 대안을 정리하세요.
대규모 예상 질문집을 다시 만들 필요는 없습니다.

## 9. 에이전트·도구 및 검증 운영

실제 독립성이 있을 때만 위임하세요.

권장 분리:
- 성능·프로덕션 실행 점검
- 제출 파일·근거·공개 범위 점검
- 총괄의 통합 판단과 수정

중요 변경 후에는 가능하면 수정에 참여하지 않은 검토자가
변경 범위와 회귀 위험을 제한적으로 확인하게 하세요.

독립 실행 여부를 확인할 수 없다면 수행했다고 보고하지 마세요.

공유 파일과 브라우저 세션의 소유자를 정하고 충돌을 방지하세요.
다시 모든 페르소나에게 전체 사이트를 처음부터 평가시키지 마세요.

개발 중에는 변경 범위의 검사를 우선 실행하고,
최종 통합 시 타입·빌드·단위/UI·브라우저 회귀를 실행하세요.

검증 실패를 없애려고 기대값을 결과에 맞춰 바꾸지 마세요.
테스트가 잘못되었다면 원문·요구사항 근거와 함께 수정 이유를 남기세요.

필수 검증이 통과하고 새로운 중요 결함이 없으면 마무리하세요.
검수를 했다는 이유만으로 다음 검수 단계를 계속 만들지 마세요.

## 10. 산출물·완료 기준·최종 보고

기존 문서를 우선 갱신하고, 필요한 경우 아래 정도로 통합하세요.

- RC1 검증·잔여 위험 보고서
- 제출용 설명 및 파일 색인
- 실행·공유용 소스 패키지
- 기존 자기평가 절차와 프롬프트 이력 갱신

최소 완료 기준:

- 현재 기능과 데이터의 의미가 유지됨
- 반드시 수정해야 할 재현 결함이 해결되거나 차단 사유가 명확함
- 실제 프로덕션 빌드의 주요 과업이 검증됨
- 성능 경고의 원인·조치·잔여 영향이 설명됨
- 목록 전체 범위와 거리 비교 범위가 정확하게 안내됨
- 제출용 복사본의 민감정보와 불필요한 파일이 점검됨
- 타인이 실행할 절차와 자료가 마련됨
- 본인 자기평가의 실시 여부가 정직하게 구분됨

최종 보고에는 다음을 포함하세요.

1. RC1 기술적 준비 상태: 준비 완료 / 조건부 준비 / 중요 결함으로 보류
2. 실제 수정한 문제와 수정 근거
3. 데이터 수록·거리 비교 범위의 정확한 집계
4. 성능 변경 전후와 측정 한계
5. 개발 서버 검사와 프로덕션 검사 결과의 구분
6. 회귀 테스트 결과
7. 제출용 파일·패키지의 실제 경로
8. 본인 자기평가 실시 여부와 다음 직접 조작
9. 수용한 제한 사항과 미해결 차단 요인
10. 공개·공유 단계에서 필요한 승인 사항

공개 배포가 아직 승인되지 않았다면,
권장 공유 방식 하나와 필요한 저장소 공개 범위·배포 대상·Kakao 도메인 변경·비용 여부를
마지막에 한 번에 정리하세요.

실제 생성하지 않은 저장소·배포 주소를 만들어내지 마세요.

이번 단계는 또 다른 기능 확장 MVP를 만드는 작업이 아닙니다.
검증 가능한 범위에서 현재 결과물을 안정화하고,
실제 자기평가와 공유·제출로 넘어갈 수 있는 한 버전으로 마무리하세요.
