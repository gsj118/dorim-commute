# 목포대학교 Unibus HCI 프로젝트 — 실제 정류장 좌표 확보 및 장소 기반 노선 추천 통합

## 0. 역할과 목표

당신은 본 프로젝트의 총괄 소프트웨어 엔지니어이자 데이터 통합·검증 책임자입니다.

현재까지 HCI 연구, 시스템 설계, Unibus 화면 분석, 1차 MVP 개발, Kakao Maps API의 실제 연동 및 브라우저 검증이 완료되었습니다.

이번 작업의 핵심 목표는 **실제 Unibus 정류장 좌표를 확보하고, 이미 작동하는 카카오 장소 검색과 연결하여 이용자가 검색한 광주권 장소 주변의 통학버스 정류장 및 노선 후보를 안내하는 기능을 완성하는 것**입니다.

기존 연구나 구현을 처음부터 반복하지 마세요.

실제 파일 수정, 데이터 확보, 코드 구현, 개발 서버 실행, 테스트, 오류 수정까지 수행하세요.

최대한 작동하는 결과물을 완성하되, 근거가 불충분한 운행정보나 위치정보를 만들어내지 마세요.

## 3. 이번 작업의 우선순위

다음 순서로 진행하세요.

1. 기존 Unibus의 정류장 위치 데이터 확보
2. 방향·운행편·정류장과 실제 좌표 연결
3. 기존 앱의 지도·검색·추천 로직 통합
4. 실제 장소 주변의 정류장 후보 검색
5. 운행조건에 따른 추천 및 참고 후보 구분
6. 지도와 결과 화면에 실제 정보 표시
7. 자동·브라우저 테스트 및 오류 수정

모든 광주권 운행편을 먼저 완성하려고 하지 마세요.

우선 기존 대표 운행편인 송정① 등교와 진월③ 하교를 대상으로 실제 검색부터 후보 안내까지 작동하는 사용자 흐름을 확보하세요.

가능하다면 양방향의 전체 정류장 좌표를 확보하되, 범위가 과도해지면 각 방향의 검증된 정류장 1개 이상을 확보하여 핵심 흐름부터 완성하세요.

대표 정류장의 위치가 확보되지 않더라도 다른 검증 가능한 지점으로 최소 기능을 시험할 수 있습니다. 다만 실제 검증되지 않은 지점에 가상 좌표를 부여해서는 안 됩니다.

## 4. 실제 Unibus 정류장 위치 조사

대상 사이트:
https://mokpo.unibus.kr/#!/index

기존에 확보한 REA 및 브라우저 분석 결과와 화면 캡처를 먼저 확인하세요.

현재 로그인된 브라우저에 접근할 수 있다면 사용 가능한 Browser 또는 Playwright 기능을 활용하세요.

REA의 기존 Chrome CDP 연결이 불가능했던 사실을 고려하고, 이미 성공한 브라우저 제어 방식을 우선하세요.

REA 사용 자체를 필수 조건으로 두지 마세요.

### 4.1 정류장 위치 확인 경로

기존 Unibus 화면에서 다음 탐색 흐름을 사용하세요.

1. 노선 및 정거장 진입
2. 등교 또는 하교 방향 선택
3. 해당 노선 선택
4. 정류장 선택
5. 지도 팝업 확인
6. 지도에 표시된 정류장 마커와 위치 설명 확인
7. 확보 가능한 좌표 및 위치 근거 기록

이전에 사용자가 확인한 것처럼 Unibus 지도 팝업에는 정류장 위치 마커가 표시됩니다.

이 마커를 실제 통학버스 정류장 위치 데이터의 1차 근거로 사용하세요.

다만 공식 웹사이트의 지도 표시점과 실제 도로변 승차 위치의 정확성이 완전히 동일하다고 단정하지 마세요.

### 4.2 숫자 좌표 확보

정상적인 화면 기능에서 제공하는 지도 링크, 위치 공유 기능, 표시 좌표, 공개적으로 접근 가능한 지도정보 등을 우선 활용하세요.

브라우저에서 정상적으로 관찰 가능한 정보로 정확한 숫자 좌표를 확인할 수 있다면 수집하세요.

다음 정보를 함께 기록하세요.

- 노선 ID
- 운행편 ID
- 등교·하교 방향
- 정류장 ID 및 이름
- 위도·경도
- 좌표계
- 좌표의 원천
- 확인 시점
- 실제 승하차 위치 확인 수준
- 관련 증거 위치

화면 스크린샷에 보이는 마커를 눈대중으로 읽어 임의의 위경도를 생성하지 마세요.

지도 중심 좌표, 근처 건물 좌표, 정류장명 검색 결과를 실제 마커 좌표로 대체하지 마세요.

실제 화면에서 정확한 좌표를 확보할 수 없다면 null을 유지하고, 가능한 대체 확인 방법을 기록하세요.

정류장 지도 마커의 숫자 좌표를 확보했더라도 다음을 구분하세요.

A. Unibus 화면에서 직접 확인한 표시 좌표

B. 추가 근거로 실제 도로변 승하차 위치까지 확인된 좌표

C. 지도·주소 검색으로만 발견한 후보 좌표

A는 출처와 한계를 명시한 참고용 위치 안내에 사용할 수 있습니다. 실제 승차 지점의 정확성을 보장하는 표현에는 B 수준의 근거가 필요합니다.

C를 검증된 승하차 좌표로 승격하지 마세요.

### 4.3 정류장 방향 검증

같은 이름의 정류장이라도 등교 승차 위치와 하교 하차 위치가 다를 수 있습니다.

특히 도로 양편 정류장은 별도의 위치 관계로 관리하세요.

서광주우체국, CU 승차 지점, 주요 환승·생활권 지점을 조사할 때 실제 방향과 운행편 관계를 함께 확인하세요.

기존 공식 노선표의 정류장명과 웹사이트의 표시명이 다르면 근거를 검토하고 별칭으로 연결할 수 있는지 판단하세요.

명칭이 비슷하다는 이유만으로 다른 정류장을 동일한 위치로 통합하지 마세요.

## 5. 확보한 좌표의 실제 앱 통합

기존 app/src/data/routes.json 및 데이터 모델을 활용하세요.

좌표를 확보한 정류장만 실제 위치 데이터로 보완하세요.

다음 항목을 보존하세요.

- 실제 노선 및 운행편과의 연결
- 방향별 정류장 관계
- 확인된 운행시간 및 조건
- 원본 노선표 출처
- 위치 좌표 출처
- 검증 상태
- 유효기간 및 확인 시점

좌표의 VERIFIED 여부만 확인하지 말고 원천과 검증 범위를 함께 고려하세요.

실제로 검증된 좌표가 없는 정류장은 지도에서 정확한 승하차 위치처럼 표시하지 마세요.

데이터 모델의 수정이 필요하다면 기존 타입·도메인 함수·테스트의 의미를 유지하면서 최소한으로 변경하세요.

개발용 가상 데이터와 실제 데이터는 계속 분리하세요.

## 6. 장소 검색과 정류장 후보 탐색 연결

기존 Kakao API 연동 기능을 재사용하세요.

사용자가 다음과 같은 장소를 검색할 수 있어야 합니다.

- 광주권 아파트
- 상가 및 건물
- 학교·병원·공공기관
- 도로명주소와 지번주소
- 주요 생활권 장소

### 등교

사용자가 검색한 광주권 출발지에서 접근 가능한 목포대학교 도림캠퍼스행 승차 정류장을 찾습니다.

### 하교

목포대학교 도림캠퍼스에서 출발하는 광주행 운행편 중 검색한 목적지 주변의 하차 정류장을 찾습니다.

### 처리 과정

1. 등교·하교 방향 확인
2. 장소 검색 및 명시적 선택
3. 선택한 장소의 실제 좌표 확보
4. 지원 지역 확인
5. 해당 방향의 정류장 후보 조회
6. 운행편 경유 여부 및 승하차 관계 확인
7. 운행조건 확인
8. 좌표가 확인된 후보의 직선거리 계산
9. 유효 후보 정렬
10. 추천 근거 및 불확실성 표시

단순히 가장 가까운 정류장 하나만 찾지 말고, 실제 이용 가능성이 있는 복수 후보를 비교할 수 있도록 구현하세요.

정류장 후보 탐색 반경이나 결과 개수 제한이 필요하다면 근거를 설명하고, 조정 가능한 설정값으로 관리하세요.

적합한 정류장이 없거나 지나치게 멀다면 무조건 가장 가까운 버스를 추천하지 말고 결과 없음 또는 제한적 후보로 안내하세요.

## 7. 추천 결과와 참고 후보의 구분

현재 기존 연구에서 일부 운행요일, 실제 정류장 위치, 특수일 운행조건이 미확정 상태임을 유지하세요.

다음 두 상태를 명확하게 구분하세요.

### 추천 가능 후보

실제 경유 관계, 방향, 위치 좌표 및 필요한 운행조건을 확인하여 적용된 검색 조건에 적합하다고 판정할 수 있는 후보입니다.

### 참고 후보

일부 정보는 확인되지만 실제 이용 가능 여부를 확정하기에는 근거가 부족한 후보입니다.

참고 후보에는 부족한 정보를 명시하고 공식 확인 경로를 제공하세요.

정보가 부족하다고 후보를 무조건 숨기지는 말되, 확정적으로 운행한다고 표시하지 마세요.

특정 날짜의 운행 여부를 검증하지 못했다면 해당 날짜에 이용 가능하다는 추천을 확정하지 마세요.

시간표에 없는 중간 정류장 도착시각을 계산하여 공식 시간처럼 표시하지 마세요.

직선거리를 도보거리 또는 실제 이동시간으로 표시하지 마세요.

## 8. 추천 결과 화면 완성

실제 검색 결과가 확보되면 다음을 표시하세요.

- 사용자가 선택한 장소
- 해당 장소의 지도 위치
- 검색 장소 주변의 정류장 후보
- 정류장명과 방향
- 해당 운행편의 노선명
- 검증된 위치까지의 직선거리
- 확인된 출발·승차 시각
- 운행조건
- 추천 또는 참고 후보인 이유
- 공식 자료 및 좌표의 출처
- 확인되지 않은 사항

지도에서는 검색 장소와 통학버스 정류장을 서로 구분하여 표시하세요.

후보를 선택하면 해당 노선 상세 및 정류장 정보로 이동할 수 있어야 합니다.

검색 결과가 없는 경우에도 기존 등교·하교 목록으로 돌아갈 수 있어야 합니다.

모바일 화면에서는 지도와 결과 목록 사이를 쉽게 이동할 수 있도록 구성하세요.

기존 UX 구조와 시각적 일관성을 유지하세요.

추가적인 디자인 확장보다 정확한 데이터 연결과 주요 과업의 완수를 우선하세요.

## 9. 독립 하위 에이전트 활용

이번 작업에서 독립적인 분석과 개발이 가능하다면 하위 에이전트를 활용하세요.

### Agent A — Unibus 좌표 및 데이터 검증

- 기존 REA 증거 확인
- 실제 정류장 지도 마커 조사
- 방향 및 운행편 연결
- 숫자 좌표와 좌표계 확인
- 데이터 출처 및 신뢰 수준 기록

### Agent B — 추천 기능 및 UI 통합

- 기존 추천 알고리즘 확인
- 실제 좌표 데이터 연결
- 장소 검색 결과와 정류장 후보 연결
- 추천 결과 UI 구현
- 정상·예외 테스트 추가

총괄 에이전트는 두 작업을 통합하고 데이터 계약을 검증하며 실제 브라우저 테스트를 수행하세요.

브라우저 세션이나 동일 파일에 대한 접근 충돌이 예상되면 순차적으로 실행하세요.

전문 에이전트 간 형식적인 토론은 필요하지 않습니다. 실제 데이터나 설계 판단이 충돌하는 경우에만 교차검증하세요.

하위 에이전트 수를 늘리는 것보다 실제 기능 완성과 검증을 우선하세요.

## 10. 실제 테스트 및 오류 수정

기존 테스트가 유지되는지 확인하세요.

필수 검사:
- TypeScript 타입 검사
- 프로덕션 빌드
- 기존 단위·UI 테스트
- 기존 Playwright 브라우저 테스트
- 등교·하교 목록 및 상세 탐색
- 검색 오류 복구
- 모바일 반응형 및 주요 접근성 검사

추가할 검사:
- 실제 장소 검색 후 좌표 선택
- 실제 Unibus 정류장 위치 표시
- 검색 장소와 정류장 사이 거리 계산
- 복수 후보의 거리순 정렬
- 등교·하교 반대 방향 혼동 방지
- 운행조건 미확정 후보 처리
- 위치 정보가 없는 정류장 처리
- 근접 정류장 없음 처리
- 지도 API 오류 후 재시도
- 검색 결과에서 노선 상세 이동

실제 Kakao 연결 검증은 기존 설정을 재사용하여 수행하세요.

외부 서비스 요청은 필요한 검증 범위로 제한하세요.

모의 데이터 검증과 실제 데이터 통합 검증을 구분하세요.

실제 검증된 좌표가 확보되면 최소한 등교 1건과 하교 1건의 사용자 과업을 브라우저에서 끝까지 실행하세요.

실제로 발생한 오류는 원인을 확인하고 수정한 뒤 관련 테스트를 재실행하세요.

## 11. 작업 완료 기준

다음 조건을 목표로 하세요.

1. 기존 1차 MVP 기능이 유지됩니다.
2. 기존 Kakao API 연동이 정상 작동합니다.
3. 실제 Unibus 정류장 좌표를 가능한 범위까지 확보합니다.
4. 확보한 좌표와 운행편 관계가 정확하게 연결됩니다.
5. 사용자가 광주권 장소를 실제 검색할 수 있습니다.
6. 해당 장소 주변의 검증된 정류장 후보를 조회할 수 있습니다.
7. 실제 좌표 기반 직선거리를 계산할 수 있습니다.
8. 적용 가능한 운행조건에 따라 추천·참고 후보를 구분합니다.
9. 지도에 장소와 정류장을 표시할 수 있습니다.
10. 실제 데이터 기반 통합 테스트와 기존 회귀 테스트를 수행합니다.

외부 사이트의 제약으로 숫자 좌표를 확보하지 못하면 해당 사유와 실제 시도 결과를 보고하세요.

그 경우에도 좌표를 확보했을 때 즉시 작동할 수 있도록 데이터 연결, 후보 탐색, 추천 UI, 자동 테스트 등 독립적으로 구현 가능한 범위는 완료하세요.

확보하지 못한 실제 데이터를 가상값으로 대신하여 완료 조건을 충족했다고 보고하지 마세요.
