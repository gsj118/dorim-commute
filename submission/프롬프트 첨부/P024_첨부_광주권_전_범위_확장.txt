# 목포대학교 Unibus HCI 프로젝트 — 6차 MVP 전체 광주권 데이터 확장·사용자 관점 점검·시연 공격 검증

## 0. 목표와 실행 범위

당신은 HCI 평가·운행 데이터·소프트웨어 품질을 통합하는 총괄이다. 기존 프로젝트를 이어서 실제 코드 수정, 공식 자료 대조, 브라우저 실행, 결함 수정, 회귀 검증과 문서화를 수행하라.

이번 목표는 다음과 같다.
1. 대표8편에 머문 데이터를 기준 PDF의 전체 광주권 등교·하교 운행편으로 확장한다.
2. 일반 이용자에 가까운 제한정보 관점으로 탐색 흐름을 점검한다.
3. 전문 검증자 관점으로 데이터·조건·기능·접근성 결함을 찾는다.
4. 시연 중 예상 밖 조작을 요구하고 설계 근거를 집요하게 따지는 평가자를 시뮬레이션한다.
5. 재현 근거가 있는 문제를 고치고 실제 시연 준비물을 만든다.

이 프롬프트는 실제 실행 지시다. 분석·역할 소개·제안만으로 끝내지 말라. 실제 인간의 이해·감정·시간·만족도·성공률은 만들지 말라. 가상 페르소나의 수나 의견 일치를 연구 표본으로 세지 말라.

## 1. 시작점과 보호 범위

AGENTS.md 및 하위 지침을 먼저 읽고, 현재 코드를 직접 확인하라. 필요한 문서만 선택해서 읽는다.
- README.md
- docs/context/SOURCE_INDEX.md, DATA_RULES.md, RESEARCH_FINDINGS.md, REQUIREMENTS.md
- docs/design/SYSTEM_SPEC.md, UX_FLOW.md, DESIGN_DECISIONS.md
- docs/verification/MVP5_REVIEW.md, MVP3_DATA.md, USER_CONFIRMATIONS.md, USABILITY_PROTOCOL.md
- docs/verification/AI_PERSONA_REVIEW.md, HEURISTIC_REVIEW.md, COGNITIVE_WALKTHROUGH.md
- app/src, app/tests, 기존 검증 스크립트와 관련 증거

이전 보고는 단서다. 현재 파일·명령·브라우저 결과를 확인하라. 기존69단위/UI·36브라우저·실Kakao4사례 통과는 당시 결과이며 새 성공으로 재사용하지 말라. 실제 자기평가는 문서상 미실시지만 사용자가 이후 수행했을 가능성도 있으므로 현재 파일과 제공 기록을 확인하고, 증거 없이 실시/미실시를 변경하지 말라. 사용자에게 파일 제출을 강제하며 독립 작업을 중단하지 말라.

원본 연구·강의·공식 자료·기존 증거·사용자 변경·Kakao 키/앱/도메인 설정을 보호하라. 키를 출력하지 말고, 새 앱/키 발급·유료 활성화·결제·외부 연락·푸시·공개 배포는 하지 말라. 필요 없는 설치·재설계는 피하라. 현재 요청 원문은 기존 PROMPT_LOG 방식으로 보존하라.

## 2. 우선 과제: 전체 광주권 수록 범위 완성

현재 알려진 수록은 등교 송정①④⑤⑥⑩, 하교 진월①③④의8편이다. 기준 S25 PDF의 실제 경로를 SOURCE_INDEX에서 찾고 광주권 등교·하교 표 전체와 대조하라. 전체 수와 빠진 편은 원문에서 확인하며 추정하지 말라. 목포 등 다른 권역까지 임의로 확대하지 말라.

먼저 원문 행별 대조표를 작성한다.
- 방향·문서 편명·원문 페이지/행
- 현재 수록 여부와 누락 지점/시각/조건
- 명확히 전사 가능한 정보
- 충돌·자료 부족과 해당 필드의 처리
- 위치/숫자좌표/방향·편 연결의 근거 상태

누락 편과 지점·문서 시각·요일/금요일 대체·원문 비고를 구축하라. 하교를 등교 역순으로 만들지 말라. 같은 이름의 다른 방향·편 위치를 임의 병합하지 말라. 공개 공식 Unibus의 해당 방향/편/정류장 지도 표시점을 정상 경로로 확인해 숫자좌표를 확보할 수 있으면 연결하라. 지도 중심·근처시설 좌표·등교 좌표로 하교 위치를 대체하지 말라.

숫자좌표가 없으면 null과 위치 텍스트로 목록/상세를 제공한다. 한 필드가 미확정이라는 이유로 명확한 편 전체를 조용히 누락하지 말라. 충돌 정보는 원문과 양쪽 근거를 보존하고 확정 시간판정·거리후보·평가 정답에서 관련 범위만 보류한다. 미수록과 미운행, 위치 미확보와 운행 불가를 구분하라. 실제도로변 확인·특정날짜 운행 확인으로 승격하지 말라.

완료 보고에서 다음을 따로 세라.
① PDF 광주권 전체 행 대비 문서 전사 범위
② 목록/상세에서 확인 가능한 편·지점 범위
③ 확보 좌표로 거리 비교 가능한 관계 범위
④ 충돌/보류/위치 미확보 범위
⑤ 현재 실제 운행 확인 범위

전사만 완료하고 거리/실제 운행까지 전부 검증했다고 표현하지 말라. As-is와 To-be는 확장된 동일 데이터·시각 해석·불확실성 정책을 사용한다. 기존8편에만 맞춘 고정 문구·개수·테스트·과업도 함께 점검한다. CF는 필요한 원문 근거로 갱신한다.

## 3. 역할군 A: 실제 이용 상황에 가까운 가상 사용자

아래는 관점과 제약을 가진 AI 시뮬레이션이다. 실제 사람을 관찰한 결과가 아니다. 각 역할은 목표·알고 있는 정보·모르는 정보·허용 도움·성공 기준을 먼저 정의한다. 시작할 때 정답 노선/클릭 경로를 제공하지 말라. 이미 가진 개발 맥락을 완전히 지웠거나 진짜 초보자를 재현했다고 주장하지 말라.

A1 처음 이용하는 학생: 집 근처 아파트/건물명만 알고 정류장·노선명을 모른다. 등교 승차 지점과 두 편 이상의 승차시각·위치 근거·추가 확인을 찾는다.
A2 익숙한 통학생: 자주 타는 편을 알고 목록으로 바로 들어간다. 다른 편과 변경된 조건을 확인하며 강제 장소검색 없이 이용할 수 있어야 한다. 실제 변경 전후 자료가 없으면 변경 사실을 만들지 않는다.
A3 시간 제약 하교 이용자: 학교에서16시 이후 출발 가능하고 목적지 주변을 비교한다. 월요일/금요일 대체·시간순/거리순·0건 복구를 확인한다.
A4 모바일 저숙련·설명을 건너뛰는 이용자: 작은 화면에서 눈에 띄는 버튼과 번호를 보고 탐색한다. 잘못된 장소/방향 선택을 바꿔보고 지도·목록·상세·뒤로가기를 오간다. 오류를 일부러 주입한 행동과 정상 사용자에게 일어날 수 있다는 가정을 구분한다.

선택적 입력·공개시설명으로도 과업을 수행한다. 정확한 집주소·위치 권한을 필수화하지 않는다. 실제로 무엇을 읽었는지·헷갈렸는지·느꼈는지 AI가 관측했다고 서술하지 말라. 화면에 드러난 단서와 오해 가능성을 분석하고, 인지적 판단은 가설로 남겨라.

## 4. 역할군 B: 전문적이고 집요한 검증자

B1 운행 데이터 감사자: PDF 전 행·원문 시각/조건·방향·관계·좌표 근거를 앱과 대조한다. 전체 수록 주장과 검색 범위의 예외를 독립 검증한다.
B2 반례 탐색 QA: 순서를 바꾼 조작·연속 조건변경·잘못된 URL/입력·0건·공급자 실패·지연 응답·재시도·중단·새로고침을 검사한다. 모의 장애와 실제 외부 서비스 결과를 구분한다.
B3 접근성·모바일 검토자: 320/390/데스크톱, 가능한 확대/리플로우, 키보드·초점·라벨·상태·대비·지도 없는 대안을 점검한다. axe와 실제 키보드 조작을 병행한다. 자동 위반0을 WCAG 전체 적합으로 쓰지 않는다.
B4 방법론·반대 검토자: As-is/To-be 동일 데이터·시간 정의·순서/초기화·판정주체·JSON 출처를 점검한다. 다른 역할의 지적을 반박하고, 실제 재현·과업 영향·기존 해결 여부·수정 부작용·검증 가능성으로 채택/기각한다. 취향을 결함으로 확정하지 않는다.

## 5. 역할군 C: 시연장에서 까다롭게 요구하는 평가자

무례한 말투를 연기하는 데 시간을 쓰지 말라. 예상 밖 조작을 요구하고 설명의 허점을 찾는 것이 목적이다. 총괄은 상대가 납득했다고 자작 결론을 만들지 말고 화면·원문·시험 결과로 답하라.

C1 즉석 조작 요구자 — “지금 이거 해보세요.”
- “다 넣었다면서요? PDF에서 제가 고른 다른 등교편과 하교편을 바로 찾아보세요.” 기존8편 밖의 명확한 편을 원문에서 실제 골라 실행한다.
- “아파트 이름 말고 주소로 찾아보세요. 잘못된 결과를 골랐다가 바꿔보세요.”
- “하교16시 이후로 찾고 금요일로 바꿔보세요. 왜 후보가 없어지죠?”
- “검색한 뒤 상세를 열고 뒤로 가보세요. 조건이 그대로인가요?”
- “지도/검색이 안 되면요? 휴대폰·키보드로도 해보세요.”
- “이 입력으로 결과가 없으면 다음에 뭘 할 수 있죠?”
실제 브라우저에서 실행하고 화면 변화·실제 메시지·완료/실패/보류를 기록한다.

C2 설계 근거 추궁자 — “이건 왜 이렇게 했어요?”
- “왜 지도보다 목록/장소검색인가요? 익숙한 사람에겐 더 느리지 않나요?”
- “가장 가까운 편이 실제 최적인가요? 직선거리와 걸어가는 거리는 다르잖아요.”
- “같은 정류장 이름인데 왜 다른 카드죠? 같은 도로변이라고 말할 수 있나요?”
- “학교 출발시각을 도착시각으로 오해하지 않나요?”
- “참고 후보·확인 필요 문구가 너무 많지 않나요? 왜 필요한가요?”
- “왜 이 반경/정렬/표시 개수를 썼고 바꿀 수 있죠?”
기존 연구 사실·설계 가설·데이터 제약·사용자 선택·미검증 사항을 나눠 답한다. 근거 부족은 인정하며 필요하면 수정/보류한다. 모든 비판을 새 기능 추가로 해결하지 말라.

C3 주장 검증자·시연 방해 상황 검토자
- “AI 페르소나 여러 명이면 실제 여러 명 사용자 실험인가요?”
- “90%성공·30%단축됐다는 근거가 있나요? 자동 클릭시간 아닌가요?”
- “지금 실제 운행하는 버스라고 보장할 수 있나요?”
- “As-is가 실제 Unibus와 똑같나요? 데이터도 같았나요?”
- “평가하다 새로고침하면요? 준비/판정시간도 측정되나요? 내보낸 건 누구 기록이죠?”
- “시연 직전 인터넷이 끊기면요? API 결과가 달라지면요?”
- “과제는 Claude Code라고 했는데 실제 사용 도구는 무엇인가요?”
사실대로 답하고 제한을 숨기지 말라. 장애 시 목록/문서/재시도/보류로 이어지는 실제 대안을 준비한다. 녹화/캡처·모의 상태를 실시간 성공처럼 보여주거나 검증 미완료 문구를 숨기지 말라.

## 6. 독립성·브라우저 실행·증거 규칙

역할 수와 에이전트 수는 다르다. 실제 분리 이익이 있을 때만 동시 가용 범위 안에서 최소 하위 에이전트를 사용한다. 권장 분리는 데이터/사용자 과업/QA접근성·시연 공격/총괄 통합이다. 같은 파일 동시 편집을 막는다. 가능한 독립 초안 후 교차검토하되 역할극의 다수결로 결론 내리지 않는다.

각 과업을 실행 전에 고정한다. 초기 정보·시작 URL/기기·입력·성공 기준을 기록한다. 실제 조작에 대해 URL, 입력/클릭, 화면 변화, 오류문구, 관련 캡처/시험, 완료/실패/보류, 기대와 실제 차이를 보존한다. 핵심 주장·실패 상태 중심으로 증거를 남기며 매 클릭 전체 DOM/API응답을 수집하지 말라. 키·정확한집주소·계정정보를 기록하지 않는다.

증거 유형을 표시한다.
- SOURCE: 공식문서/기존관찰/사용자확인 사실과 각각의 근거 수준
- AI-HYPOTHESIS: 사용자 행동·이해의 예상 및 휴리스틱/워크스루 해석
- BROWSER-OBSERVED: 실제 입력·화면·오류·초점 등 이번에 관찰한 사실
- AUTOMATED-TEST: 이번에 실행한 검증 결과(실API/모의 구분)
- HUMAN-OBSERVED: 사용자가 실제 직접 수행해 제공한 기록만 해당

기존에 고친 문제는 회귀로 확인하되 새 결함/새 성과로 중복 집계하지 않는다. A/B/C에 같은 문제가 나와도 한 문제로 묶는다. 화면을 조작하지 않은 분석을 브라우저 재현이라고 쓰지 않는다.

## 7. 채택·수정·검증

문제마다 ID, 역할/방법, 증거, 영향 과업, 재현 조건, 심각도(Critical/High/Medium/Low), 발생 가능성의 근거/미측정, 반대 검토, 채택/기각/보류, 수정 전후, 회귀 결과, 잔여 위험을 기록한다.

우선순위는 데이터/방향/시각 오류와 핵심 기능 장애 → 접근성 → 중요한 탐색/이해 문제 → 표현 보완이다. 추정만으로 전체 UI를 바꾸지 말라. 공식 자료 부족과 UI 결함을 구분한다. Critical/High 미해결이 있으면 영향 범위와 우회/차단 여부를 명확히 보고하라.

기존 A~D와 새로 전사한 등교·하교편, 원문 충돌/위치없음/금요일대체/0건복구를 함께 검증한다. 예외를 만들려고 존재하지 않는 운행 사실을 생성하지 말라. 합성 시험 데이터는 실제 데이터와 분리한다.

타입검사·생산빌드·기존/신규 단위UI·Playwright·실Kakao 장소/주소검색·지도·모바일·키보드/axe·평가타이머/중단/내보내기/삭제/새로고침을 변경 범위에 맞게 실행한다. 준비시간과 정지 후 판정시간 제외, selfEvaluation/criterionAssessor/timingStarted·리허설 분리를 보존한다. 기능검증으로 사람의 사용성 효과를 확정하지 말라.

초기 독립 점검→근거 교차검토→국소수정→관련 재검증→최종 회귀 순으로 진행한다. 추가 탐색은 최대2회 중심으로 제한하되 그 과정에서 발견한 주요 수정의 필수 재검증은 마쳐라. 새로운 근거 없이 같은 토론/전체테스트를 반복하지 말라. 실제 인간 평가가 없다는 이유로 독립적으로 가능한 작업을 멈추지 말라.

## 8. 시연 준비물과 산출물

기존 구조를 확인하고 중복 문서를 최소화하라. 기존 연구/5차 증거를 덮어쓰지 말라. 필요한 산출물은 다음과 같다.
- 전체 광주권 PDF→앱 행별 수록/보류/좌표 범위 대조표
- 역할별 분석과 통합 문제표(실제 브라우저 재현·기각 근거 포함)
- docs/verification/MVP6_REVIEW.md
- docs/verification/DEMO_CHALLENGE.md: 주 시연 흐름, 즉석 요구 목록, 질문→실행→예상 화면/자료상 판정→실제 결과→솔직한 답변 근거→실패 시 대안
- 새 검증 증거와 관련 README/현재기준/결정기록/PROMPT_LOG 갱신

질문 방어 문구만 작성하지 말고 브라우저에서 실제 확인하라. 시연 시나리오는 짧은 핵심 흐름과 확장 요구를 나누며 소요시간을 실측하지 않았으면 예상이라고 표시한다. 실제 정류장 도착시각·도보시간·사용자 발언·만족도를 만들어 넣지 않는다.

## 9. 완료 기준과 최종 보고

1. 공식 PDF 광주권 등하교 전체 행의 누락/충돌/수록 상태가 추적 가능하다.
2. 명확한 운행편·지점·문서시각/비고는 앱에 반영되고 As-is/To-be 자료가 같다.
3. 거리후보 범위와 목록 범위, 실제운행 확인 수준을 따로 보고한다.
4. 일반 사용자 관점·전문 검증·까다로운 시연 요구를 실제로 수행하고 분석과 관찰을 구분한다.
5. 근거 있는 주요 결함 수정과 필요한 회귀 검증을 마친다.
6. 실제 시연 가능한 핵심 흐름·즉석 요구·질문 근거·장애 대안을 준비한다.
7. 실제 인간이 수행하지 않은 결과는 비워두고 일반 사용자 효과를 주장하지 않는다.

최종 보고는 실제 수행한 역할/도구, 전체 수록 대조 결과, 새로 재현한 문제, 채택/기각 이유, 수정 전후와 테스트 결과, 시연에서 가능한 것/보류할 것, 질문 대응 근거, 남은 중요한 문제, 변경 파일 순으로 간결하게 제시하라. 테스트/브라우저/사람 평가의 미실행·실패·환경 제약을 구분하라. 수행하지 않은 역할·실험·증거를 완료로 보고하지 말라.
