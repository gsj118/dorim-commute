0. 최우선 실행 원칙
────────────────────

이 프롬프트는
앞선 자료 분석을 통해 세부 정확성·누락 방지를 위해 작성된 실행 규칙이다.

따라서 여기 적힌 모든 주의사항과 검수 규칙을
최종 제출 문서 안에 장황하게 그대로 옮기지 마라.

최종 문서는 반드시:

- 원본 워크북이 요구하는 분량

- 대학생 과제다운 자연스러운 설명 수준

을 우선한다.

세부 규칙은 내부 판단·자체검수 기준으로 사용하고,
실제 제출 문서에는 필요한 사실·근거·한계·계획만 간결하게 표현한다.

즉,
프롬프트는 길어도
최종 과제는 불필요하게 장황한 규정집처럼 만들지 않는다.

새 Work 채팅에 실제로 첨부된 자료 목록을 먼저 확인하고,

과제 요구사항의 우선순위:

2) 교수자의 작성예시

서비스 사실의 우선순위:

링크만 있고 실제로 열지 못한 자료도
읽었다고 주장하지 않는다.

────────────────────
1-1. 공식 통학버스 노선표 처리 원칙
────────────────────

앞선 분석에서는
업로드 환경의 제한 때문에
공식 통학버스 노선표 PDF 대신
해당 PDF의 페이지 이미지 3장을 사용해 사실을 검토했다.

그것은 자료 부족이 아니라
당시 업로드 제약에 따른 임시 처리였다.

이번 새 Work에서는
실제 원본 통학버스 운행노선 PDF가 첨부되어 있다면
그 PDF를 최우선 근거로 직접 읽고 검증한다.

원본 PDF가 있는 경우:

- PDF 자체의 제목
- 페이지
- 표의 행·열
- 병합 셀
- 색상
- 각주
- 비고
- 노선/편 구분
- 승차지점
- 시각
- 요일 조건
- 캠퍼스 경유
- 예외 문구

를 직접 확인한다.

앞선 이미지 판독 결과를 그대로 복사하지 말고
원본 PDF와 다시 대조한다.

원본 PDF와 앞선 이미지 판독이 충돌하면
원본 PDF를 기준으로 수정한다.

반대로 원본 PDF를 실제로 열 수 없고
페이지 이미지밖에 없는 경우에만
출처를
“제공된 노선표 페이지 이미지”
라고 정확히 표현한다.

PDF를 열지 못했는데 열었다고 주장하지 않는다.

표의 행·열·병합 셀·색상·각주를 실제 자료로 확인하고,
읽기 어려운 지명·시간·요일을 추정하지 않는다.

────────────────────
3. 확인된 서비스 사실과 중요한 한계
────────────────────

아래 내용은
첨부된 실제 Unibus 화면 정리본과
원본 공식 통학버스 자료를 직접 다시 대조한 후 사용한다.

기존 분석을 그대로 복사하지 말고
실제 첨부 자료가 이를 지원하는지 재검증한다.

Unibus 화면 정리본에서 확인할 핵심:

- 홈에 노선안내·버스예약·차량위치조회 등의 진입 기능과 공지사항이 제공됨
- 노선 및 정거장 화면에 등교/하교 탭 존재
- 등교 목록에 노선 식별 정보·주요 출발지·시각 등이 결합된 항목 존재
- 항목 선택 후 특정 노선의 정류장 목록 확인 가능
- 각 정류장 옆 지도 기능 존재
- 선택 정류장을 지도 팝업에서 확인 가능
- 지도/로드뷰 탭 존재
- 차량위치조회는 별도 기능
- 버스예약 기능 존재
- 공지사항과 문의게시판 존재
- 학기 운행 공지에서 통학버스 노선표 첨부 제공

중요한 제한:

제공된 화면에서
일반 생활권 장소 입력
→ 주변 통학버스 승차지점 탐색

흐름은 확인되지 않았다.

그러나 이를

“Unibus 전체 서비스에 절대로 그런 기능이 없다”

라고 확대해서 단정하지 않는다.

표현은 필요하면:

“제공된 화면 범위에서는 확인되지 않았다.”

로 제한한다.

또한:

- 하교 탭이 있다는 것과 하교 전체 화면을 검증했다는 것은 다르다.
- 로드뷰 탭 존재와 실제 작동 확인은 다르다.
- 정적 캡처만으로 모든 상호작용을 시험한 것처럼 쓰지 않는다.
- 화면은 주로 데스크톱 캡처이므로 모바일 사용성 문제를 직접 관찰한 것처럼 쓰지 않는다.
- 기존 지도 기능은 분명히 인정한다.
- 지도 기능이 없어서 문제라고 쓰지 않는다.
- 차량위치 갱신 주기·정확도는 미확인이다.
- 버스예약의 실제 이용률·필수 여부도 미확인이다.

화면 예시 중
“담양) 광주송정역 07:20”
등 특정 노선 상세가 보이더라도
그 화면이 공식 도림캠퍼스 광주권 노선표의 특정 운행편과
동일하다고 자동 결합하지 않는다.

그 화면은 UI 구조의 근거로 사용하고,
공식 운행 데이터는 원본 노선표와 별도로 검증한다.

────────────────────
3-1. 공식 노선표에서 재검증할 핵심
────────────────────

원본 PDF를 직접 확인하여
다음 기존 분석이 맞는지 다시 검증한다.

- 제목이 「2026학년도 2학기 통학버스 노선표(안)」인지
- 광주권 등교가 15개 노선·19편인지
- 월~목 운행 4편 포함 여부
- 광주권 하교가 13개 노선·19편인지
- 노선 안에 여러 승차지점과 시각이 순서대로 연결되는지
- 동일 지점명이 여러 경로에 등장하는지
- 일부 행에 요일 조건이 있는지
- 금요일 별도 시간이 존재하는지
- 에너지밸리캠퍼스 경유 등의 조건이 존재하는지
- 날씨·탑승인원·수업 등에 따른 조정 안내가 존재하는지

원본 PDF가 기존 분석과 다르면
반드시 원본을 기준으로 수정한다.

특히:

노선
운행편
차량번호
승차지점

을 같은 단위로 쓰지 않는다.

15개 노선·19편이라면
19편을 19개 노선이라고 쓰지 않는다.

한 운행편에 여러 승차지점과 시간이 연결된다면
데이터 구조 역시

‘정류장명 → 시간 하나’

가 아니라

‘운행편 → 정차 순서 → 승차지점 → 해당 시각’

관계임을 이해한다.

동일한 승차지점명이 여러 경로에 등장한다고 해서
물리적으로 동일한 승차 위치라고
추가 검증 없이 단정하지 않는다.

전체 고유 승차지점 수를
직접 계산·검증하지 않았다면 숫자를 만들지 않는다.

────────────────────
3-2. 공지사항의 내부 불일치
────────────────────

기존 화면 분석에서

공지 제목:
2026학년도 2학기

인데

본문 운행기간:
2025. 9. 1.(화) ~ 12. 18.(월)

처럼 보이는 불일치가 확인되었다.

새 Work에서 실제 화면을 다시 보고 검증한다.

실제로 불일치한다면
임의로 2026년으로 고치지 않는다.

필요하다면:

“제공 공지 화면에는 학년도 표기와 본문 운행기간 연도 사이에
불일치가 있어 정확한 운행기간은 추가 확인이 필요하다.”

정도로 짧게 처리한다.

이번 프로젝트의 핵심 문제와 직접 관련이 없다면
이 사실을 본문에서 과도하게 강조하지 않는다.

연구 과업에서 사용할 실제 노선·시각·요일은
사용자 평가 전에 최신 공지와 다시 대조할 계획을 넣는다.

────────────────────
4. 개인 경험과 연구 진실성
────────────────────

작성자는 실제 목포대학교 통학버스 이용자이며
개인적으로는 버스예약 없이
노선과 시간을 확인한 뒤 버스에 탑승하고 있다.

이것을:

- 학생 전체의 이용 방식
- 예약 기능 불필요
- 예약 기능 미사용

으로 일반화하지 않는다.

학교 커뮤니티에서

“○○에서 학교 가려면 어떤 버스를 타야 하나요?”
“어디서 타야 하나요?”
“어디에서 내려야 하나요?”

같은 질문을 본 경험은
개인적인 문제 발견 계기로만 사용한다.

게시물 수,
빈도,
전체 학생 행동에 대한 조사 결과로 사용하지 않는다.

현재 정식:

- 인터뷰
- 설문
- 맥락질의
- 사용성 테스트

는 수행하지 않았다.

실제 사용자 발화,
관찰 사건,
인사이트,
성공률,
완료시간을 생성하지 않는다.

연구자 또는 AI 역할극은
질문·절차 연습이나 파일럿 아이디어 검토용일 뿐
실제 참여자 자료가 아니다.

문제 존재와 해결안의 유용성 모두
향후 사용자 연구에서 반박될 수 있어야 한다.

기존 방식으로 쉽게 해결하는 사례도
반대 사례로 보존한다.

────────────────────
5. 5W1H 작성 방향
────────────────────

Who:

광주권에서 도림캠퍼스로 통학하며
출발 장소와 통학버스 노선·승차지점의 대응에
충분히 익숙하지 않은 재학생.

신입생만으로 제한하지 않는다.

향후 참여자 모집도
“현재 UI가 불편한 학생”만 찾지 않는다.

실제 이용 경험,
이용 가능성,
Unibus 숙련도 차이를 고려한다.

What:

자신이 알고 있는 생활권 장소를 기준으로

- 이용 가능한 승차지점
- 적절한 등교 운행편
- 탑승 시각
- 실제 승차 위치

를 찾고 이해하는 과업.

문제는
Unibus 전체 UI 품질이 나쁘다는 것이 아니다.

현실에서 알고 있는 장소와
통학버스 내부의 노선·승차지점 체계를
연결하는 초기 탐색에 어려움이 있을 가능성을 검증한다.

When:

등교 전에 승차정보를 확인할 때,
평소와 다른 광주권 장소에서 학교로 이동하려 할 때,
처음 또는 익숙하지 않은 승차지점을 찾아야 할 때.

실제 발생 빈도는 조사하지 않았으므로
“자주 발생한다”고 쓰지 않는다.

Where:

스마트폰 중심 사용을 연구·설계 대상으로 삼는다.

실제 사용자 연구에서는
집이나 안전하게 정지한 일상 장소 등
현실적인 맥락을 확인한다.

데스크톱 캡처만으로
모바일에서 특정 문제가 발생한다고 단정하지 않는다.

Why:

사용자가

어디에서
어떤 버스를
몇 시에 타야 하는지

올바르게 이해하도록 돕는 것이 핵심 사용자 가치다.

지각,
오탑승,
반복 탐색 등이 실제로 얼마나 발생하는지는
아직 미확인이다.

How:

현재 자료에서 확인되는 기본 흐름은

노선/주요 출발지점 선택
→ 정류장 목록 확인
→ 선택 정류장 지도 확인

이다.

필요하면 공지·노선표 등을 함께 확인할 수 있다.

사용자가 실제로

- 여러 노선을 반복 확인하는지
- 외부 지도를 병행하는지
- 학교 커뮤니티를 검색하는지
- 주변 사람에게 질문하는지

는 사용자 연구에서 확인한다.

5W1H 뒤에
짧고 명확한 문제 가설 문장을 작성한다.

해결책을 문제문장에 미리 끼워 넣지 않는다.

가능하면 쉬운 말로:

사용자는
“나는 이 장소 근처에 있다.”

에서 출발할 수 있지만,

현재 확인된 시스템 흐름은
“어느 통학버스 노선을 먼저 볼 것인가.”

에서 시작한다는 차이를 설명한다.

노선을 이미 잘 아는 사용자에게는
현재 흐름이 충분히 유용할 가능성도 인정한다.

────────────────────
6. E01~E03
────────────────────

실제 첨부 자료를 다시 확인한 뒤
다음 세 근거를 중심으로 작성한다.

E01 — 노선 중심의 진입 구조

내용:
노선/주요 출발지점 항목을 먼저 선택하고
그 뒤 해당 노선의 정류장 목록을 확인하는 구조.

출처:
Unibus ‘노선 및 정거장’ 화면 및 노선 상세 화면.

가능하면 내부 이미지 파일명 대신
사람이 알아볼 수 있는 출처명을 사용한다.

한계:
이 구조가 실제 사용자에게 어렵거나
반복 탐색을 일으킨다는 사실까지 관찰한 것은 아니다.

E02 — 기존 위치 확인 기능과 다른 탐색 방향

내용:
선택한 통학버스 정류장의 위치를
지도에서 확인하는 기능은 이미 존재한다.

그러나 제공된 화면 범위에서는

일반 생활권 장소
→ 주변 통학버스 승차지점

방향의 탐색 흐름은 확인되지 않았다.

출처:
Unibus 노선 상세·정류장 지도 화면.

한계:
제공된 화면만으로
서비스 전체 기능의 절대적 부재를 증명하지 않는다.

E03 — 실제 운행정보의 구조

내용:
원본 통학버스 노선표에서 검증된
광주권 등교 노선·운행편 및
운행편별 승차지점·시각·요일/경유 조건.

기존 분석에서는
15개 노선·19편으로 확인되었지만,
새 Work의 원본 PDF에서 다시 검증하고
원본 값이 다르면 수정한다.

출처:
2026학년도 2학기 도림캠퍼스 통학버스 운행노선 원본 PDF.

한계:
문서 제목의 ‘(안)’,
운행 조정 가능성,
정보량 자체가 사용자 불편을 증명하지 않는다는 점을 기록한다.

세 근거 모두:

- 내용
- 출처·상황
- 신뢰도
- 한계

를 작성한다.

세 근거는 서비스·문서 근거이지
사용자 행동 연구 결과가 아니다.

────────────────────
7. 목표·해결 가설·측정
────────────────────

프로젝트 기간:
착수 후 6주.

현재값:

미측정 — 2~3주차 기존 방식(B조건) 과업 평가에서 확보 예정

으로 처리한다.

현재 성공률이나
현재 평균 ○초 등을 임의로 만들지 않는다.

또한
“미측정 표기를 교수자가 공식 허용했다”
고 주장하지 않는다.

단지 허위 기준값을 만들지 않기 위해
현재 상태를 정확하게 기록하는 것이다.

잠정 가상 설계 목표:

1)
개선안(I조건)의
올바른 승차정보 확인 성공률 90% 이상

2)
비교 가능한 정확한 완료 과업의
완료시간 중앙값을
B조건 대비 30% 이상 감소

90%와 30%는:

- 교수자 지정 기준이 아님
- 현재 실측 성능이 아님
- 달성이 보장된 값이 아님

을 분명히 한다.

“잠정 가상 설계 목표값”으로 표현한다.

초기 사용자 연구와 파일럿 후,
개선안 본평가 전에 목표값의 타당성을 재검토할 수 있다.

변경한다면:

- 이유
- 시점

을 기록하는 계획을 넣는다.

해결 가설은
기능 목록이 아니라
사용자 결과와 연결한다.

가설 1:

검증된 생활권 장소와
실제 통학버스 승차지점·운행편 정보를 연결하면
사용자가 올바른 승차정보를 확인하는 데 도움이 될 것이다.

가설 2:

승차지점 후보 비교와
위치·시각·운행 조건 확인을 하나의 흐름으로 연결하면
정확성을 유지하면서 대표 과업 완료시간을 줄일 수 있을 것이다.

성공 판정:

지정한:

- 출발 장소
- 목적지
- 요일

조건에서

- 올바른 승차지점
- 해당 운행편 또는 노선
- 탑승 시각
- 실제 위치
- 필요한 운행 조건

을 정확하게 확인하는 경우.

여러 개의 유효한 답이 존재한다면
사전에 검증한 정답 집합을 허용한다.

일반 장소 자체를
통학버스 승차지점으로 오인하면
성공으로 판단하지 않는다.

성공률:

성공한 평가 과업 수 / 실제 수행 과업 수

로 측정한다.

필요하면:

- 참여자 수
- 과업 수
- 성공 건수
- 전체 수행 건수

를 함께 기록한다.

소표본에서 90%라는 숫자가
과도하게 정밀한 의미를 갖지 않는다는 한계도
필요한 정도만 설명한다.

한 사람의 반복 과업을
독립된 여러 사용자처럼 취급하지 않는다.

시간:

과업 제시 후
정해진 시작 기준부터
최종 답을 제시할 때까지 측정한다.

B와 I의:

- 기기
- 정보 범위
- 과업 난도
- 개입 규칙

을 최대한 맞춘다.

가능하면 비슷한 난도의 과업과
순서 교대를 사용해 학습 효과를 줄이는 계획을 넣는다.

실패·오답·시간 초과는
별도로 기록한다.

비교 가능한 성공 자료가 부족하면
시간 개선률을 억지로 산출하지 않는다.

Chapter 05 맥락질의에서
연구자의 질문 때문에 늘어난 시간을
그대로 B/I 시간 비교 baseline으로 사용하지 않는다.

5주 비교 평가에서
필요하면 B조건도 같은 조건에서 다시 측정한다.

시간이 줄었더라도:

- 성공률 저하
- 중대한 오탑승 판단
- 장소/승차지점 혼동

이 발생하면
성공으로 판정하지 않는다.

B조건에서 이미 대부분 쉽게 수행된다면
문제 정의와 해결안을 재검토한다.

목표 미달도 숨기지 않고
실제 프로젝트 결과로 보고한다.

────────────────────
8. 범위·산출물·기술
────────────────────

포함 범위:

- 제한된 광주권 생활권 장소에서
  도림캠퍼스 등교 승차정보 탐색
- 실제 사용자 관찰·인터뷰
- 어피니티·HTA·As-is/To-be·요구사항 도출
- 장소 확인 → 승차지점 후보 → 운행편·시각·위치·조건 확인의 검증용 흐름
- 기존 목록 확인과 대체 탐색 경로
- 지원하지 않는 장소 또는 정보 없음의 최소 예외 흐름
- 종이 프로토타입
- 클릭 가능한 디지털 프로토타입
- 사용자 평가
- 개선

제외 범위:

- 하교/하차 전체 안내
- 광주 전체 노선·장소 데이터 구축
- 실시간 도착 예측
- AI 추천
- 예약 시스템 개편
- 실제 예약·결제
- 필수 위치 권한
- 정확한 집주소 수집
- 완성형 도보 길찾기
- 학교 운영 서버
- 상용 서비스 배포
- 코딩 완성을 프로젝트 성공 조건으로 삼는 것

장기 확장:

- 다른 광주 출발 장소
- 지원 지역·노선 확대
- 선택적 현재 위치
- 도림캠퍼스 → 광주 목적지 하교
- 목적지 기반 하차 안내

산출물:

연구 자료:
연구계획,
동의 절차,
익명화된 사용자 기록,
분석,
요구사항 추적 결과.

프로토타입:
종이 시안 +
실제 검증 데이터를 반영한 클릭 가능한 디지털 시안.

평가 결과:
과업,
판정 기준,
실측 결과,
실패 사례,
B/I 비교,
수정 결과,
한계.

각 산출물에
형식과 완료 기준을 기록한다.

아직 존재하지 않는 파일 링크를 만들지 않는다.

────────────────────
8-1. 기술 데이터 구분
────────────────────

현재 자료와 원본 PDF를 검토하여
다음 네 층위로 구분한다.

A. 현재 자료에서 정리 가능한 데이터

예:
- 승차지점명
- 운행편과의 관계
- 정차 순서
- 시각
- 명시된 요일·경유·예외 조건

B. 추가 검증이 필요한 데이터

예:
- 정확한 승차 위치 좌표
- 일반 생활권 장소 좌표
- 장소와 승차지점의 공간 관계
- 실제 접근 가능성

C. 핵심 UX 가설 검증에 반드시 필요하지 않은 데이터

- 광주 전체 데이터
- 실시간 차량 위치
- 실시간 도착예측
- 전체 자유 장소 검색
- 실제 도보 경로 탐색

D. 실제 웹 프로토타입 확장 시 필요한 선택적 기술

- 제한 장소 데이터
- JSON/CSV
- 웹 UI
- 필요 시 장소검색 API/지오코딩
- 필요 시 지도 API
- 거리 계산

“기술적으로 구현 가능해 보임”

과

“현재 자료만으로 구현 준비 완료”

를 구분한다.

────────────────────
8-2. 선택적 웹 구현
────────────────────

실제 코딩은
사용자 연구 이후의 선택적 확장이다.

연구 결과와 데이터 검증이 허용한다면

약 2개 노선 수준,
검증 가능한 고유 승차지점 약 10~15개

정도부터
작은 실제 작동 웹 프로토타입을 시도할 수 있다.

여건이 충분하다면
2~3개 노선·15~25개 수준으로 확장할 수 있지만
이 숫자는 의무가 아니다.

실제 연구 과업에 필요한 운행편과 장소를 먼저 결정하고,
필요한 데이터 수는 그 결과로 결정한다.

숫자를 맞추기 위해
노선을 임의로 자르거나
요일·예외 조건을 버리지 않는다.

일부 데이터만 지원한다면
지원 범위를 명확하게 표시한다.

전체 광주권을 지원하는 것처럼 꾸미지 않는다.

좌표를 확보·검증하지 않았다면:

- 가장 가까운 정류장
- ○○m
- 도보 ○분

등을 사실처럼 생성하지 않는다.

지도 API 없이도
검증된 장소 선택
→ 고정된 승차지점 후보
→ 이용 정보 확인

흐름으로 핵심 UX 가설을 시험할 수 있다.

4주 말까지
실제 웹 확장 여부를 결정하는 계획을 세운다.

실제 코딩 때문에
5주 사용자 테스트가 지연될 위험이 생기면
즉시 클릭형 프로토타입으로 축소한다.

향후 실제 개발이 필요할 경우
코딩 보조 도구를 활용할 수 있지만
이번 제안서에서 완성형 개발을 약속하지 않는다.

9. 사용자 연구 및 Chapter 04~06 연결
────────────────────

현재 단계에서 가능한 주요 연구질문 후보:

RQ1.
사용자는 실제 등교편 탐색을
어떤 정보와 도구에서 시작하는가?

RQ2.
출발 장소와 통학버스 승차정보를 연결할 때
어떤 판단·장벽·확인 기준이 나타나는가?

RQ3.
통학버스 노선 또는 Unibus 숙련도에 따라
탐색 방식이 어떻게 달라지는가?

최종 Chapter 03 문서에서는
Chapter 04를 대신 작성하지 말고,
6주 계획과 연구 방향에서
후속 과제로 자연스럽게 연결되는 정도로 작성한다.

연구 방법 후보:

실제 과업 관찰
+
반구조화 인터뷰

관찰:
실제 행동 순서,
정보 탐색,
도구 전환,
되돌아감,
중단,
우회 행동 등을 확인한다.

인터뷰:
행동의 이유,
최근 경험,
판단 기준,
기대와 불확실성을 확인한다.

발생하지 않은 행동을
미리 관찰 결과처럼 쓰지 않는다.

참여자:

목포대학교 재학생 중
광주권 통학버스 이용 경험이 있거나
실제로 이용할 가능성이 있는 사람.

“현재 UI가 불편한 사람”만 모집하지 않는다.

숙련도 차이와 반대 사례를 허용한다.

모든 모집 인원은 계획값임을 표시한다.

탐색 연구:
실제 참여자 2~3명 정도를 목표로 계획할 수 있다.

Chapter 05:
실제 참여자 최소 1인 확보가 필수적인 실행 목표.

후반 비교 평가:
실제 참여자 약 5명 내외를 모집 목표로 둘 수 있으나,
실제 확보 인원과 표본 한계는 그대로 보고한다.

기존 참여자가 다시 참여하면
학습 효과 가능성을 기록한다.

참여자 1인의 맥락질의 결과만으로
정량 효과를 입증했다고 하지 않는다.

Chapter 04 연결:

- 연구 목표 1개
- 연구질문 3개
- 참여자 포함/제외 기준
- 관찰 + 인터뷰
- 약 30분 절차
- 질문 가이드
- 기록 양식
- 동의
- 익명화
- 보관·삭제
- 파일럿

으로 이어질 수 있어야 한다.

파일럿·역할극은
실제 연구 결과에서 제외한다.

Chapter 05 연결:

실제 참여자가
평소 기기와 자료를 이용해
대표 과업을 수행하도록 한다.

기록은:

- 행동
- 발화
- 연구자 추론
- 사용자 확인 결과

를 구분한다.

클릭,
멈춤,
되돌아가기,
도구 전환,
지도 사용,
질문,
우회 등은
관찰 후보일 뿐
이미 발생했다고 쓰지 않는다.

실제 자료에서
핵심 사건,
인사이트,
설계 기회를 도출한다.

Chapter 06 연결:

실제 익명화된 원자료에서

행동/발화/사건 하나당
원자적 메모 하나

형태로 20개 이상을 만든다.

자료가 부족하면
추가 관찰한다.

같은 사건을 복제하거나
가상 행동을 만들어 수량을 채우지 않는다.

이후:

- 어피니티 군집
- 반대/미분류 메모
- 인사이트
- 확신도
- HTA
- 선행조건
- 오류·예외
- As-is
- To-be
- 사용자 요구사항
- 성공 지표

로 연결한다.

원자료
→ 메모
→ 군집/인사이트
→ 요구사항
→ 화면
→ 평가

의 추적성을 유지한다.

AI는 익명화된 자료의
대안·누락 검토 등 보조 목적으로만 사용하며
실제 사용자 발화를 생성하지 않는다.

11. 개인 작업 관리·최소 범위
────────────────────

프로젝트는 구서준 1인의 개인 프로젝트다.

PM,
UX Researcher,
Designer,
Developer

등의 역할을
여러 실제 팀원이 있는 것처럼 만들지 않는다.

필요한 업무 역할을
학생 1인이 단계별로 수행한다.

사용자 연구:
연구질문,
모집,
관찰,
인터뷰,
기록,
익명화.

디자인:
As-is/To-be,
정보 구조,
사용자 흐름,
화면 설계.

프로토타입:
종이,
Figma 또는 웹 기반 클릭형 시안,
필요하면 제한된 실제 위치 데이터.

평가:
B/I 비교,
성공률,
완료시간,
오류,
정성 피드백.

도움을 받을 수 있는 대상:

- 실제 사용자 연구 참여자
- 교수자
- 공식 Unibus 자료
- 공식 통학버스 자료
- 지도 관련 공개 자료/API 문서
- AI 코딩 보조 도구

그러나 이들을
팀원처럼 표현하지 않는다.

파일도 가능하면:

- 원자료
- 익명자료
- 분석
- 프로토타입
- 평가

로 구분하고
버전·출처·변경 내용을 관리하는 계획을 넣는다.

지연 시 최소 실행 범위:

- 실제 참여자 최소 1인의 맥락질의 유지
- 실제 근거 분석 유지
- 검증된 1~2개 등교 운행편
- 대표 장소 시나리오 약 2개
- 승차정보 확인 핵심 흐름
- 실제 사용자 평가
- 개선

을 남긴다.

가장 먼저 제거할 것:

- API
- 실제 코딩
- 광주 전체 지원
- 지원 노선 확대
- 하교 기능

비교 평가 표본이 충분하지 않으면
효과가 입증되었다고 쓰지 않는다.

탐색적 결과와 한계를 정직하게 보고한다.

12. 위험·접근성·윤리
────────────────────

워크북의 위험 5종을 모두 작성한다.

가능성·영향은
각 1~3의 계획 단계 주관적 등급이며
실측 확률이 아니다.

초기 제안값:

1. 참여자 모집 실패
가능성 2 / 영향 3

대응:
- 1주부터 참여 후보 접촉
- 예비 참여자 확보
- 필요한 경우 모집 채널 확대

확인:
2주 초

2. 범위 확대
가능성 3 / 영향 3

대응:
- 핵심 / 선택 / 제외 구분
- 이번 핵심은 광주 생활권 → 도림캠퍼스 등교
- 매주 범위 점검

3. 개인정보 노출
가능성 2 / 영향 3

대응:
- 최소 정보 수집
- 참여자 코드
- 실명·학번·집주소 미수집 원칙
- 민감정보가 화면에 나타나면 기록 중단/비식별 처리

확인:
각 연구 세션 전후

4. 기술 구현 불가
가능성 2 / 영향 2

대응:
- API 의존 최소화
- 제한 실제 데이터
- 클릭 가능한 프로토타입 대체
- 실제 코딩보다 사용자 평가 우선

확인:
4주 말

5. AI 오류·환각
가능성 2 / 영향 3

대응:
- 모든 노선·시각·요일·승차지점 공식 자료 대조
- AI가 만든 가상 발화·관찰 결과 사용 금지
- 모든 AI 산출물 사람 검토

위치·운행 데이터의
최신성·정확성 문제도
관련 기술 위험 안에 포함한다.

윤리:

- 연구 목적·시간·기록 방식 안내
- 참여 전 동의
- 중도 중단·철회 가능
- 촬영·녹음은 별도 동의
- 이름 대신 참여자 코드
- 실명·학번·정확한 집주소·불필요한 이동 이력 수집 금지
- 원자료 접근을 연구자 본인으로 제한
- 적절한 보호 저장
- 연구 종료 후 정해진 시점의 삭제 계획

삭제 기간을 제시할 경우
학교 지침이 있으면 그 지침을 우선한다.

학교 지침을 확인하지 않았다면
특정 기간이 공식 규정인 것처럼 쓰지 않는다.

실제 사용자 발화,
개인정보,
원본 화면 기록을
공개형 AI에 그대로 입력하지 않는다.

AI 분석이 필요한 경우
완전히 익명화된 요약을 사용한다.

실제 이동 중 화면 조작이나
위험한 현장 탑승 실험을 요구하지 않는다.

접근성:

- 읽을 수 있는 글자 크기
- 충분한 대비
- 터치 영역
- 색상 외 텍스트 조건 표시
- 위치를 텍스트로도 확인 가능한 구조
- 목록 형태의 대체 탐색 경로

등을 고려한다.

실제로 테스트하지 않은
화면낭독기 완전 지원 등을
완료했다고 주장하지 않는다.

현재 위치는
후속 선택 기능이다.

기본 대표 과업은
사용자가 선택하거나 입력한 장소명으로 수행 가능해야 한다.

13. 원본 워크북 구조·자기검토·AI 기록
────────────────────

원본 워크북의 다음 항목을 모두 유지한다.

0. 활동 흐름
1. 문서 정보
2. 5W1H와 문제 근거
3. 프로젝트 목표와 SMART

문서 작성 완료

“완료했다”고 만들지 않는다.

문서상 검토는 수행할 수 있지만

“제출 전 작성자 리허설 예정”

제출 체크리스트는

“미측정 상태와 baseline 확보 계획을 명확히 기재함”

이라는 상태를 반영한다.

실제 연구,
실제 발표,
사람의 최종 검수

를 하지 않았는데 했다고 체크하지 않는다.

────────────────────
13-1. AI 사용 기록
────────────────────

AI 사용 사실을 솔직하게 기록한다.

이번 문서 작성 과정에서 실제 사용한 역할:

- 교수자 강의자료·워크북 구조 비교
- Chapter 02 결과와 Chapter 03 연결 검토
- 실제 Unibus 화면과 공식 자료 대조 보조
- 프로젝트 범위 검토
- SMART 목표 비평
- 6주 일정 구조화
- 위험 탐색
- Markdown 문장·형식 검수

최종 작성에 사용하는 도구명은
현재 실제 사용하는 작업 환경에 맞게 기록한다.

이전 자료에서 다른 AI 이름이 언급되었다는 이유로
이번 작성 도구를 잘못 기록하지 않는다.

AI 제안 중 채택하지 않은 것의 예:

- 가짜 사용자 연구 결과
- 임의 baseline
- Unibus 전체가 나쁘다는 주장
- 기존 지도 기능이 없다는 주장
- 실시간 도착예측
- AI 버스 추천
- 전체 광주권 완성형 서비스
- 하교 전체를 필수 범위로 확대
- 정확한 집주소 필수 수집
- 코딩 완료를 프로젝트 성공 조건으로 만드는 것

사람이 확인한 것과
앞으로 실제 연구에서 확인할 것을 구분한다.

사용하지 않은 도구,
실행하지 않은 검증,
사람의 승인 이력을 만들지 않는다.

15. 최종 문체
────────────────────

최종 문서는
국립목포대학교 컴퓨터공학 계열 학생이
실제 학교 서비스를 대상으로
6주 HCI/UX 프로젝트를 계획한 문서처럼 작성한다.

지나치게 기업 제안서나
학술 논문처럼 쓰지 않는다.

다음과 같은 표현을 남발하지 않는다.

- 혁신적
- 획기적
- 최적화된
- 사용자 경험을 극대화
- 완벽한
- 최고의

대신:

누가
언제
무엇을
어떻게 확인하고
무엇을 측정할 것인지

구체적으로 작성한다.

Chapter 02와 사실관계가 모순되지 않게 하되,
Chapter 03에서는 Chapter 02를 단순 반복하지 않는다.

“이미 해결안을 정했고 그것을 증명한다”

가 아니라

“초기 해결 가설이 실제 문제를 해결하는지
6주 동안 조사·검증한다”

라는 프로젝트의 성격이 드러나야 한다.

03_프로젝트제안서_통학버스_구서준.md

파일 생성이 불가능하면
생성했다고 주장하지 말고
실패 사실을 명확하게 알려라.

최종 채팅 응답에서는
문서 전체를 다시 붙이지 말고
다음 다섯 가지만 짧게 알려라.

1.
생성 파일명과 실제 다운로드 링크

2.
자체검수 결과와
아직 작성자가 직접 확인해야 할 사항

3.
미측정으로 남아 있는 값
예:
B/I 성공률,
대표 과업 완료시간 baseline

4.
다음 Chapter 04에서 가장 먼저 검증할 가정

핵심 질문:

“실제 광주권 통학생이
자신이 알고 있는 생활권 장소와
도림캠퍼스 등교용 통학버스 승차지점을 연결하는 과정에서
의미 있는 탐색 어려움을 겪는가?”

5.
다음날 간단한 발표에 사용할
30~45초 예상 분량의 발표 요약

발표 요약에는 자연스럽게 다음을 포함한다.

- 기존 Unibus에도 노선·정류장·지도 기능이 이미 있음
- 따라서 기존 서비스를 전반적으로 나쁘다고 보는 프로젝트가 아님
- 노선을 잘 모르는 사용자가
  자신이 알고 있는 생활권 장소에서
  적절한 승차지점·버스·시간을 찾는 진입 과정을 연구함
- 실제 사용자 연구를 통해 문제 존재부터 확인할 예정
- 연구 결과를 바탕으로 제한된 프로토타입을 만들어 비교 평가할 예정
- 아직 실제 사용자 연구 결과가 나온 단계는 아님

실제로 발표 시간을 재지 않았다면
“30~45초 예상 분량”
이라고 표시한다.
