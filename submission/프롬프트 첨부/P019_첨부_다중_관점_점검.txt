# 목포대학교 Unibus HCI 프로젝트 — 5차 MVP AI 다중 페르소나 평가 및 단일 사용자 실험

## 0. 역할 및 최종 목표

당신은 HCI 사용성 평가 책임자이자 소프트웨어 품질 검증 및 UX 개선 총괄 오케스트레이터입니다.

현재까지 4차 MVP의 구현과 검증을 완료했습니다.

이번 작업에서는 실제 인간 참여자를 프로젝트 개발자 본인 1명으로 제한하고, 추가적인 사용성 문제 탐색에는 전문적으로 구성한 AI 페르소나, 휴리스틱 평가, 인지적 워크스루, 자동화 브라우저 테스트를 활용합니다.

핵심 목표는 다음과 같습니다.

1. As-is와 To-be의 비교 공정성 확보
2. 서로 다른 AI 페르소나 관점에서 잠재적 사용성 문제 발견
3. HCI 평가 방법론을 활용한 독립적인 UX 검토
4. 실제 브라우저를 이용한 기능·탐색 검증
5. 발견된 결함의 근거 기반 수정
6. 개발자 본인 1명이 수행할 실제 평가 환경 준비
7. AI 평가와 인간 사용자 평가의 명확한 구분
8. 최종 과제에서 활용할 수 있는 개선 과정 및 증거 확보

기존 기능을 무조건 재설계하거나 새 기능을 추가하는 것보다 실제 사용성 문제의 발견과 해결을 우선하세요.

실제 코드 수정, 브라우저 실행, 테스트, 오류 수정과 문서화를 수행하세요.

실제 인간의 사용 경험, 수행 시간, 성공률, 만족도 결과를 만들어내지 마세요.

## 3. 평가 방법의 엄격한 구분

이번 프로젝트에서는 세 가지 증거 유형을 구분합니다.

### A. 실제 인간 사용자 평가

실제 참여자:
프로젝트 개발자 본인 1명

실제 사용자가 화면을 직접 조작하고 수행한 기록만 이 유형으로 분류하세요.

본인은 개발 경험과 시스템에 대한 사전 지식을 가지고 있으므로 일반 사용자를 대표한다고 간주하지 마세요.

1명의 결과로 일반 사용자 집단의 성공률이나 개선 효과를 확정하지 마세요.

### B. AI 기반 사용성 점검

AI 페르소나, 휴리스틱 평가, 인지적 워크스루를 통해 잠재적인 문제를 탐색합니다.

이는 분석적·시뮬레이션 기반 평가이며 실제 인간 참여자 실험이 아닙니다.

AI가 가상의 감정, 만족도, 클릭 실수, 수행 시간 등을 실제 관측한 것처럼 생성해서는 안 됩니다.

AI의 예상 행동과 실제 브라우저에서 재현된 행동을 구분하세요.

### C. 자동화 기능 검증

Playwright 및 관련 테스트 도구를 사용하여 정상 동작, 오류, 접근성, 데이터 일관성을 검증합니다.

실제로 실행한 자동 테스트의 결과는 객관적 실행 증거로 기록할 수 있습니다.

다만 자동화된 클릭 시간과 경로를 인간의 인지적 탐색시간으로 해석하지 마세요.

세 유형의 기록, 지표, 결론이 혼합되지 않도록 하세요.

## 4. AI 페르소나 설계

기존 HCI 연구와 광주권 통학생의 실제 이용 상황을 바탕으로 다음 네 가지 페르소나를 구성하세요.

페르소나의 목표·정보 수준·제약·성공 기준을 구체적으로 명시하세요.

가상의 개인정보, 실제 인터뷰 발언, 통계 또는 관찰 결과를 만들어내지 마세요.

### Persona A — 통학버스를 처음 이용하는 신입생

특성:
- 기존 노선명과 정류장명을 모름
- 자신이 거주하는 아파트 또는 주변 건물명은 알고 있음
- 학교에 가는 통학버스를 처음 찾음
- 유사한 정류장 이름을 혼동할 수 있음

주요 평가:
- 검색 진입점 발견
- 등교 방향 이해
- 아파트명 검색
- 승차 지점과 시간 확인
- 추천 후보 및 추가 확인 정보 이해

### Persona B — 기존 통학생

특성:
- 자주 이용하는 노선을 알고 있음
- 기존 Unibus 탐색 방식에 익숙함
- 노선 변경이나 새로운 운행편 확인이 필요함
- 기존 정보와 새로운 추천 결과를 비교하려 함

주요 평가:
- 기존 목록 탐색의 효율
- 노선 변경 정보 발견 가능성
- 동일 정류장의 복수 운행편 구분
- As-is와 To-be 사이의 정보 일관성
- 변경된 출발시각 해석

### Persona C — 시간 제약이 있는 하교 이용자

특성:
- 특정 시각 이후에 학교를 출발할 수 있음
- 여러 하교 노선 중 적합한 편을 찾으려 함
- 시간조건과 금요일 대체 운행을 구분해야 함
- 목적지 주변의 복수 하차 지점을 비교함

주요 평가:
- 시간조건 입력
- 시각순·거리순 정렬
- 금요일 대체 운행의 이해
- 후보 간 비교
- 운행 미확정 정보의 해석

### Persona D — 모바일 환경의 저숙련 탐색 사용자

특성:
- 작은 화면으로 서비스를 이용함
- 지도와 목록을 오가며 탐색함
- 복잡한 전문 용어에 익숙하지 않음
- 잘못된 선택을 한 뒤 이전 상태로 돌아가려 함

주요 평가:
- 모바일 레이아웃
- 지도 마커의 이해
- 후보 카드의 가독성
- 화면 이동과 상태 복원
- 오류 메시지 및 복구
- 키보드·기본 접근성

페르소나 특성은 평가를 위한 가정입니다. 실제 참여자의 성향이나 행동을 관찰한 결과처럼 기록하지 마세요.

## 5. 페르소나별 독립 평가

각 페르소나는 사전에 정의된 과업, 제한된 정보, 실제 UI를 기준으로 평가하세요.

가능하면 서로의 결과를 보기 전에 독립적으로 분석하도록 구성하세요.

평가 시작 전에는 정답 경로나 개발자의 설계 의도를 과도하게 제공하지 마세요.

실제 브라우저 접근이 가능하면 Playwright 등으로 해당 과업을 실행하세요.

브라우저를 이용한 경우 다음 정보를 남기세요.

- 실제 접근한 URL
- 실행한 입력 및 클릭
- 화면 변화
- 실제 오류 메시지
- 스크린샷 또는 재현 근거
- 과업 완료 여부
- 발견한 잠재적 사용성 문제

실제로 브라우저를 조작하지 않은 판단은 분석적 추정으로 표시하세요.

각 문제의 심각도를 다음처럼 구분하세요.

- Critical: 핵심 과업 수행 불가능
- High: 심각한 혼동이나 잘못된 선택 위험
- Medium: 반복적인 불편이나 탐색 부담
- Low: 경미한 표현·시각적 개선 문제

심각도와 실제 발생 가능성은 별개로 다루세요.

동일한 모델이 여러 페르소나를 맡는다는 점을 고려하여, 여러 페르소나의 의견 일치를 독립적인 사용자 증거로 해석하지 마세요.

## 6. 인지적 워크스루

기존 USABILITY_PROTOCOL의 A~D 과업을 기반으로 각 주요 행동 단계에 대해 다음 질문을 검토하세요.

1. 사용자가 이 단계에서 무엇을 해야 하는지 이해할 수 있는가?
2. 올바른 조작 요소를 발견할 수 있는가?
3. 해당 요소가 목표를 달성하는 데 도움이 된다는 사실을 이해할 수 있는가?
4. 조작 후 제공되는 피드백을 보고 올바르게 진행하고 있음을 알 수 있는가?

As-is와 To-be를 동일한 평가 기준으로 검토하세요.

각 단계에서 예상되는 문제와 실제 브라우저에서 확인된 문제를 구분하세요.

정류장의 공식 운행 여부가 불명확하다는 이유만으로 UI가 잘못되었다고 판단하지 마세요.

정보의 구조와 표현 방식으로 해결할 수 있는 문제를 우선 찾으세요.

## 7. 휴리스틱 평가

Nielsen의 10가지 사용성 휴리스틱을 기본 평가 틀로 활용하세요.

특히 다음 영역을 집중 검토하세요.

- 시스템 상태의 가시성
- 실제 사용자 언어와 시스템 표현의 일치
- 사용자 통제 및 자유
- 일관성과 표준
- 오류 예방
- 회상보다 인식에 의존하는 설계
- 효율성과 유연성
- 간결하고 이해하기 쉬운 정보 표현
- 오류 발견 및 복구 지원
- 필요한 도움말 제공

각 문제를 해당 평가 원칙, 실제 화면 또는 코드 근거, 예상 영향, 개선 가능성과 연결하세요.

단순한 취향 차이를 객관적인 사용성 결함처럼 취급하지 마세요.

휴리스틱 위반을 발견했다는 사실이 실제 사용자의 불편을 증명하지는 않는다는 점을 유지하세요.

## 8. 반대 관점의 독립 검증

AI 페르소나와 평가 에이전트가 발견한 문제를 총괄 에이전트가 그대로 채택하지 마세요.

가능하면 별도의 비판적 검토를 수행하세요.

다음 질문을 적용하세요.

- 실제 UI에서 재현되는 문제인가?
- 특정 페르소나의 인위적인 가정에 의존하는가?
- 이미 해결된 문제를 반복 지적한 것은 아닌가?
- 사용자의 과업 달성에 실제로 영향을 주는가?
- 수정으로 인해 다른 사용자에게 불편이 발생할 수 있는가?
- 기존 HCI 연구의 목적과 일치하는가?
- 개선 효과를 검증할 수 있는가?

재현 가능한 문제와 근거가 충분한 개선안을 우선 채택하세요.

다수결이나 형식적인 토론으로 결론을 확정하지 마세요.

## 9. 실제 인간 사용자 평가 — 본인 1명

실제 인간 평가 참여자는 프로젝트 작성자 본인 1명으로 설정합니다.

사용자를 대신해 인간 평가 데이터를 생성하지 마세요.

기존 평가 도구를 활용하여 사용자가 직접 과업을 수행할 수 있도록 준비하세요.

### 9.1 평가 조건

- As-is와 To-be 모두 이용
- 동일한 실제 운행 데이터 사용
- 과업 시작 조건 및 성공 기준 통일
- 이전 검색 상태 초기화
- 평가 순서와 사전 경험 기록
- 실제 사용자 조작 시간만 측정
- 성공 여부와 주관적 판단 구분

본인이 이미 해당 시스템을 개발하고 여러 번 이용했다는 편향을 보고서에 명시하세요.

가능하다면 비교 과업의 순서와 사례를 조정하여 학습 효과를 줄이되, 이를 통해 편향이 제거되었다고 주장하지 마세요.

### 9.2 측정 자료

실제 사용자가 수행한 경우에만 다음을 기록하세요.

- 실제 과업 수행 시간
- 과업 성공 또는 실패
- 오류·되돌아가기
- 혼동한 정보
- 주관적인 사용 편의성
- 발견한 문제
- 개선 제안

자기평가의 기술통계는 계산할 수 있지만, 표본 1명의 결과를 일반 사용자 집단의 개선율이나 신뢰성 있는 모집단 추정으로 표현하지 마세요.

성공률 90% 및 탐색시간 30% 감소는 초기 목표로 유지하고, 실측 결과와 구분하세요.

## 10. 평가 도구 신뢰성 점검

기존 평가 도구의 다음 기능을 검증하세요.

1. 평가 동의 및 시작
2. 과업별 시간 측정
3. 종료 후 판정 입력 시간 제외
4. 중단·재시작·취소 처리
5. 모드별 기록 구분
6. 시행 순서와 상태 초기화
7. 성공·실패 판정 저장
8. JSON 내보내기
9. 기록 삭제
10. 새로고침 및 오류 복구

가상 페르소나 실행 기록과 실제 사용자 기록을 별도 유형으로 관리하세요.

기존 데이터 구조에 출처 구분이 충분하다면 불필요하게 변경하지 마세요.

실제 사용자가 참여하지 않았다면 평가 완료 데이터를 생성하지 마세요.

## 11. 실제 UX 개선 및 코드 수정

평가 과정에서 발견한 문제를 다음 순서로 처리하세요.

1. 실제 브라우저에서 재현된 기능 오류
2. 객관적인 접근성 문제
3. 인지적 워크스루에서 근거가 확인된 중요한 문제
4. 휴리스틱 평가에서 검증 가능한 문제
5. 실제 사용자가 제시한 문제
6. 근거가 제한적인 선택적 개선안

실제 사용자 피드백이 아직 없다면 5번은 미실행으로 두고 나머지를 진행하세요.

각 수정에 대해 다음을 기록하세요.

- 문제 ID
- 발견 방법
- 발견한 페르소나 또는 평가 에이전트
- 재현 근거
- 심각도
- 수정 전 동작
- 실제 수정 내용
- 수정 후 테스트
- 잔여 위험

근거가 약한 개선을 무조건 적용하지 마세요.

기존 기능을 불필요하게 다시 구현하거나 UI 디자인 전체를 무조건 변경하지 마세요.

## 12. 하위 에이전트 운영

실제 작업 분리의 이점이 있을 때 하위 에이전트를 사용하세요.

권장 구조:

### Agent A — AI 페르소나 및 인지적 워크스루

- 네 유형의 페르소나 평가
- 과업별 행동 단계 분석
- 잠재적인 혼동 및 탐색 문제 발견
- 재현 가능한 근거 기록

### Agent B — 휴리스틱·접근성 평가

- Nielsen 휴리스틱 평가
- 모바일 UI 및 키보드 접근성
- WCAG 관련 검사
- 오류 예방·상태 복원 검토
- 문제의 심각도와 우선순위 평가

### Agent C — 자동화 및 평가 데이터 검증

필요할 경우에만 별도로 생성하세요.

- 평가 도구의 시간 측정 검사
- Playwright 정상·예외 테스트
- 평가 기록 내보내기·삭제 검증
- As-is/To-be 데이터 공정성 점검
- 기존 회귀 테스트

총괄 에이전트는 평가 결과의 교차검증, 코드 수정, 통합 및 최종 보고를 담당하세요.

하위 에이전트를 무조건 4개 생성할 필요는 없습니다.

페르소나 네 개와 실제 하위 에이전트 네 개는 다른 개념입니다.

작업 독립성이 부족하다면 에이전트 수를 줄이세요.

동일 파일의 동시 수정을 방지하세요.

## 13. 실제 실행 및 자동 검증

기존 4차 MVP의 정상 동작을 유지하세요.

다음을 수행하세요.

- TypeScript 타입 검사
- 프로덕션 빌드
- 기존 단위·UI 테스트
- 기존 Playwright 테스트
- Kakao 실제 장소 검색
- As-is/To-be 과업 실행
- 추천 후보 및 지도 확인
- 모바일 반응형 검사
- 키보드 접근성 검사
- axe 등 자동 접근성 검사
- 평가 도구 시간 측정 검사
- JSON 내보내기·삭제 검증
- 변경된 기능의 회귀 검사

W3C의 접근성 평가 기준을 참고하여 자동 검사와 수동 판단이 필요한 항목을 구분하세요.

자동 검사에서 위반이 발견되지 않았다고 모든 접근성 문제가 해결되었다고 주장하지 마세요.

실제 오류가 발견되면 수정한 뒤 관련 테스트를 재실행하세요.

브라우저 자동화 결과와 실제 인간 사용자 관찰 결과를 별도로 기록하세요.

## 14. 최종 보고서와 과제 평가 대응

다음 세 유형의 결과를 명확하게 분리하여 보고하세요.

### Part A — 자동화 기능 검증

실제로 실행한 테스트, 통과 결과, 발견한 결함과 수정사항

### Part B — AI 기반 분석적 사용성 평가

페르소나별 분석, 인지적 워크스루, 휴리스틱 평가, 재현 여부, 잠재적 한계

### Part C — 실제 자기평가

실제 사용자인 본인 1명이 직접 수행한 기록만 수록

평가를 아직 실시하지 않았다면 Part C는 평가 절차와 빈 결과 양식만 준비하세요.

최초 기획과 변경된 추천형 탐색 구조의 관계도 보존하세요.

다음 흐름을 명확히 정리하세요.

초기 기획 → 기존 서비스 분석 → 데이터 한계 발견 → 추천형 후보 비교 도입 → 구현 → AI 기반 사용성 점검 → 실제 자기평가 → 개선

실제로 수행되지 않은 과정은 완료된 것으로 기록하지 마세요.

이번 결과가 AI를 활용한 체계적인 설계·검증이라는 점은 설명하되, 실제 다수 사용자 실험을 대체한 것처럼 표현하지 마세요.
