# 목포대학교 Unibus 기반 HCI 프로젝트 — 멀티 에이전트 시스템 설계 및 최종 명세 확정

## 0. 역할과 작업 목표

당신은 본 HCI 프로젝트의 총괄 시스템 아키텍트이자 멀티 에이전트 오케스트레이터입니다.

이번 작업의 목표는 현재까지 축적된 HCI 연구자료와 프로젝트 컨텍스트를 바탕으로, 실제 웹서비스 구현에 필요한 **서비스 구조, 장소 검색 시스템, 통학버스 추천 알고리즘, 데이터 처리 규칙, 사용자 인터페이스, 기술 아키텍처를 종합적으로 검토하고 최종 설계 명세를 작성하는 것**입니다.

실제 구현을 시작하기 전에 기술적으로 실현 가능하고, 사용자에게 허위 정보를 제공하지 않으며, 기존 HCI 연구 목적에 부합하는 시스템을 설계해야 합니다.

이번 단계에서는 웹사이트 구현, 패키지 설치, 프로젝트 초기화, 배포를 수행하지 마세요.

## 1. 기존 컨텍스트 활용

프로젝트 루트의 AGENTS.md를 먼저 확인하고 다음 문서를 순서대로 검토하세요.

- docs/context/PROJECT_OVERVIEW.md
- docs/context/RESEARCH_FINDINGS.md
- docs/context/REQUIREMENTS.md
- docs/context/DATA_RULES.md
- docs/context/SOURCE_INDEX.md
- docs/context/IMPLEMENTATION_ROADMAP.md
- docs/PROMPT_LOG.md

이미 정리된 문서가 있으므로 원본 42개를 처음부터 전부 다시 분석하지 마세요.

현재 설계에 필요한 정보가 누락되었거나 서로 충돌하는 경우에만 SOURCE_INDEX.md를 통해 해당 원본의 특정 부분을 재확인하세요.

문서에 기록되지 않은 내용을 기존 연구에서 확인된 사실처럼 작성하지 마세요.

기존에 정리된 다음 사항을 유지하세요.

- 등교와 하교를 모두 지원
- 기존 Unibus의 목록 기반 탐색 방식 유지
- 생활권 장소 기반 탐색 기능 추가
- 등교의 지점별 승차 시각과 하교의 학교 출발 시각 구분
- 연구자료는 작성자 1인의 회고와 자료 분석을 중심으로 구성됨
- 목표 성공률 90%, 탐색시간 30% 감소는 검증되지 않은 목표값
- 출처 색인에 기록된 11개 충돌·미확정 항목은 해결된 것으로 간주하지 않음

## 2. 프로젝트의 핵심 방향

프로젝트명:
광주권 등하교 통학버스 이용정보 탐색 UI 개선

서비스 범위:
목포대학교 도림캠퍼스 ↔ 광주권

1차 구현에서는 광주광역시를 중심으로 지원하되, 기존 연구 및 공식 노선표에 포함된 광주 인접 지역의 처리 여부를 확인하여 정확한 지원 범위를 정의하세요.

목포권 전체로 신규 검색 서비스를 확장하지는 않습니다. 다만 향후 지역을 추가할 수 있는 데이터 구조를 설계하세요.

### 2.1 기존 서비스 재현

기존 목포대학교 Unibus의 화면 구조와 대표적인 탐색 흐름을 참고하여 As-is 기준 버전을 구현할 계획입니다.

REA(Reverse Engineer Anything)가 연결되어 있는지 확인하고, 활용 가능한 분석 기능과 한계를 조사하세요.

기존 화면 캡처 PDF 및 적법하게 접근 가능한 공개 화면을 바탕으로 UI 구조를 분석하세요.

비공개 API, 인증정보, 보호된 소스 코드 및 자산을 무단으로 추출하거나 복제하지 마세요.

공식 서비스와 혼동되지 않는 교육용 프로토타입으로 설계하세요.

### 2.2 개선 서비스

기존 기능을 유지하면서 사용자가 자신의 출발지 또는 목적지를 직접 검색하여 적절한 통학버스 노선과 승하차 위치를 찾도록 개선합니다.

가능하다면 동일한 프로젝트에서 As-is와 To-be를 전환하여 비교할 수 있도록 설계하세요.

기존 서비스 전체를 무조건 복제하는 것보다 HCI 핵심 과업의 충실한 구현과 비교 가능성을 우선하세요.

## 3. 핵심 사용자 경험 설계

### 3.1 출발지·목적지 입력

검색 대상을 버스정류장이나 지하철역으로 제한하지 않습니다.

사용자는 다음과 같은 일상적인 장소 정보를 검색할 수 있어야 합니다.

- 아파트명
- 건물명 및 상호명
- 학교, 병원, 공공기관 등 시설명
- 도로명주소
- 지번주소
- 주요 생활권 장소명

카카오맵 등 장소·주소 검색 API의 활용 가능성을 검토하세요.

동명이소 장소가 존재하면 주소 및 지역 정보를 표시하여 사용자가 정확한 장소를 선택하도록 설계하세요.

검색 결과가 없으면 주소 재검색 또는 지도에서 위치 선택 등의 대체 방법을 제공하는 방안을 검토하세요.

아파트의 세부 동·호수와 같은 불필요한 개인정보는 요구하지 마세요.

### 3.2 등교·하교 구분

등교:
- 출발지: 사용자가 검색하는 광주권 장소
- 목적지: 목포대학교 도림캠퍼스 자동 설정

하교:
- 출발지: 목포대학교 도림캠퍼스 자동 설정
- 목적지: 사용자가 검색하는 광주권 장소

등교·하교 전환 버튼을 제공하고, 필요하다면 출발지와 목적지를 맞바꾸는 기능도 검토하세요.

출발지와 목적지를 모두 표시하되, 학교에 해당하는 입력값은 자동으로 설정하여 입력 부담을 줄이세요.

기존 목록 기반 노선 검색 기능도 별도로 유지하세요.

### 3.3 시간 조건

등교 시:
- 원하는 학교 도착 시각
- 해당 조건을 충족하는 노선 탐색

하교 시:
- 학교에서 출발할 수 있는 시각
- 해당 시각 이후의 운행편 탐색

시간 조건을 필수 또는 선택 항목 중 무엇으로 설정할지 HCI 관점에서 검토하세요.

공식 노선표에 실제 도착 시각이 없는 경우에는 시간을 임의로 계산하여 확정적인 정보처럼 제시하지 마세요.

## 4. 멀티 에이전트 독립 분석

실제 Subagent 기능을 사용할 수 있다면 다음 4개의 전문 에이전트를 병렬로 실행하세요.

에이전트의 작업 범위와 근거 자료를 구분하고, 초기에는 읽기 전용으로 운영하세요.

### Agent A — 검색 및 추천 알고리즘 전문가

다음을 설계하세요.

1. 사용자의 장소 검색부터 노선 추천까지의 전체 처리 과정
2. 장소 좌표와 통학버스 정류장 좌표의 연결 방법
3. 등교와 하교에 따른 승하차 정류장 판별
4. 복수 정류장 및 복수 노선의 추천 순위 결정
5. 시간 조건과 도보 거리의 우선순위
6. 가장 가까운 정류장이 최선이 아닌 경우의 처리
7. 추천 결과가 없는 경우의 대안 안내
8. 정적 노선표만 있을 때 구현 가능한 추천 범위

다음 대안을 비교하세요.

- 최단거리 기반 추천
- 거리와 시간의 가중치 기반 추천
- 운행 가능 조건을 먼저 검증한 뒤 거리·시간으로 정렬하는 단계적 추천

단순한 직선거리와 실제 도보 이동거리를 구분하세요.

알고리즘이 사용한 기준을 사용자에게 설명할 수 있어야 합니다.

### Agent B — 데이터 및 외부 API 전문가

다음을 검증하세요.

1. 공식 통학버스 노선표에서 확보 가능한 데이터
2. 정류장별 좌표 확보 가능성
3. 등교·하교 노선 정보의 차이
4. 카카오맵 및 대체 지도 API의 실제 제공 기능
5. 장소명 검색, 주소 검색, 좌표 변환, 지도 표시 지원 여부
6. 도보 경로 및 소요시간 계산 가능 여부
7. API 이용약관, 인증 방식, 비용과 호출 제한
8. 정적 데이터의 유효기간 및 갱신 방법
9. 데이터 충돌과 불확실성을 처리하는 방법

API가 제공하지 않는 기능을 제공한다고 가정하지 마세요.

공식 문서와 실제 접근 가능 여부를 확인하여 사용 가능한 기능과 제약을 구분하세요.

검증하지 못한 API 기능은 미확인으로 표시하고 대안을 제시하세요.

기존에 발견된 11개 충돌·미확정 항목을 검토하여 각각을 다음 중 하나로 분류하세요.

- 해결됨: 근거를 확인한 경우만
- 구현 전 필수 확인
- 제한된 구현이 가능한 미확정 사항
- 1차 구현 범위 밖

### Agent C — HCI·UX 전문가

기존 연구와 사용자 과업을 기준으로 다음을 설계하세요.

1. 신입생의 첫 등교 탐색
2. 기존 통학생의 노선 변경 확인
3. 집 주변 등교 승차 정류장 탐색
4. 하교 후 특정 목적지 주변 하차 정류장 탐색
5. 유사한 정류장 이름과 도로 양편 위치의 구분
6. 검색 실패 및 이용 가능 노선 없음 안내
7. 노선 추천 결과의 설명 가능성
8. 모바일 환경에서의 사용 편의성
9. 기존 Unibus 탐색 흐름과 개선안의 비교

기존 HTA와 어피니티 분석 결과가 실제 설계에 반영되었는지 검증하세요.

새로운 아이디어는 기존 연구 결과와 구분하여 설계 가설로 기록하세요.

화려한 UI보다 정보 탐색 효율, 정확성, 일관성을 우선하세요.

### Agent D — 시스템 아키텍처 및 비판적 검증 전문가

다음을 검토하세요.

1. 프로젝트에 적합한 프런트엔드 구조
2. 백엔드 및 데이터베이스의 실제 필요성
3. 정적 JSON 기반 구현 가능성
4. 외부 API 연동 구조
5. 인증키 및 개인정보 보호
6. 데이터 모델과 검색 성능
7. 오류 및 네트워크 장애 처리
8. 테스트 및 배포 용이성
9. 유지보수와 노선 확장 가능성
10. 구현 복잡도 대비 실제 HCI 개선 효과

과도한 기술 스택이나 불필요한 서버 개발을 지양하세요.

각 설계안에서 발생할 수 있는 문제와 반례를 적극적으로 검토하세요.

## 5. 교차검증 및 설계안 평가

4개 에이전트의 분석 결과를 총괄 오케스트레이터가 취합하세요.

에이전트 간 의견이 충돌하는 경우 해당 문제를 다시 검토하게 하세요.

필요하면 상대 에이전트의 분석 결과에 대한 비판과 반론을 요청하세요.

하지만 단순한 다수결이나 형식적인 합의로 결론을 결정하지 마세요.

다음 기준으로 평가하세요.

- 기존 HCI 연구와의 일치성
- 실제 구현 가능성
- 추천 정보의 정확성
- 사용자 편의성
- 개발 및 유지보수 복잡도
- 외부 API 의존도
- 검증 및 테스트 가능성
- 과제 평가 기준과의 부합성

필요 이상으로 에이전트를 추가하지 마세요.

실제 서브에이전트를 실행하지 못했다면 이를 명확하게 밝히고, 수행한 분석의 범위를 구분하세요.

## 6. 추천 시스템의 필수 설계 원칙

### 6.1 데이터 정확성

확인되지 않은 운행정보를 만들어내지 마세요.

정보는 다음 상태로 구분하세요.

- 공식 확인 정보
- 계산 또는 추정 정보
- 미확인 정보
- 충돌하는 정보

운행시간, 정류장 위치, 출발지와 목적지, 경유 여부에 대한 근거를 추적할 수 있도록 설계하세요.

데이터 충돌이 있는 경우 임의의 값을 정답으로 선택하지 마세요.

### 6.2 추천 기준

실제 운행 가능 여부를 확인하지 않은 노선을 단순히 거리가 가깝다는 이유로 추천하지 마세요.

검색 장소와 가까운 정류장을 먼저 찾되, 실제 운행 방향, 경유 여부, 운행시간 등을 검증해야 합니다.

거리, 시간, 편의성을 종합하되 확인되지 않은 요소를 임의의 점수로 계산하지 마세요.

추천 점수 또는 순위 산정에 사용되는 가중치와 임계값은 근거 및 설정 방법을 설명하세요.

### 6.3 결과 안내

추천 결과에는 확보 가능한 범위에서 다음 정보를 표시하도록 설계하세요.

- 추천 노선명
- 승차 또는 하차 정류장
- 해당 정류장의 지도상 위치
- 검색 장소와의 거리
- 이용 가능한 출발 시각
- 추천 이유
- 공식 운행정보 확인 경로
- 정보의 기준일 및 신뢰 수준

실제 도보 경로를 계산할 수 없는 경우 직선거리임을 명시하세요.

실시간 데이터가 없으면 실시간 운행정보를 표시하지 마세요.

실제 예약 및 GPS 기능이 없다면 이를 정상 작동하는 공식 기능처럼 구현하지 마세요.

## 7. 대표 사용자 시나리오 및 검증 조건

최소 다음 사례를 포함해 검증 가능한 테스트 시나리오를 설계하세요.

1. 광주권 아파트명을 검색하여 등교 노선 찾기
2. 광주권 건물명을 검색하여 하교 노선 찾기
3. 동일한 이름의 장소가 여러 개 존재하는 경우
4. 주변에 복수의 통학버스 정류장이 존재하는 경우
5. 가장 가까운 정류장이 원하는 시간과 맞지 않는 경우
6. 승차 정류장과 하차 정류장이 도로 양편에 있는 경우
7. 검색한 위치 주변에 적합한 노선이 없는 경우
8. 공식 노선표의 시간 또는 경유 정보가 충돌하는 경우
9. 지도 API가 응답하지 않는 경우
10. 주소는 검색되지만 정확한 정류장 좌표가 확보되지 않은 경우

각 시나리오에서 다음 내용을 정의하세요.

- 사용자 입력
- 필요한 데이터
- 기대되는 시스템 동작
- 예상되는 오류 및 예외
- 사용자에게 보여줄 안내 문구
- 실제 구현 후 검증할 수 있는 테스트 조건

가상의 사례와 실제 검증된 사례를 구분하세요.

## 8. 전체 시스템 및 구현 범위 확정

다음 사항을 종합적으로 검토하고 권장안을 결정하세요.

1. 사이트 전체 정보 구조 및 주요 화면
2. As-is와 To-be의 관계 및 전환 방식
3. 검색 입력 및 결과 화면 구성
4. 노선 추천 알고리즘과 처리 순서
5. 노선·운행편·정류장·장소 데이터 모델
6. 지도 API 및 외부 서비스 연동 구조
7. 필수 구현 기능과 선택적 기능
8. 구현하지 않을 기능 및 그 이유
9. 개발에 필요한 기술 스택
10. 실제 구현 작업의 의존관계와 순서
11. 단위·통합·브라우저 테스트 계획
12. GitHub 공유 및 배포 구조

가능한 경우 핵심 구조를 Mermaid 다이어그램, 데이터 관계도, 의사코드, 상태 흐름도로 표현하세요.

아직 구현하거나 검증하지 않은 기능을 완료된 것으로 표시하지 마세요.

## 9. 연구 및 과제 평가 기준 반영

다음 평가 기준을 설계 검토에 반영하세요.

- 기획 내용과 구현 결과의 일치성
- 주요 기능의 구현 및 정상 작동 여부
- UI·UX 완성도
- 프롬프트를 통한 개선 과정의 적절성
- 실행 가능한 결과물의 공유 가능성

HCI 연구의 사용성 평가 목표는 실제 사용자 측정 결과와 구분하세요.

AI 에이전트의 평가와 실제 사용자 실험을 동일하게 취급하지 마세요.

과제 안내에는 Claude Code 활용 조건이 있으므로, 실제 사용 기록을 구분하고 제출 요건 충족 여부를 확인할 수 있도록 하세요.
