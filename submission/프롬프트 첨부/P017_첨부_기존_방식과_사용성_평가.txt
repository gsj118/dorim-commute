# 목포대학교 Unibus HCI 프로젝트 — 4차 MVP As-is/To-be 비교 및 사용성 평가 체계 구축

## 0. 역할 및 목표

당신은 HCI 프로젝트의 총괄 소프트웨어 엔지니어이자 UX 평가 및 품질 검증 책임자입니다.

현재까지 3차 MVP를 완료했습니다. 이번 작업은 신규 기능을 무조건 확장하는 단계가 아니라, 기존에 구현한 탐색 서비스를 HCI 과제의 관점에서 평가하고 완성도를 높이는 단계입니다.

**핵심 목표는 기존 Unibus의 목록 기반 탐색(As-is)과 개선된 장소 기반 후보 추천·비교(To-be)를 동일한 조건에서 비교할 수 있도록 구현하고, 실제 사용성 평가가 가능한 환경을 구축하는 것입니다.**

단순한 설계나 문서 작성으로 종료하지 마세요. 코드 구현, 실제 브라우저 확인, 오류 수정, 검증까지 진행하세요.

## 3. 프로젝트 핵심 목적 유지

프로젝트명:
광주권 등하교 통학버스 이용정보 탐색 UI 개선

최종 개선 방향:
생활권 장소 기반 통학버스 노선 후보 추천 및 비교

핵심 사용자 문제는 통학버스 정보의 탐색 부담과 승하차 위치·운행정보의 이해 어려움입니다.

기존 연구 결과와 구현 결과의 연결을 유지하세요.

초기 자동 추천 구상에서 근거 기반 후보 비교로 변경한 이유는 기존 설계 결정 기록에 따라 보존하세요.

실제 데이터의 한계를 숨기거나 공식 운행 여부를 임의로 확정하지 마세요.

## 4. As-is / To-be 비교 기능 구현

### 4.1 As-is 기준 화면

기존 Unibus 화면 캡처와 REA 분석 기록을 참고하세요.

다음 대표 탐색 흐름을 구현하세요.

홈 → 등교·하교 선택 → 노선 목록 → 운행편 상세 → 정류장 및 위치 확인

기존 Unibus의 정보 구조, 화면 구성, 목록 탐색 방식과 주요 상호작용을 가능한 범위에서 재현하세요.

단, 공식 사이트의 보호된 소스 코드나 자산을 무단 복제하지 마세요.

As-is는 실제 원본 Unibus 서비스 그 자체가 아니라 **기존 UI를 근거로 자체 재구현한 비교용 기준 화면**임을 명시하세요.

실제 원본과 재현 화면 사이의 차이도 기록하세요.

### 4.2 To-be 개선 화면

현재 구현한 장소 기반 탐색 서비스를 활용하세요.

다음 흐름을 유지하세요.

등교·하교 선택 → 출발지·목적지 검색 → 노선·정류장 후보 비교 → 지도·운행정보 확인

기존 개선 기능을 제거하거나 단순화하지 마세요.

### 4.3 비교의 공정성

두 방식은 가능한 한 동일한 공식 노선·운행편·정류장 데이터를 사용하세요.

As-is에서만 데이터가 부족하거나 To-be에서만 정보가 추가되는 방식으로 비교하지 마세요.

다만 실제 원본 Unibus에서 일부 하교 목록이 누락된 현상은 별도 관찰 사실로 기록하세요.

기준 화면의 데이터 보완 사실을 감추지 마세요.

두 버전에서 동일하게 해결할 수 있는 대표 과업을 선정하세요.

탐색 방식의 차이와 데이터 제공 범위의 차이를 명확히 구분하세요.

### 4.4 모드 전환 UX

사용자가 As-is와 To-be를 쉽게 전환할 수 있도록 구성하세요.

모드 전환이 혼동을 일으키지 않도록 설명을 제공하세요.

비교 화면은 프로젝트의 핵심 기능을 방해하지 않도록 설계하세요.

필요하다면 일반 사용자에게는 To-be를 기본으로 제공하고 비교 모드는 별도로 진입하도록 구성하세요.

## 5. HCI 사용성 평가 환경 구축

기존 사용자 연구, HTA 및 프로젝트 제안서의 목표를 확인하세요.

이번 단계에서는 **실제 사용자 평가를 실시했다고 주장하지 말고, 실행 가능한 평가 환경과 과업을 준비**하세요.

### 5.1 대표 과업

최소 다음 과업을 검토하세요.

A. 광주권 아파트 또는 생활권 장소에서 목포대학교까지 등교할 수 있는 통학버스 정보 찾기

B. 목포대학교에서 광주권의 특정 목적지로 하교할 때 관련 노선 및 하차 지점 찾기

C. 특정 출발시각 조건에 맞는 하교 운행편 비교

D. 유사한 정류장 또는 도로 양편 위치를 구분하여 확인하기

각 과업은 현재 확보된 실제 노선 데이터로 수행 가능한지 검증하세요.

As-is와 To-be 양쪽에서 비교 가능한 과업과 한쪽에만 적용되는 과업을 구분하세요.

실제 과업에 사용할 장소명, 정류장명, 운행편을 근거와 함께 확정하세요.

### 5.2 평가 지표

다음 지표를 검토하고 측정 방법을 정의하세요.

- 과업 성공 여부
- 과업 완료 시간
- 화면 이동 또는 상호작용 횟수
- 잘못된 선택 및 되돌아가기
- 정보 확인 실패
- 사용자에게 남은 불확실성
- 주관적 사용 편의성

성공 기준과 실패 기준을 과업별로 구체화하세요.

기존 목표인 성공률 90%, 탐색시간 30% 감소는 검증되지 않은 목표값으로 유지하세요.

실제 사용자 실험 없이 개선율을 만들어내지 마세요.

### 5.3 평가 도구

필요성이 인정되면 사용성 평가를 지원할 수 있는 간단한 기능을 구현하세요.

예:
- 과업 시작 및 종료
- 사용자가 성공 여부 기록
- 경과 시간 측정
- 평가용 과업 안내
- 결과 확인 및 내보내기

다만 평가 도구 구현이 실제 사용자 탐색 UX를 해치지 않도록 일반 서비스 화면과 분리하세요.

개인정보와 검색어를 불필요하게 서버에 저장하지 마세요.

평가 기록은 참여자의 인지와 동의하에 수집하도록 설계하세요.

실제 사용자 데이터와 자동 테스트 데이터를 구분하세요.

추가적인 백엔드나 데이터베이스는 필수적이지 않다면 도입하지 마세요.

## 6. UI·디자인 완성도 개선

기존 Unibus의 기준 화면과 개선된 To-be 화면을 실제 브라우저에서 확인하세요.

다음 기준으로 개선하세요.

1. 주요 기능의 시각적 위계
2. 등교·하교 방향 구분
3. 장소 검색의 이해 가능성
4. 후보 카드의 정보 우선순위
5. 지도와 결과 목록의 상호작용
6. 거리·시각·불확실성 정보의 가독성
7. 모바일 환경의 탐색 편의성
8. 키보드 접근성 및 기본 WCAG 검사
9. 검색 실패·결과 없음·오류 복구
10. 불필요한 클릭과 화면 이동 최소화

시각적 완성도를 개선하되 기존 핵심 기능과 근거 정보를 제거하지 마세요.

디자인 변경은 가능한 한 실제 사용자 과업과 연결된 문제를 해결하는 방향으로 수행하세요.

변경 전후 화면은 동일한 뷰포트 조건에서 캡처하여 비교 가능한 증거를 남기세요.

## 7. 기술적 안정화

3차 MVP에서 정적 데이터 증가에 따른 빌드 청크 크기 경고가 보고되었습니다.

먼저 실제 빌드 결과를 확인하고 원인을 분석하세요.

경고가 발생했다는 이유만으로 무조건 코드 분할을 적용하지 마세요.

다음 대안을 필요에 따라 검토하세요.

- 라우트 단위 코드 분할
- 사용 시점의 동적 import
- 정적 JSON 로딩 구조 개선
- 불필요한 라이브러리 제거
- 지도 관련 모듈 지연 로딩

현재 번들 구성과 실제 로딩 동작을 기준으로 실익이 있는 방안만 적용하세요.

청크 크기 경고를 숨기기 위해 임계값만 높이는 방식은 사용하지 마세요.

변경 전후 번들 크기와 주요 기능 정상 동작을 비교하세요.

과도한 최적화보다 안정성·유지보수성·사용성을 우선하세요.

## 8. 하위 에이전트 운영

실제 병렬화의 이점이 있다면 전문 하위 에이전트 2개를 우선 활용하세요.

### Agent A — As-is 재현 및 비교 기준

- 기존 Unibus 화면 근거 검토
- As-is UI 구현
- 동일 데이터 기반 비교 구조
- 원본 화면과 재현 화면의 차이 기록
- 비교 가능한 대표 과업 검증

### Agent B — HCI 평가 및 UX 검증

- 대표 사용자 과업 설계
- 평가 지표와 측정 기준
- 사용성 평가 환경 구성
- To-be UX 문제점 검토
- 모바일·접근성 테스트

총괄 에이전트는 공통 데이터 계약, 파일 소유 범위, 코드 통합, 성능 개선 및 최종 테스트를 담당하세요.

같은 파일을 동시에 수정하지 마세요.

병렬화할 수 없는 작업은 순차 수행하세요.

독립 QA가 실질적으로 필요하다면 제한된 범위에서 추가할 수 있지만 에이전트 수를 늘리는 것 자체를 목표로 하지 마세요.

## 9. 테스트 및 실제 검증

기존 테스트를 유지하고 신규 기능에 맞게 확장하세요.

필수 검사:

- TypeScript 타입 검사
- 프로덕션 빌드
- 단위·UI 테스트
- Playwright 브라우저 테스트
- 실제 Kakao 검색·지도 연결
- As-is 목록·상세 탐색
- To-be 장소 검색·후보 비교
- 두 모드의 데이터 일치성
- 모드 전환 및 뒤로가기
- 대표 과업의 정상·예외 동작
- 모바일 반응형

기존 테스트가 통과한 사실을 유지하면서 새로운 오류를 발견하면 수정하고 재검증하세요.

## 10. 개선 과정 및 과제 평가 기준 대응

최초 기획과 구현 결과 사이의 변경사항을 기록하세요.

다음 평가 기준을 고려합니다.

- 기획 내용과 구현 결과의 일치성
- 주요 기능 정상 작동
- UI 및 디자인 완성도
- 프롬프트의 구체성 및 개선 과정
- 소스 코드와 결과물의 공유·제출 충실성

기획 변경은 다음 흐름으로 설명하세요.

초기 기획 → 실제 자료·시스템 분석 → 데이터 한계 발견 → 대안 비교 → 추천형 탐색 개선 → 구현 및 검증

변경 근거를 기술적 제약뿐 아니라 사용자 관점에서도 설명하세요.

기존 연구의 문제 정의와 개선 목표가 유지되는지 확인하세요.

초기 연구 산출물을 소급하여 변경하거나 없었던 실험 결과를 생성하지 마세요.

과제 안내에는 Claude Code가 명시되어 있습니다.

이 차이를 숨기지 말고 평가·제출상 유의사항으로 유지하세요.

## 12. 완료 기준

이번 작업의 목표는 다음과 같습니다.

1. 기존 3차 MVP 기능 유지
2. As-is 기준 탐색 화면 실제 구현
3. 기존 To-be 검색 기능과 모드 전환
4. 동일 데이터에 기반한 비교 구조
5. 비교 가능한 실제 대표 사용자 과업 확정
6. 사용성 평가 절차 및 측정 기준 완성
7. 필요시 평가 보조 기능 구현
8. 데스크톱·모바일 UI 개선
9. 빌드 경고 원인 분석 및 타당한 개선
10. 기존·신규 자동 테스트 통과
11. 실제 브라우저에서 두 방식의 과업 검증
12. 기획 변경 및 개선 과정 기록

실제 외부 사용자 평가는 이번 단계에서 아직 수행하지 않아도 됩니다.

다만 이후 사용자가 평가를 수행할 수 있도록 구체적인 절차와 실행 가능한 환경을 준비하세요.

기능 구현과 실제 사용자 평가 결과를 명확하게 구분하세요.
