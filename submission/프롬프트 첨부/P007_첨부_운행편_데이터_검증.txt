# 목포대학교 Unibus HCI 프로젝트 — 대표 운행편 데이터 검증 및 구현 준비

## 0. 역할과 최종 목표

당신은 목포대학교 Unibus 기반 HCI 프로젝트의 데이터 검증 책임자이자 시스템 통합 설계자입니다.

이전 작업에서 프로젝트 자료 분석, 시스템 설계, 멀티 에이전트 교차검증, REA 기반 실제 Unibus 화면 확인까지 완료했습니다.

이번 작업에서는 기존 분석을 처음부터 반복하지 않고, 이미 작성된 설계 명세를 바탕으로 실제 웹사이트 구현에 사용할 수 있는 대표 운행편 데이터와 검증 기준을 확보하세요.

이번 단계의 핵심 목표는 등교 1편·하교 1편을 검증하고, 미확정 정보가 남아 있어도 허위 안내 없이 개발을 진행할 수 있는 최소 데이터 명세를 확정하는 것입니다.

소스 코드 구현, 패키지 설치, 프로젝트 초기화, 배포는 이번 작업에서 진행하지 마세요.

이전 채팅 내용을 직접 기억하거나 접근할 수 있다고 가정하지 마세요.

## 2. 이전 작업의 완료 사항과 미해결 상태

이전 작업에서 다음 사항을 보고했습니다.

- 시스템 설계 명세 7개 작성 완료
- 알고리즘·데이터/API·UX·아키텍처 분석 완료
- 운행 조건과 위치를 검증한 후 직선거리순으로 추천하는 방식 채택
- React, TypeScript, Vite, 정적 JSON 기반 아키텍처 채택
- 실제 Unibus 사이트에 REA로 접근하여 대표 화면 확인
- 등교·하교 목록 및 노선 상세 확인
- 정류장별 위치 설명과 지도 팝업 확인
- CF01~CF11에 이어 CF12를 추가 기록
- 웹사이트 구현 및 배포는 미진행

위 사항은 이전 작업의 보고 내용입니다. 현재 파일과 기록을 확인하여 실제 상태를 검증하세요.

특히 CF12는 REA 관찰 환경에서 하교 목록이 두 항목만 표시된 현상과 공식 노선표의 차이입니다.

이것이 실제 데이터 충돌인지, 화면 필터·접근 경로·운행기간·표시 조건의 차이인지는 아직 확정되지 않았습니다.

기존 미해결 항목을 임의로 해결된 것으로 처리하지 마세요.

## 3. 실제 Unibus 및 REA 검증 자료 활용

분석 대상:
https://mokpo.unibus.kr/#!/index

이전 작업에서 사용한 REA 연결 상태와 저장된 화면 캡처, 분석 기록을 확인하세요.

먼저 기존에 확보한 증거를 활용하세요. 동일한 화면을 불필요하게 반복 조사하지 마세요.

추가 확인이 실제 데이터 검증에 필요할 때만 REA를 사용하세요.

현재 브라우저의 로그인 세션을 사용할 수 있다고 가정하지 마세요.

접근 가능한 공개 화면과 정상적으로 허가된 범위에서만 조사하고, 인증 우회·보호된 API 접근·비공개 데이터 추출을 시도하지 마세요.

실제 사이트의 표시 정보와 공식 노선표가 다르면 각각의 출처, 기준일, 적용 기간, 표시 조건을 기록하세요.

화면에 표시된 정보가 현재 운행 중인 실제 조건과 동일하다고 단정하지 마세요.

## 4. 대표 데이터 검증

### 4.1 등교 대표 운행편 1개

기존 HCI 연구와 공식 자료를 고려하여 광주권에서 목포대학교 도림캠퍼스로 향하는 대표 운행편 1개를 선정하세요.

가능하면 기존 사용자 연구에서 다룬 생활권 장소와 관련된 노선을 우선 검토하세요.

다음 정보를 확인하세요.

1. 공식 노선명 또는 운행편 식별 정보
2. 출발지 및 주요 경유 정류장
3. 정류장별 승차 가능 여부
4. 정류장별 실제 승차 시각
5. 운행 요일 및 적용 기간
6. 정류장의 실제 승차 위치
7. 확보 가능한 위치 좌표
8. 학교 도착 시각의 공식 제공 여부
9. 근거 문서 및 출처
10. 충돌하거나 확인되지 않은 데이터

정류장별 시각은 공식 자료에서 확인되는 경우에만 확정하세요.

실제 학교 도착 시각이 제공되지 않으면 임의로 만들어내지 마세요.

### 4.2 하교 대표 운행편 1개

목포대학교 도림캠퍼스에서 광주권으로 향하는 대표 운행편 1개를 선정하세요.

가능하면 기존 HCI 연구에서 다룬 하교 시나리오와 연결하세요.

다음 정보를 확인하세요.

1. 노선명 또는 운행편 식별 정보
2. 학교 출발 시각
3. 학교 내 실제 승차 장소
4. 경유 정류장 순서
5. 광주권 주요 하차 정류장
6. 각 정류장의 실제 하차 위치
7. 운행 요일 및 적용 기간
8. 확보 가능한 위치 좌표
9. 중간 정류장 도착 시각의 제공 여부
10. 근거 문서 및 출처

학교 승차 위치와 광주권 하차 위치를 혼동하지 마세요.

등교 정류장과 하교 정류장의 명칭이 같더라도 실제 위치가 동일하다고 가정하지 마세요.

## 5. 위치 및 지도 데이터 검증

각 대표 운행편에 대해 확인 가능한 정류장 좌표를 확보하세요.

필요한 경우 정상적인 지도 검색 및 지도 서비스의 공개 정보를 활용하세요.

다음 사항을 구분하세요.

- 공식적으로 확인된 정류장 위치
- 여러 근거가 일치하는 위치
- 지도 검색으로 발견한 후보 위치
- 도로변 방향이나 실제 승하차 지점이 불확실한 위치
- 좌표를 확보하지 못한 위치

지도에서 검색된 장소의 중심 좌표가 실제 버스 승하차 위치라고 단정하지 마세요.

특히 도로 양편에 승하차 위치가 구분되는 경우에는 방향별 위치를 별도로 검증하세요.

현장 확인이 필요한 위치는 그 사유와 확인 방법을 기록하고, 실제 방문하거나 확인하지 않은 결과를 만들어내지 마세요.

위치가 미확정인 정류장은 지도상 정확한 승차 지점으로 안내하지 않도록 설계하세요.

## 6. 하위 에이전트 운영

이번 작업은 자료 검증 중심이므로 불필요하게 많은 에이전트를 생성하지 마세요.

실제로 독립적인 검증 작업을 병렬 수행할 수 있다면 하위 에이전트 2개를 우선 활용하세요.

### Agent A — 운행정보 검증

담당:
- 공식 노선표와 REA 관찰 정보 비교
- 등교·하교 대표 운행편 조사
- 출발 시각·경유지·요일·적용 기간 확인
- CF01~CF12 중 운행정보 관련 충돌 검토
- 각 정보의 출처와 신뢰 상태 기록

### Agent B — 정류장 위치 검증

담당:
- 대표 운행편의 정류장 위치 조사
- 실제 승차·하차 위치 구분
- 확보 가능한 좌표 및 지도 근거 확인
- 동일 명칭의 다른 위치 문제 검토
- 좌표 정확성과 미확정 사항 정리

### 총괄 에이전트

담당:
- 두 에이전트 결과 취합
- 데이터 충돌 및 누락 검증
- 기존 시스템 명세와의 일관성 확인
- 구현용 데이터 구조와 검증 규칙 확정
- 남은 위험 및 구현 가능 범위 정리

작업 분리의 실익이 작거나 실제 하위 에이전트 실행이 불가능하면 단일 에이전트로 진행하세요.

에이전트 결과가 충돌하면 관련 근거를 다시 확인하세요.

## 7. 데이터 정확성 및 추천 가능 여부 판정

각 데이터 필드에 출처와 검증 상태를 연결하세요.

최소 다음 상태를 구분하세요.

- VERIFIED: 근거에 의해 확인된 정보
- CONFLICTED: 근거 간 충돌이 있는 정보
- UNVERIFIED: 확인되지 않은 정보
- ESTIMATED: 명시적인 계산 또는 추정 정보
- MOCK: 기능 테스트용 가상 데이터

추정값이나 가상 데이터가 실제 공식 정보로 표시되지 않도록 설계하세요.

대표 운행편별로 다음 상태를 구분하세요.

A. 실제 추천에 사용할 수 있는 검증된 데이터

B. 일부 기능에만 사용할 수 있는 제한적 데이터

C. 참고용 목록으로 표시할 수 있지만 추천에는 사용할 수 없는 데이터

D. 검증 전까지 안내에서 제외해야 하는 데이터

추천 가능 여부는 실제로 확인한 필드와 기존 시스템 설계 기준으로 판단하세요.

어떤 필드가 부족하여 추천이 제한되는지 명확하게 설명하세요.

단순한 결측 데이터 하나 때문에 전체 기능을 중단하지 않도록 제한적 안내와 안전한 대체 방식을 검토하세요.

## 8. 기존 CF01~CF12 처리

기존 VALIDATION_MATRIX.md에 기록된 충돌 및 미확정 항목을 다시 확인하세요.

모든 항목을 처음부터 재조사하지 말고, 이번 대표 운행편과 직접 관련된 항목을 우선 처리하세요.

각 항목에는 다음 정보를 남기세요.

- 현재 상태
- 관련 근거
- 구현에 미치는 영향
- 이번 작업에서 검증한 내용
- 해결 여부
- 추가 검증이 필요한 사항

특히 다음 문제를 우선 고려하세요.

1. 운행 요일의 상충
2. 동성고 07:30편 관련 경로·시각 차이
3. 에너지밸리 운행편 수 불일치
4. 공지사항의 적용 연도 혼재
5. REA 관찰 하교 목록과 공식 PDF의 차이(CF12)

이 문제들이 모두 이번 대표 운행편의 직접적인 검증 대상일 필요는 없습니다.

이번 구현을 실제로 차단하는 항목과 추후 보완 가능한 항목을 구별하세요.

## 9. 구현을 위한 데이터 계약 확정

대표 데이터 검증 결과를 바탕으로 실제 프런트엔드에서 사용할 데이터 구조를 구체화하세요.

최소 다음 개념을 구분하세요.

- Region: 지원 지역
- Route: 노선
- Trip: 개별 운행편
- Stop: 정류장
- StopOccurrence: 운행편별 정류장 방문·승하차 정보
- Place: 사용자가 검색한 장소
- Source: 근거 자료 및 기준일
- VerificationStatus: 정보 검증 상태

명칭과 실제 필드 구조는 기존 DATA_API_DESIGN.md와 일관되게 조정하세요.

동일한 정류장을 서로 다른 운행편이나 방향에서 사용하는 경우를 고려하세요.

공식 시간표가 없는 필드는 null 등으로 표현할 수 있어야 합니다.

데이터의 출처, 유효기간, 검증 상태를 추적할 수 있어야 합니다.

검증된 값과 가상 테스트 데이터가 섞이지 않도록 분리하세요.

실제 코드 작성 전에 필요한 구조와 검증 규칙을 명세로 확정하세요.

## 10. 구현 준비 상태 평가

대표 데이터를 기준으로 다음 기능의 구현 준비 상태를 판단하세요.

1. 기존 노선 목록 조회
2. 등교·하교 방향 전환
3. 장소·주소 검색
4. 장소 좌표 확보
5. 주변 정류장 후보 검색
6. 운행편 경유 여부 검증
7. 실제 이용 가능한 노선 추천
8. 정류장 위치의 지도 표시
9. 거리 기반 후보 정렬
10. 시간 조건 적용
11. 정보 불확실성 안내
12. 기존 As-is와 개선 To-be 비교

각 기능을 다음 중 하나로 분류하세요.

- 즉시 구현 가능
- 가상 테스트 데이터로 선행 구현 가능
- 실제 데이터 확보 후 구현 가능
- 외부 API 권한 또는 추가 검증 필요
- 1차 구현 제외 권장

모든 기능이 완벽하게 검증되어야만 개발을 시작할 수 있다고 가정하지 마세요.
