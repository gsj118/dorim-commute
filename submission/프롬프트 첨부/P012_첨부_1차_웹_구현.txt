# 목포대학교 Unibus HCI 프로젝트 — 1차 MVP 실제 구현 및 실행 검증

## 0. 역할과 최종 목표

당신은 본 프로젝트의 총괄 소프트웨어 엔지니어이자 개발 오케스트레이터입니다.

기존 HCI 연구, 시스템 설계, REA 기반 Unibus 분석, 데이터 검증 및 사용자 확인사항 반영이 완료되었습니다.

이제 문서 작성 중심의 단계를 종료하고 **실제로 실행 가능한 웹 애플리케이션을 구현하세요.**

이번 작업에서는 코드 작성, 필요한 패키지 설치, 개발 서버 실행, 오류 수정, 기능 검증을 수행할 수 있습니다.

최종 목표는 기존 Unibus의 주요 탐색 구조를 참고하면서, 새로운 장소 기반 통학버스 탐색 기능을 확장할 수 있는 1차 MVP를 완성하는 것입니다.

기능이 정상적으로 동작하는지 실제 실행 결과로 검증하세요.

단순한 화면 목업이나 코드 생성만으로 작업을 완료했다고 판단하지 마세요.

## 2. 현재 확정된 서비스 범위

프로젝트:
광주권 등하교 통학버스 이용정보 탐색 UI 개선

지원 범위:
목포대학교 도림캠퍼스 ↔ 광주권

다음 원칙을 유지하세요.

1. 등교·하교 모두 지원합니다.
2. 기존 Unibus의 목록 중심 탐색 방식을 유지합니다.
3. 새로운 장소 기반 검색 기능을 추가합니다.
4. 학교와 광주권 장소를 출발지·목적지로 연결합니다.
5. 실제 검증된 운행편과 정류장 데이터만 사용합니다.
6. 미확정 정보는 정확한 값처럼 표시하지 않습니다.
7. 향후 목포권 확장이 가능하도록 데이터 구조를 설계합니다.
8. 공식 Unibus 서비스로 오인되지 않도록 비공식 교육용 프로토타입임을 표시합니다.

기존 Unibus:
https://mokpo.unibus.kr/#!/index

REA를 활용한 분석 및 화면 캡처 자료가 이미 존재합니다. 기존 증거를 우선 활용하고, 필요한 화면만 추가 확인하세요.

기존 웹사이트의 인증정보, 보호된 소스 코드, 비공개 API, 저작권 보호 자산을 무단 추출하거나 복제하지 마세요.

공개적으로 관찰 가능한 화면 구조를 참고하여 자체 코드로 재구현하세요.

## 3. 이번 MVP의 우선 구현 기능

### 3.1 프로젝트 기반 구축

기존 아키텍처 결정에 따라 다음 기술을 우선 사용하세요.

- React
- TypeScript
- Vite
- 정적 JSON 기반 노선 데이터
- 필요시 React Router
- 카카오맵 SDK 연동을 고려한 지도 컴포넌트

백엔드와 데이터베이스는 현 단계에서 필수적이지 않습니다.

불필요한 서버, 인증 시스템, 복잡한 상태 관리 라이브러리를 추가하지 마세요.

기존 프로젝트 폴더 안에 적절한 애플리케이션 디렉터리를 구성하세요.

### 3.2 기존 Unibus 기반 화면

기존 REA 분석과 화면 캡처를 참고하여 다음 화면을 구현하세요.

- 홈 화면
- 등교·하교 노선 목록
- 노선 상세 화면
- 정류장 목록 및 위치 확인
- 운행정보 및 출처 안내

기존 Unibus의 정보 구조와 탐색 흐름을 최대한 일관되게 반영하세요.

다만 디자인을 그대로 재현하는 것보다 대표 과업을 실제로 수행할 수 있도록 구현하는 것을 우선하세요.

사용자가 홈 화면에서 노선을 선택하고, 상세 정보를 확인한 뒤 다시 목록으로 돌아갈 수 있어야 합니다.

기존 사이트에서 하교 목록이 두 개만 표시되는 문제는 이미 확인했습니다.

따라서 하교 목록은 웹사이트에 표시된 두 항목에 제한하지 않고, 기존 사용자 결정에 따라 2026학년도 2학기 공식 PDF를 기준으로 구축하세요.

존재하지 않는 노선이나 운행편을 임의로 생성하지 마세요.

### 3.3 등교·하교 운행정보 처리

기존 검증 자료와 USER_CONFIRMATIONS.md의 확정 사항을 반영하세요.

- 등교: 정류장별 승차시각 표시
- 하교: 학교 출발시각 표시
- 광주행 학교 승차장: MNU 스퀘어 앞
- 금요일 대체편: 해당 운행편의 실제 조건에 따라 적용
- 공휴일: 사용자 확인에 따른 미운행 규칙 적용
- 특수일: 별도 공지 확인 안내
- 운행 기준: 2026학년도 2학기 공식 PDF
- 운행기간 및 적용 조건: 기존 검증 문서 기준

날짜별 정확한 운행 여부를 판단할 근거가 부족하다면 확정적으로 안내하지 마세요.

운행편별로 실제 확인된 시각과 조건만 사용하세요.

### 3.4 신규 장소 기반 검색 UI

이번 MVP에서 신규 서비스의 핵심 화면을 실제로 구현하세요.

등교:
사용자 출발지 → 목포대학교 도림캠퍼스

하교:
목포대학교 도림캠퍼스 → 사용자 목적지

다음 UI를 제공하세요.

- 등교·하교 전환
- 출발지·목적지 표시
- 학교 위치 자동 설정
- 장소 검색 입력창
- 장소 선택 결과 표시
- 노선 및 정류장 후보 영역
- 추천 근거 및 데이터 신뢰 수준
- 검색 실패와 데이터 부족 안내

사용자가 버스정류장 이름을 반드시 알아야만 검색할 수 있는 구조로 만들지 마세요.

아파트, 건물, 상가, 학교, 주소 등 일상적인 장소를 검색할 수 있도록 설계하세요.

### 3.5 카카오맵 연동 준비 및 가능 범위 구현

기존 설계에 따라 카카오맵 SDK를 우선 검토하세요.

장소명 검색, 주소 검색, 지도 표시를 위한 모듈과 컴포넌트를 구성하세요.

현재 프로젝트에 유효한 API 키와 설정이 존재하면 실제 연동을 시도하세요.

API 키가 없다면 다음을 구현하세요.

1. 환경변수 기반 API 설정
2. .env.example
3. API 연동 모듈
4. 키가 없는 경우의 명확한 안내
5. 공식 설정 절차를 담은 개발 문서
6. API 연결 이후 정상 동작을 검증할 테스트 가능한 구조

API 키를 소스 코드에 직접 작성하거나 Git에 커밋하지 마세요.

API 연결이 불가능하다는 이유로 전체 MVP 구현을 중단하지 마세요.

다만 실제로 동작하지 않는 장소 검색을 정상적인 기능처럼 표시하지 마세요.

실제 위치를 확인하지 않은 정류장에 임의의 좌표를 부여하지 마세요.

### 3.6 추천 알고리즘 기본 구현

기존 SEARCH_RECOMMENDATION.md에서 채택한 방식에 따르세요.

기본 처리 순서:

1. 등교·하교 방향 확인
2. 이용 요일 및 운행 조건 확인
3. 검색 장소의 실제 좌표 확보
4. 검증된 정류장 좌표 확보
5. 해당 방향의 운행편 경유 여부 확인
6. 추천 가능한 후보 필터링
7. 검증된 후보의 직선거리 계산
8. 거리순 정렬
9. 추천 근거와 한계 표시

필터 조건과 검증 규칙을 우선 적용하고, 임의의 가중치 점수로 확인되지 않은 정보를 보완하지 마세요.

실제 좌표가 없다면 거리값을 만들어내지 마세요.

검증된 좌표가 부족하여 실제 추천 후보가 0개라면 그 사실을 명확하게 안내하고 기존 노선 목록 탐색을 제공하세요.

추천 알고리즘 자체는 검증된 데이터 또는 명확히 분리된 테스트 데이터로 테스트할 수 있도록 구현하세요.

테스트용 가상 데이터가 실제 서비스 결과에 섞이지 않도록 하세요.

## 4. 데이터 구축 및 정합성

기존 문서의 데이터 계약을 기준으로 구현하세요.

최소한 다음 개념을 명확하게 구분하세요.

- Route
- Trip
- Stop
- StopOccurrence
- ServiceRule
- Place
- Source
- VerificationStatus

기존 설계에서 채택한 이름이나 구조가 다르면 일관성을 우선하세요.

우선 기존 검증 자료에서 확인된 송정① 등교편과 진월③ 하교편을 구현하세요.

다른 노선은 공식 PDF에서 명확하게 확인할 수 있는 범위까지 구축하되, 구현 범위가 제한되면 해당 범위를 기록하세요.

데이터가 없는 부분을 임의로 채우지 마세요.

출처, 적용 기간, 확인 상태를 데이터에서 추적할 수 있도록 하세요.

특히 사용자 확인 정보와 공식 확인 정보가 모두 VERIFIED 상태이더라도, 원천과 확인 범위를 함께 판단하도록 구현하세요.

기존 CF01~CF12는 관련 데이터의 사용 가능 여부를 결정하는 데 활용하되, 모든 항목의 완전 해결을 구현 선행조건으로 두지 마세요.

## 5. UI·UX 구현 기준

이번 결과물은 실제 제출할 HCI 프로젝트입니다.

따라서 기본 기능만 동작하는 수준에 머물지 말고, 일정 수준의 시각적 완성도와 사용성을 갖춘 웹사이트를 구현하세요.

다음 기준을 적용하세요.

1. 기존 Unibus와 일관된 정보 구조
2. 모바일 우선 반응형 설계
3. 명확한 등교·하교 방향 구분
4. 읽기 쉬운 시간표와 정류장 목록
5. 명확한 버튼 및 탐색 상태
6. 검색 실패·데이터 부족·API 오류 안내
7. 키보드 탐색과 기본 접근성
8. 불필요한 화면 이동 최소화
9. 출처 및 정보 기준일 표시
10. 비공식 교육용 프로토타입 안내

디자인을 개선하더라도 기존 연구에서 확인된 핵심 사용자 문제를 해결하는 목적을 유지하세요.

As-is와 To-be의 비교를 고려하여 공통 노선 데이터를 재사용할 수 있도록 설계하세요.

두 모드를 구현하는 경우 기능상 차이와 데이터상 차이를 구분하세요.

단, 비교 기능 때문에 핵심 구현이 지연된다면 우선 실제 작동하는 To-be 흐름과 기존 목록 탐색을 완성하고, 비교 모드는 후속 작업으로 명시하세요.

## 6. 하위 에이전트 및 도구 운영

이번 작업에서는 실제 코드 구현을 수행합니다.

독립적인 작업이 존재하고 병렬화의 이점이 있다면 하위 에이전트를 활용하세요.

권장 작업 분리:

Agent A — 데이터 및 추천 로직
- 공식 노선 데이터 구조화
- 운행 조건 및 검증 상태 처리
- 추천 알고리즘과 단위 테스트

Agent B — 프런트엔드 UI
- 기본 화면 구조
- 노선 목록·상세 컴포넌트
- 반응형 UI와 탐색 흐름

Agent C — 독립 검증
- 구현 결과의 기능 검증
- 요구사항 충족 여부 확인
- 오류와 접근성 문제 점검

총괄 에이전트는 작업 통합, 공통 인터페이스 조정, 지도 연동, 최종 실행 및 검증을 담당하세요.

각 에이전트의 파일 소유 범위를 명확하게 분리하세요.

같은 파일을 동시에 수정하여 충돌이 발생하지 않도록 하세요.

작업의 독립성이 부족하다면 병렬화하지 마세요.

실제 사용할 수 있는 Skills, MCP, REA, 브라우저 테스트 도구를 확인하고 필요한 경우 활용하세요.

사용할 수 없는 도구를 사용할 수 있다고 가정하지 마세요.

에이전트 개수보다 실제 구현 품질과 테스트 결과를 우선하세요.

- 기존 코드 및 package.json 확인

- 컴포넌트 구조 및 데이터 인터페이스 정의
- 병렬화 가능한 작업만 분리

### 3단계: 실제 구현
- 필요한 파일 생성 및 수정
- 필요한 의존성 설치
- 기본 앱과 라우팅 구성
- 실제 노선 데이터 연결
- 목록·상세·장소 검색 UI 구현
- 추천 알고리즘 기본 구현
- 지도 API 연동 가능 범위 구현

### 4단계: 실행
- 개발 서버 실행
- 실제 화면 로딩 확인
- 대표 사용자 흐름 확인
- 콘솔 오류 및 런타임 예외 검사

### 5단계: 자동 검증
- TypeScript 타입 검사
- 프로덕션 빌드
- 가능한 경우 ESLint 검사
- 추천 로직 단위 테스트
- 주요 컴포넌트 및 상태 테스트
- 대표 등교·하교 탐색 테스트

### 6단계: 오류 수정
- 발견된 오류의 원인 확인
- 관련 코드 수정
- 변경 범위 재검증

실제 브라우저 도구가 사용 가능하다면 모바일·데스크톱 화면을 확인하고 필요시 스크린샷을 비교하세요.

가능한 작업을 끝까지 수행하고, 단순히 구현 계획만 출력한 채 종료하지 마세요.

다만 외부 API 키, 실제 계정 권한, 검증되지 않은 좌표처럼 임의로 해결할 수 없는 항목은 정직하게 미완료 처리하세요.

## 9. 완료 기준

이번 단계에서 반드시 달성해야 하는 최소 조건은 다음과 같습니다.

1. React·TypeScript·Vite 애플리케이션이 실제 실행됩니다.
2. 홈 화면에서 등교·하교 노선 목록에 접근할 수 있습니다.
3. 공식 자료에 근거한 대표 운행편 데이터를 표시합니다.
4. 노선을 선택하면 정류장 및 운행정보를 확인할 수 있습니다.
5. 등교·하교별 시간정보가 올바르게 구분됩니다.
6. 신규 장소 기반 검색 인터페이스가 존재합니다.
7. 지도 및 장소 검색 연동 구조가 구현됩니다.
8. 실제 데이터가 부족한 경우 안전하게 안내합니다.
9. 추천 알고리즘의 필터링·정렬 로직을 테스트할 수 있습니다.
10. 타입 검사와 프로덕션 빌드가 성공합니다.
11. 정상 탐색 및 대표 예외 상황을 검증합니다.
12. 로컬 실행 방법을 문서화합니다.

API 키나 외부 데이터가 없어 일부 기능을 완성하지 못했다면 해당 기능을 명확하게 미완료로 표시하세요.

최소 조건 중 실제로 충족하지 못한 항목도 구체적으로 보고하세요.
