6. 문제 정의에서 반드시 지킬 것
==================================================

이번 프로젝트를:

“Unibus UI가 전반적으로 나쁘다”

라고 정의하지 않는다.

또한:

“Unibus에는 지도 기능이 없다”

라고 쓰지 않는다.

실제 첨부 화면에는:

- 노선안내
- 등교/하교 구분
- 노선·출발지점 목록
- 노선별 정류장 목록
- 정류장별 지도
- 차량위치조회
- 버스예약
- 공지사항
- 문의게시판

등이 존재한다.

현재 화면에서 확인되는 대표 흐름은:

노선 또는 주요 출발지점 선택
→ 해당 노선의 정류장 목록 확인
→ 선택한 정류장 지도 확인

이다.

이번 프로젝트가 검증하려는 핵심 차이는:

사용자의 현실적 사고 출발점은

“나는 ○○ 근처에 있다.”

일 수 있지만,

현재 제공 화면에서 확인되는 정보의 출발점은

“어느 통학버스 노선을 먼저 확인할 것인가.”

라는 점이다.

제공된 화면 범위에서는:

일반 생활권 장소
→ 주변 통학버스 승차지점

방향의 탐색 흐름은 확인되지 않았다.

그러나:

“Unibus 전체 서비스에 이 기능이 절대로 없다”

라고 확대해서 단정하지 않는다.

또한
노선을 이미 잘 알고 있는 숙련 사용자에게는
현재 방식이 충분히 편리할 가능성도 인정한다.


==================================================
7. 5W1H 작성 방향
==================================================

Who:

광주권에서 도림캠퍼스로 통학하며
생활권 장소와 통학버스 노선·승차지점의 대응을
아직 잘 모르는 재학생.

What:

알고 있는 장소를 기준으로
이용 가능한 승차지점·운행편·탑승 시각·위치를 확인하는 과업.

When:

등교 전 승차정보를 확인할 때,
평소와 다른 광주권 장소에서 학교로 이동해야 할 때,
익숙하지 않은 승차지점을 찾아야 할 때.

실제 발생 빈도는 조사하지 않았으므로
“자주 발생한다”라고 단정하지 않는다.

Where:

스마트폰 중심 사용 상황을 연구·설계 대상으로 삼는다.

단,
현재 제공된 화면 캡처는 주로 데스크톱이므로
모바일에서 특정 사용성 문제가 발생한다고 이미 관찰한 것처럼 쓰지 않는다.

Why:

사용자가

어디에서
어떤 버스를
몇 시에 타야 하는지

올바르게 이해하도록 하는 것이 핵심 사용자 가치다.

How:

현재 자료에서 확인되는 대표 흐름은

노선/출발지점 선택
→ 정류장 확인
→ 지도 확인

이며,
필요한 경우 공지·노선표 등의 정보를 함께 확인할 수 있다.

사용자가 실제로:

- 여러 노선을 반복 확인하는지
- 외부 지도를 함께 쓰는지
- 주변 사람에게 묻는지
- 커뮤니티를 검색하는지

등은 향후 사용자 연구에서 확인한다.


==================================================
8. E01~E03 최종 근거
==================================================

실제 첨부 자료를 직접 다시 확인하여 작성한다.

E01 — 노선 중심 탐색 구조

현재 Unibus의 ‘노선 및 정거장’에서는
노선 또는 주요 출발지점 항목을 먼저 선택한 뒤
해당 노선의 정류장 목록으로 들어가는 구조가 확인된다.

한계:

이 구조 때문에 실제 사용자가 어려움을 겪는지까지
확인한 사용자 연구는 아직 없다.


E02 — 기존 위치 확인 기능과 탐색 방향의 차이

선택한 통학버스 정류장의 위치는
지도에서 이미 확인할 수 있다.

그러나 제공된 화면 범위에서는:

일반 생활권 장소
→ 주변 통학버스 승차지점

이라는 탐색 경로는 확인되지 않았다.

한계:

제공 화면만으로 서비스 전체 기능의 절대적인 부재를 증명하지 않는다.


E03 — 공식 운행정보의 구조

첨부 원본 공식 통학버스 노선표를 직접 확인한다.

기존 분석에서는 광주권 등교가:

15개 노선·19편
<월~목 운행 4편 포함>

으로 확인되었다.

원본 PDF에서 다시 검증하여
맞으면 정확하게 사용하고,
다르면 원본 PDF를 기준으로 수정한다.

공식 자료에는
한 운행편 안에 여러 승차지점과 시각,
요일·경유 조건 등이 연결될 수 있다는 점을 반영한다.

노선 / 운행편 / 차량 편수 / 승차지점을
같은 단위로 취급하지 않는다.

노선 수가 많다는 사실만으로
사용성 문제가 입증됐다고 쓰지 않는다.

각 근거에는 반드시:

- 내용
- 출처·상황
- 신뢰도
- 한계

를 기록한다.

9. 개인 경험의 사용 범위
==================================================

작성자는 실제 목포대학교 통학버스 이용자다.

개인적으로는
버스예약을 사용하지 않고
노선과 시간을 확인한 뒤 탑승하고 있다.

이는 작성자 개인의 사용 방식이다.

다음처럼 일반화하지 않는다.

- 학생들은 예약하지 않는다.
- 예약 기능은 사용되지 않는다.
- 예약 기능은 필요 없다.

또한 작성자는 학교 커뮤니티에서:

“○○에서 학교 가려면 어떤 버스를 타야 하나요?”
“어디서 타야 하나요?”
“어디에서 내려야 하나요?”

와 같은 질문을 본 경험이 있다.

그러나 게시물을 실제 수집·분석하지 않았으므로
질문의 빈도나 학생 전체의 문제로 사용하지 않는다.

이 경험은
주제를 떠올린 개인적인 배경 또는
향후 사용자 연구에서 확인할 가설로만 사용한다.

변경한다면 이유와 시점을 기록한다.


==================================================
11. 해결 가설과 성공 지표
==================================================

가설 1:

검증된 생활권 장소와
실제 통학버스 승차지점·운행편 정보를 연결하면
노선을 잘 모르는 사용자가 올바른 승차정보를 찾는 데 도움이 될 것이다.

가설 2:

승차지점 후보 비교와
위치·시각·운행 조건 확인을 하나의 흐름으로 연결하면
정확성을 유지하면서 대표 과업 완료시간을 줄일 수 있을 것이다.

성공 판정에서는
사용자가 지정된 출발 장소·등교 조건에서:

- 올바른 승차지점
- 올바른 운행편 또는 노선
- 탑승 시각
- 실제 위치
- 필요한 운행 조건

을 정확하게 확인했는지 본다.

성공률:

성공한 평가 과업 수 / 전체 수행 과업 수

로 계산한다.

시간:

정해진 과업 시작 시점부터
최종 답을 제시할 때까지 측정한다.

B와 I 조건의:

- 기기
- 정보 범위
- 과업 난이도
- 연구자 개입 규칙

을 최대한 맞춘다.

빠르게 끝냈더라도:

- 잘못된 버스 선택
- 잘못된 승차지점 선택
- 장소와 실제 승차지점 혼동

이 증가하면 성공으로 판단하지 않는다.


==================================================
12. 포함 범위 / 제외 범위
==================================================

포함 범위:

- 광주 생활권 장소 → 도림캠퍼스 등교 승차정보 탐색
- 모바일 중심 흐름
- 실제 사용자 연구
- 실제 연구자료 분석
- 일부 검증된 장소·운행편 데이터
- 종이 프로토타입
- 클릭 가능한 디지털 프로토타입
- 기존 방식(B)과 개선안(I) 비교 평가
- 평가 결과에 따른 개선

제외 범위:

- 광주 전체 장소·노선 데이터 구축
- 하교·하차 전체 안내
- 실시간 도착 예측
- AI 추천
- 예약 시스템 개편
- 실제 예약·결제 기능
- 완성형 길찾기
- 필수 현재 위치 권한
- 정확한 집주소 수집
- 상용 서비스 배포

후속 확장:

- 지원 장소·노선 확대
- 선택적 현재 위치 활용
- 평소와 다른 출발 장소
- 하교 방향 탐색
- 목적지 기반 하차 안내

장기 비전과 이번 6주 필수 구현 범위를 명확히 구분한다.


==================================================
13. 기술 구현의 위치
==================================================

실제 웹 구현은
사용자 연구 이후의 선택적 확장이다.

기술 구현 자체를
HCI 프로젝트 성공 조건으로 만들지 않는다.

연구 결과와 시간이 허용하면:

약 2개 노선 안팎,
검증 가능한 10~15개 고유 승차지점 수준

의 제한적 실제 데이터를 활용한 프로토타입부터 시도할 수 있다.

여건이 충분하면
2~3개 노선·15~25개 정도로 확장할 수 있지만
의무 범위는 아니다.

숫자를 맞추기 위해:

- 운행편을 임의로 자르거나
- 요일 조건을 제거하거나
- 경유 조건을 무시하지 않는다.

좌표를 검증하지 않았다면:

- 가장 가까운 정류장
- ○○m
- 도보 ○분

등을 실제 정보처럼 만들지 않는다.

구현이 지연되면
웹 개발 범위를 먼저 줄이고,
실제 데이터를 반영한 클릭형 프로토타입으로 전환한다.

사용자 연구·분석·평가는 삭제하지 않는다.


==================================================
14. Chapter 04~07 후속 연결
==================================================

현재 Chapter 03은
향후 Chapter 04~07 및 프로토타입·평가 단계까지
자연스럽게 이어질 수 있어야 한다.

단,
아직 수행하지 않은 결과를
완료된 결과처럼 작성하지 않는다.


[Chapter 04 — 사용자 연구]

향후 다음 연구질문 축을 검토할 수 있다.

RQ1.
사용자는 등교용 통학버스 정보를
실제로 어떤 정보·도구에서 탐색하기 시작하는가?

RQ2.
생활권 장소와 통학버스 승차지점을 연결할 때
어떤 판단·장벽·확인 기준이 나타나는가?

RQ3.
Unibus 또는 통학버스 노선 숙련도에 따라
탐색 방식이 어떻게 달라지는가?

방법 후보:

실제 과업 관찰
+
반구조화 인터뷰

연구 목표·RQ·참여자 기준·방법·절차·동의·기록·익명화를
Chapter 04에서 구체화한다.

파일럿·연구자 역할극은
실제 사용자 연구 결과로 사용하지 않는다.


[Chapter 05 — 맥락질의]

실제 참여자가
평소 사용하는 기기와 정보원을 활용해
대표 과업을 수행하도록 한다.

관찰 초점:

- 행동 순서
- 사용하는 도구·정보
- 중단·방해
- 우회 방법
- 오류·복구

기록은:

관찰 사실
/ 사용자 발화
/ 연구자 추론
/ 사용자 확인 결과

를 명확히 구분한다.

행동 직후 짧고 중립적으로 해석을 확인한다.

클릭,
멈춤,
되돌아가기,
지도 확인,
도구 전환,
질문,
우회

등은 관찰 후보일 뿐
미리 발생했다고 쓰지 않는다.

실제 근거에서:

- 핵심 사건
- 인사이트
- 설계 기회

를 도출한다.


[Chapter 06 — 작업분석·어피니티]

Chapter 05의 실제 익명 원자료를
한 메모에 행동·발화·사건 하나씩 분절한다.

원자료 ID를 유지한다.

이후:

원자료
→ 어피니티 군집
→ 인사이트·반대 사례
→ HTA
→ As-is
→ To-be
→ 사용자 요구사항
→ 프로토타입
→ 평가

의 추적성을 유지한다.

HTA에는:

- 목표·하위 작업
- 선행 조건
- 필요한 정보·도구
- 오류·예외
- 실행 계획

을 고려한다.

As-is와 To-be 차이는
단순 기능 목록이 아니라
사용자 행동 변화 수준에서 표현한다.

자료가 부족하면 추가 관찰한다.

중복·가상 메모로
요구량을 억지로 채우지 않는다.


[Chapter 07 — 아이디어 도출 및 페르소나]

Chapter 07은 현재 단계에서
페르소나나 최종 해결안을 미리 만드는 근거로 사용하지 않는다.

실제 사용자 연구와 Chapter 06 분석 이후에 적용한다.

작업분석에서 근거가 충분한 문제를
HMW(How Might We) 질문으로 전환한다.

너무 좁아서 해결책을 미리 정하거나,
너무 넓어서 방향을 잃지 않게 한다.

한 가지 아이디어를 곧바로 확정하지 않는다.

여러 해결 대안을 확산한 뒤:

- 사용자 가치
- 실행 가능성
- 프로젝트 범위
- 포용성
- 위험

등 명시적 기준으로 수렴한다.

현재 Chapter 02에서 제안한:

생활권 장소
→ 승차지점 후보
→ 승차정보 확인

흐름 역시
강력한 초기 해결 가설이지
최종 해결안으로 고정하지 않는다.

실제 사용자 연구 결과가
다른 문제 또는 더 좋은 대안을 지지한다면 수정한다.

페르소나는
실제 사용자 조사에서 반복되는:

- 행동
- 목표
- 사용 맥락
- 현재 전략
- 장벽

을 대표하는 모델로 작성한다.

현재 단계에서:

- 이름
- 나이
- 성격
- 취미
- 구체적 행동

을 상상으로 만들어
완성된 페르소나를 작성하지 않는다.

한 명의 인터뷰 참여자를
그대로 페르소나로 복제하지 않는다.

행동 차이가 충분히 확인되면
숙련도·사용 빈도·환경 등의 실제 행동 변수를 이용해
근거 기반 페르소나를 만든다.

후속 흐름은:

실제 사용자 연구
→ 원자료
→ 어피니티·작업분석
→ HMW
→ 아이디어 확산
→ 명시적 기준으로 수렴
→ 근거 기반 페르소나
→ 시나리오
→ 프로토타입
→ 사용자 테스트

로 연결한다.


==================================================
15. 참여자 계획
==================================================

모든 인원은
현재 실제 확보 인원이 아니라 “모집 계획값”이다.

초기 탐색 연구:

실제 광주권 통학버스 이용 경험이 있거나
현실적으로 이용할 가능성이 있는 재학생
2~3명 정도를 목표로 한다.

Chapter 05 맥락질의:

최소 실제 참여자 1인은 반드시 확보하는 실행 목표로 둔다.

후반 비교 평가:

실제 참여자 약 5명 안팎을 모집 목표로 둘 수 있다.

실제 확보 인원이 적다면
그 숫자와 표본의 한계를 그대로 보고한다.

“현재 UI가 불편하다고 생각하는 학생”만 모집하지 않는다.

숙련도가 다른 사용자와
현재 방식으로 문제없이 수행하는 반대 사례도 포함될 수 있게 한다.

한 참여자의 결과를
전체 학생 행동으로 일반화하지 않는다.

19. 지연 시 최소 실행 범위
==================================================

일정이 지연되면 반드시 보존할 것:

- 실제 사용자 연구
- 실제 원자료 분석
- 검증된 일부 등교 데이터
- 핵심 탐색 흐름
- 클릭 가능한 프로토타입
- 실제 사용자 평가
- 개선

먼저 제거할 것:

- API
- 실제 코딩
- 광주 전체 데이터
- 지원 노선 확대
- 하교 기능
- 고도화된 지도·위치 기능

기술 개발 때문에
사용자 연구·평가를 삭제하지 않는다.


==================================================
20. 위험과 대응
==================================================

워크북의 5개 위험을 모두 작성한다.

1. 참여자 모집 실패
2. 범위 확대
3. 개인정보 노출
4. 기술 구현 불가
5. AI 오류·환각

각각:

- 가능성 1~3
- 영향 1~3
- 예방·대응
- 확인 시점

을 작성한다.

합리적인 계획 단계 판단값을 사용하되
실측 확률처럼 표현하지 않는다.

AI 오류 대응에는:

- 공식 자료 재대조
- 노선·시간·요일 확인
- 가상 사용자 발화 생성 금지
- 사람의 최종 확인

을 포함한다.


==================================================
21. 윤리·개인정보·접근성
==================================================

사용자 연구에서는:

- 연구 목적
- 예상 시간
- 기록 방법
- 중단·철회 권리

를 안내하고 사전 동의를 받는다.

촬영·녹음은 별도 동의를 받는다.

불필요한:

- 실명
- 학번
- 정확한 집주소
- 이동 이력

을 수집하지 않는다.

참여자 코드를 사용한다.

원자료는 연구자 본인만 접근하도록 계획한다.

실제 사용자 발화·개인정보·원본 기록을
공개형 AI에 그대로 입력하지 않는다.

AI가 필요하면
완전히 익명화된 요약만 사용한다.

접근성에서는:

- 글자 크기
- 대비
- 터치 영역
- 색상 외 조건 표시
- 위치의 텍스트 설명
- 목록 기반 대체 탐색 경로

등을 검토한다.

실제로 시험하지 않은 접근성을
이미 충족했다고 쓰지 않는다.

==================================================
23. 완료 표시·3분 자기 검토
==================================================

문서 작성 완료와
실제 사용자 연구 완료를 구분한다.

현재 실제 3분 발표 리허설을 수행했다는 증거가 없으므로
수행했다고 만들지 않는다.

3분 자기 제안 검토에는
각 질문에 대한 실제 문서 수준의 검토 의견을 작성하되,

실제 시간 확인은:

“제출 전 작성자 리허설 예정”

처럼 정직하게 표시한다.

제출 전 체크리스트는
현재 문서만으로 충족한 항목은 체크할 수 있다.

그러나:

- 실제 사용자 연구 완료
- 실제 평가 완료
- 발표 리허설 완료

를 의미하는 허위 체크는 하지 않는다.

24. AI 사용 기록
==================================================

이번 작성에서 실제 AI 활용 목적은:

- 교수자 강의자료·워크북 구조 비교
- Chapter 02와 Chapter 03의 연결 검토
- Unibus 화면과 공식 노선표 대조
- 문제·근거·가설 구분
- SMART 목표 검토
- 6주 일정 구조화
- Chapter 04~07 후속 연결 검토
- 범위·위험·윤리 검토
- Markdown 최종 작성·검수

이다.

채택하지 않은 방향의 예:

- 기존 Unibus 전체가 나쁘다는 주장
- 기존 지도 기능이 없다는 주장
- 가짜 인터뷰와 사용자 발화
- 임의 baseline
- 검증하지 않은 거리·도보시간
- 실시간 도착 예측
- AI 추천
- 전체 광주권 완성형 서비스
- 하교 전체 필수 구현
- 정확한 집주소 필수 수집
- 현재 위치 권한 필수 요구
- 상상으로 만든 페르소나
- 기존 초기 아이디어를 검증 없이 최종안으로 확정

실제로 사용하지 않은 도구나
수행하지 않은 사람의 검수 이력을 만들지 않는다.

26. 파일 생성
==================================================

위 모든 조건을 반영한 실제 UTF-8 Markdown 파일:

03_프로젝트제안서_통학버스_구서준.md

를 생성한다.

완성 후 파일을 다시 열어:

- 제목
- 번호
- 표
- 체크박스
- 수치
- 출처
- 사실관계
- 문장
- 파일명

을 최종 검수한다.

파일 생성이 가능하다면
문서 내용을 채팅에 전부 다시 붙이지 않는다.


==================================================
27. 최종 채팅 응답
==================================================

작업 완료 후 채팅에서는 간단히 다음만 알려라.

1. 생성 파일명과 다운로드 링크
2. 자체검수 완료 여부
3. 아직 미측정인 핵심 값
4. 다음 Chapter 04에서 가장 먼저 검증해야 할 가정
5. 다음날 발표용 30~45초 예상 분량 요약

다음 Chapter 04의 가장 중요한 검증 질문은:

“실제 광주권 통학생이
자신이 알고 있는 생활권 장소와
도림캠퍼스 등교용 통학버스 승차지점을 연결하는 과정에서
의미 있는 탐색 어려움을 겪는가?”

로 둔다.

발표 요약에는 다음이 자연스럽게 포함되어야 한다.

- 기존 Unibus에도 노선·정류장·지도 기능은 이미 존재함
- 따라서 기존 서비스 전체가 나쁘다는 프로젝트가 아님
- 노선을 잘 모르는 사용자가
  자신이 알고 있는 장소에서
  승차지점·버스·시간을 찾는 진입 과정을 연구함
- 실제 사용자 연구를 통해 문제 존재부터 검증할 예정
- 조사 결과에 따라 현재 장소 기반 아이디어가 수정될 수도 있음
- 최종적으로 프로토타입과 비교 평가까지 진행할 계획
- 아직 실제 사용자 연구 결과가 나온 단계는 아님

실제로 시간을 재지 않았다면
“30~45초 예상 분량”이라고 표시한다.
