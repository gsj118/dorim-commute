현재 만든 도림통학 서비스를 실제 서비스처럼 다듬어줘.

이번 작업의 핵심은 기능 추가가 아니라, 사용자에게 넘긴 자료 해석 부담을 줄이고 노선표에 없는 건물·아파트에서 통학편을 찾는 흐름을 간결하게 만드는 것이다.

화면 정리 제안이나 가상 사용자 보고서만 만들고 끝내지 말고, 현재 화면 관찰 → 개선 → 실제 브라우저 시험 → 필요한 수정과 재검증까지 수행해줘.

1. 문제의식

현재 서비스는 자료의 정확성과 한계를 설명하는 데 집중한 나머지, 이용 화면에 개발·연구·검증용 설명이 너무 많이 나와 있다.

사용자는 “이 아파트에서 어디로 가서 몇 시에 타면 돼?”를 알고 싶은데, 반경·정렬·좌표 상태·자료 출처·조건·집계 기준까지 해석해야 한다. 기능은 있지만 사이트가 검증용 프로토타입처럼 느껴진다.

네가 만든 기존 선택도 비판적으로 검토해줘. 기존 구현을 방어하거나 모든 정보를 필요하다고 합리화하지 말고, 실제 이용자에게 필요한 정보의 우선순위를 다시 판단해줘.

단, 모든 설명을 숨기는 것도 목표가 아니다. 실제 선택을 바꾸는 중요한 조건은 해당 결과에서 바로 보여야 한다.

2. 작업 기준과 보존

- AGENTS.md와 현재 README, 최신 검증 기록 및 관련 구현부터 확인한다. 과거 RC1을 현재 상태로 착각하지 않는다.
- 이전 리허설의 수정본 HCI-RC1-P029-20261110과 이후 변경 유무를 확인하고, 시작 코드·데이터·과업 버전을 기록한다.
- 기존 사용자 수정, 공식·연구 원본, 운행 데이터, 출처와 충돌 기록, 과거 제출본과 평가 자료를 보존한다.
- 기존 평가 탭은 열거나 새로고침하거나 조작하지 않는다. 사용자에게 보이는 별도 시연 탭을 사용한다.
- 사용자 경험 진술과 정형 평가 JSON 확보 여부를 구분한다.
- 공개 배포·푸시·유료 설정·Kakao 앱/키/도메인 변경은 하지 않는다.
- 이번에는 로컬 UI·정보구조·문구·상호작용 개선과 관련 검증을 승인한다. 운행 사실이나 자료 부족을 임의로 바꾸지 않는다.

3. 정보의 우선순위를 다시 설계

현재 보이는 주요 요소를 다음 기준으로 검토하고 실제로 정리한다.

A. 기본 화면에 바로 필요한 정보
- 등교 또는 하교
- 사용자가 출발하거나 도착하려는 장소
- 정류장 이름과 실제 위치를 확인하는 행동
- 등교는 선택한 지점의 승차 시각
- 하교는 학교 승차 위치와 학교 출발 시각
- 운행편과 선택에 직접 영향을 주는 조건

B. 필요할 때 펼쳐볼 정보
- 상세 경유 지점
- 위치 설명과 공식 자료
- 해당 결과의 구체적인 불확실성 및 근거
- 세부 검색 조건

C. 하단 도움말·이용 안내·자료 출처로 옮길 정보
- 직선거리의 의미
- 일반적인 자료 수집 기준과 업데이트 기준
- 반복되는 공통 주의사항
- 서비스 지원 범위의 자세한 설명

D. 일반 이용 흐름에서 분리할 정보
- 연구 과정과 개발·자동검증 내역
- 관계·노드·좌표 개수 같은 내부 집계
- As-is 비교와 평가 도구
- 일반 이용자가 과업을 해결하는 데 필요 없는 구현 용어

이 분류를 기계적으로 적용하지 말고 실제 화면 맥락을 판단한다. 기존 비교·평가 기능과 직접 접근 경로는 보존하면서 일반 이용 흐름의 노출을 줄일 수 있다.

모든 설명을 ‘이용약관’에 몰아넣지는 않는다. 이용 안내, 자료 출처, 실제 약관이 필요한 내용을 구분하고 불필요한 약관이나 동의 절차를 만들지 않는다.

예외적으로 다음 정보는 하단에만 숨기지 않는다.
- 선택 요일이나 시각에 해당 편을 이용할 수 없다는 조건
- 해당 결과의 운행 정보 충돌
- 실제 승차 위치를 확정할 수 없는 상태
- 사용자가 결과를 잘못 해석하면 다른 행동을 하게 되는 중요한 제한

거리 옆에는 ‘직선거리’처럼 짧고 정확한 표기를 사용하고, 상세 설명은 필요할 때 볼 수 있게 한다. 같은 경고를 여러 곳에서 반복하지 않는다.

4. 핵심 이용 흐름과 시각적 완성도

‘장소 입력 → 후보 비교 → 타는 곳 확인’을 중심으로 화면을 정리한다.

- 첫 화면에서 무엇을 하면 되는지 바로 보이게 한다.
- 정류장 이름을 몰라도 시작할 수 있어야 한다.
- 기존 노선·정류장 목록 직접 탐색도 유지한다.
- 위치 권한이나 정확한 집주소를 필수로 요구하지 않는다.
- 기본 결과를 읽기 위해 필터를 전부 이해할 필요가 없게 한다.
- 카드에서 지점·시각·편·주요 행동의 시각적 위계를 분명하게 한다.
- 배지·테두리·보조 문구·안내 상자가 과도하게 경쟁하지 않도록 정리한다.
- 문장을 삭제한 자리에 의미 없는 빈 공간이나 모호한 아이콘만 남기지 않는다.
- 모바일에서 실제로 훑어보고 누르기 편한 배치와 터치 영역을 확인한다.
- 색상만으로 상태를 전달하거나 중요한 내용을 마우스 올리기로만 제공하지 않는다.
- 상세 왕복 시 장소·요일·시간·정렬 등 기존 상태와 초점 보존을 유지한다.

새 디자인 시스템이나 대규모 기능 확장을 목표로 삼지 않는다. 필요한 만큼 레이아웃과 표현을 바꾸되 기존 핵심 동작을 보존한다.

5. ‘글을 자세히 읽지 않는 사용자’ 가상 시험

연령이나 세대 전체의 특성이라고 주장하지 말고, 다음 행동 조건을 가진 가상 사용자로 시험한다.

① 급하게 훑어보는 통학생
- 이동 중 휴대전화로 사용한다고 가정한다.
- 제목·큰 시각·정류장명·주요 버튼 위주로 본다.
- 긴 설명과 하단 안내를 먼저 읽지 않는다.
- 다음 행동이 불명확하면 멈추거나 추측한다.

② 첫 결과를 바로 누르는 사용자
- 검색 결과의 첫 항목을 우선 선택하려 한다.
- 비슷한 이름, 다른 지역, 건물 본체와 입점업체를 혼동할 수 있다.
- 주소나 선택 상태가 눈에 잘 띄어야 스스로 바로잡을 수 있다.
- 가까운 후보를 자동으로 ‘가장 좋은 편’이라고 받아들일 위험이 있다.

③ 기본 설정을 그대로 사용하는 사용자
- 반경·정렬·요일·시간 설정을 적극적으로 찾아 바꾸지 않는다.
- 등교 결과를 본 뒤 하교로 바꿀 수 있다.
- 결과가 0건이면 ‘버스가 없다’고 해석할 수 있다.
- 복구 행동이 명확할 때만 재검색하거나 목록으로 이동한다.

이 사용자들을 일부러 실패하게 만들지도, 성공하도록 설명을 읽혀주지도 않는다. 오해 가능성을 시험하는 행동 가설로 사용한다.

가능하면 구현 담당과 분리된 검토자 1명에게 현재 화면과 과업만 전달한다. 내부 데이터 정답이나 클릭 경로를 미리 알려주지 않는다. 여러 에이전트가 같은 브라우저를 동시에 조작하지 않는다.

완전한 무지 상태의 인간을 재현할 수 있다고 주장하지 않는다. 구현 지식을 이미 가진 에이전트가 스스로 연기했다면 그 한계를 명시한다.

6. 가상 시험의 실행 규칙

단순히 “이 사용자는 헷갈릴 것이다”라는 이야기를 쓰지 말고, 실제 보이는 브라우저에서 그 행동을 실행한다.

각 과업마다 다음을 남긴다.
- 사용자의 요구
- 시작 시 화면에 보이는 정보
- 눈에 띄는 단서를 바탕으로 고른 다음 행동
- 실제 클릭·입력·선택 결과
- 사용자가 내릴 법한 해석과 화면으로 확인되는 사실의 구분
- 혼동·막힘·복구 여부
- 개선 전후 대표 화면

첫 시도에서는 도움말을 읽도록 유도하지 않는다. 막힌 경우 화면에 보이는 복구 수단을 먼저 사용한다. 도움말이 필요해진 지점 자체를 관찰로 남긴다.

스크린샷과 화면에 드러난 접근성 정보로 행동을 판단하고, 숨겨진 DOM·소스코드·내부 정답으로 사용자 행동을 보완하지 않는다. 결함 원인 분석 단계에서는 코드와 데이터를 확인해도 된다.

자동 조작 시간은 사람의 인지시간이 아니다. 가상 사용자의 만족도·성공률·실제 발언을 만들어내지 않는다.

7. 대표 시험 과업

전체를 8~12개의 대표 과업으로 묶는다. 절반 이상은 노선표에 없는 건물·아파트에서 시작한다.

- 기존 시연 예시 외의 새로운 공개 건물·아파트를 최소 2곳 실제 검색한다.
- 정류장명·별칭과 대조하고, 실제 반환된 장소명과 주소를 확인한다.
- 건물명만 알고 출발해서 승차 지점·편·지점 시각을 찾는다.
- 다른 지역의 동명 장소 또는 건물 내 입점업체를 잘못 선택했다가 복구한다.
- 후보 상세에서 실제 타는 곳을 확인하고 돌아온다.
- 등교와 하교를 바꿔서 시각과 위치의 의미를 구분한다.
- 조건을 좁혀 0건을 만들고 도움말을 먼저 읽지 않은 상태에서 복구한다.
- 하교 좌표가 없는 장소에서 목록 대안을 찾는다. 이것을 장소 기반 하교 해결 성공으로 과장하지 않는다.
- 같은 이름의 복수 후보를 보고 무엇이 다른지 판단한다.
- 선택 요일에 영향을 주는 조건이나 자료 충돌을 짧게 훑는 경우에도 알아차릴 단서가 있는지 확인한다.
- 좁은 화면과 키보드로 장소 선택·상세·복귀를 수행한다.

새 장소의 결과가 좋지 않다고 성공하기 쉬운 곳으로 바꿔치기하지 않는다. 0건이나 자료 부족도 결과로 남긴다.

같은 과업을 여러 가상 역할이 수행해도 서로 독립된 인간 표본으로 세지 않는다.

8. 개선과 검증 절차

① 현재 화면의 핵심 문제를 실제 조작으로 확인한다.
② 삭제·이동·축약·항상 노출할 내용을 간결하게 정리한다.
③ 승인된 범위의 UI 개선을 구현한다.
④ 가상 사용자 행동 조건으로 실제 브라우저 과업을 수행한다.
⑤ 발견한 결함이나 중요한 혼동을 국소 수정한다.
⑥ 영향받은 과업과 관련 회귀 검사를 다시 수행한다.

한 차례 개선과 시험 후 필요한 수정·재검증으로 마무리한다. 새 중요 문제가 없으면 끝없이 페르소나나 시험을 추가하지 않는다.

타입·빌드·관련 단위/UI·브라우저 검사를 수행하고, 프로덕션 빌드에서도 대표 흐름을 확인한다. 기존 승차 시각, 방향 알림, 상태 보존, 접근성, 평가 기록에 회귀가 없는지 점검한다.

문구 축약만을 위해 중복 테스트를 대량 추가하지 않는다. 변경 위험에 맞는 검증을 선택한다.

9. 완료 판단

다음을 실제 화면과 실행 근거로 판단한다.

- 사용자가 긴 설명을 먼저 읽지 않아도 검색을 시작할 수 있는가?
- 결과에서 어디서 타는지, 몇 시인지, 어떤 편인지 구별되는가?
- 하교에서 학교 출발 시각을 하차 시각으로 오해하지 않게 하는가?
- 중요한 예외는 눈에 띄고 일반 설명은 주된 흐름을 방해하지 않는가?
- 잘못된 장소와 0건 상태에서 다음 행동을 찾을 수 있는가?
- 정보를 줄이면서도 원문과 출처에 접근할 수 있는가?
- 실제로 없는 데이터나 확정성을 디자인으로 암시하지 않는가?
- 사이트의 일반 이용 화면이 연구·검증 보고서처럼 보이는 요소를 줄였는가?

문장 수 감소나 자동검사 통과만으로 사용성이 개선됐다고 결론내리지 않는다. 확인한 동작과 설계상 기대 효과, 실제 사람에게 추가 확인할 부분을 나눈다.

10. 기록과 최종 보고

프로젝트 규칙에 따라 사용자 요청과 결과를 기록하고, 새 실행 버전과 개선 전후 근거를 남긴다. 기존 평가나 제출 결과에 수정본의 성과를 소급하지 않는다.

마지막에는 간결하게 다음을 보고한다.
- 실제 화면에서 무엇을 삭제·이동·축약했는지
- 여전히 가까이 남긴 중요 정보와 이유
- 대표 개선 전후 화면
- 가상 사용자별 실제 행동과 막힌 지점
- 수정한 결함과 남은 자료·검증 한계
- 자동검사 결과와 실행 버전
- 실제 사람이 다음에 확인하면 좋은 핵심 과업

사용자에게 보이는 최종 결과 화면을 열어둔다.

‘설명을 줄여야 한다’는 보고서만 작성하고 끝내지 말고, 실제로 사용할 때 덜 읽고도 필요한 정보를 찾을 수 있도록 화면을 고치고 시험해줘.
