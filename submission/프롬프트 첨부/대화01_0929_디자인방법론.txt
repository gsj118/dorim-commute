[최종 주제]
==================================================

이번 과제의 주제는 다음으로 확정한다.

「목포대학교 광주권 통학생을 위한
주변 통학버스 승차지점 탐색 UI 개선」

핵심 문제는
현재 Unibus의 기존 노선안내 화면 자체가 반드시 나쁘다는 것이 아니다.

실제 첨부 화면을 보면 현재 서비스는
- 등교/하교 노선 목록
- 노선별 정류장 목록
- 정류장 지도
- 차량위치조회
- 공지사항
- 예약 기능
등을 이미 제공한다.

따라서 기존 UI를 억지로 문제라고 만들지 않는다.

이번 프로젝트에서 집중할 문제는 다음과 같다.

사용자는 처음부터
‘어떤 통학버스 노선명을 선택해야 하는가?’라고 생각하기보다

“나는 광주 ○○동에 산다.”
“우리 집 근처 ○○ 버스정류장에서 가장 가까운 통학버스 정류장은 어디인가?”
“○○에서 학교 가려면 어디에서 통학버스를 타야 하는가?”

처럼 자신이 이미 알고 있는 생활권 장소를 기준으로 생각할 수 있다.

하지만 현재 확인한 Unibus의 노선 및 정거장 화면은
통학버스 노선 또는 출발지점을 먼저 선택한 뒤
그 안의 정류장을 확인하는 구조다.

따라서 이번 과제는

‘노선을 이미 아는 사용자에게 정보를 보여 주는 문제’

보다

‘노선을 모르는 사용자가 자신이 아는 장소에서
이용 가능한 통학버스 승차지점을 발견하는 문제’

를 다룬다.

1. 첨부 화면과 PDF에서 직접 확인한 사실
2. 그 구조를 바탕으로 한 분석적 해석

실제 사용자 인터뷰나 사용성 테스트는 하지 않았다.

따라서 다음과 같은 표현을 사실처럼 만들지 않는다.

- 학생들이 노선을 못 찾는다.
- 학생들이 매우 불편해한다.
- 학생들이 자주 잘못된 버스를 탄다.
- 평균 몇 분이 걸린다.
- 몇 퍼센트가 어려워한다.
- 존재하지 않는 인터뷰 발화

작성자가 학교 커뮤니티에서
“○○에서 학교 가려면 어디서 무엇을 타야 하나요?”
“어디에서 내려야 하나요?”
같은 형태의 질문을 본 경험은
문제를 발견하게 된 개인적 계기나 보조 맥락으로만 사용할 수 있다.

실제 게시글 캡처나 체계적인 조사 자료가 없다면
E01~E03의 직접 근거로 사용하지 않는다.

“에브리타임 학생들이 실제로 많이 질문한다”처럼
빈도나 일반적 행동으로 확대해서 쓰지 않는다.

해당 승차지점을 지나는 등교 버스의

학교 커뮤니티·주변 사람 등 다른 정보원을 찾아야 할 가능성.

[3. 관찰 근거]
==================================================

E01~E03은 모두

사용자 발화나 행동 관찰을 만들지 않는다.

--------------------------------------------------
E01 — 노선 중심의 진입 구조
--------------------------------------------------

실제 Unibus의
‘노선 및 정거장’ 화면을 근거로 한다.

등교/하교 탭 아래에서
여러 통학버스 노선 또는 출발지점이
목록으로 먼저 제시된다.

특정 항목을 선택한 뒤
해당 노선의 정류장 목록을 볼 수 있다.

공식 PDF에서는
광주권 등교가 15개 노선·19편으로 구성되어 있다.

확인된 사실:
현재 확인한 노선 탐색 경로는
통학버스 노선/출발지점을 기준으로 진입한다.

분석적 해석:
사용자가 통학버스 노선명보다
자신이 아는 생활권 장소만 알고 있다면
어떤 노선을 먼저 열어야 하는지 별도로 판단해야 할 수 있다.

한계:
실제 학생이 이 과정에서 얼마나 어려움을 겪는지는
사용자 평가를 하지 않았으므로 알 수 없다.

--------------------------------------------------
E02 — 정류장 위치 확인 구조
--------------------------------------------------

특정 노선을 선택하면
해당 노선의 승차지점 목록이 나온다.

각 정류장 오른쪽 지도 아이콘을 누르면
별도 지도 팝업에서 위치를 확인할 수 있다.

확인된 사실:
승차지점의 실제 위치 확인 기능 자체는 이미 존재한다.

중요:
현재 UI가 지도 기능을 제공하지 않는다고 잘못 쓰지 않는다.

분석적 해석:
문제는
‘선택한 통학버스 정류장이 어디 있는가?’는 확인할 수 있지만,

‘내가 아는 장소에서 어떤 통학버스 정류장이 가까운가?’

라는 반대 방향의 탐색은
현재 확인한 화면에서 직접 제공되지 않는다는 점이다.

단,
첨부 자료만으로 이를 완전히 단정할 수 없는 경우
“제공된 화면에서는 확인되지 않았다”라고 표현한다.

--------------------------------------------------
E03 — 다수의 승차지점과 노선 정보
--------------------------------------------------

공식 2026학년도 2학기 PDF를 사용한다.

광주권 등교는
15개 노선·19편이며
각 노선에 여러 중간 승차지점과 시각이 있다.

일부 노선에는
요일별 운행이나 다른 캠퍼스 경유 등의 조건도 있다.

분석적 해석:
학생에게 이용 가능한 후보가 여러 개 존재할 수 있기 때문에
사용자의 생활권 장소와
통학버스 승차지점 사이의 대응을 지원할 필요가 있는지
검증할 가치가 있다.

한계:
노선 수가 많다는 사실 자체가
사용성 문제를 입증하지는 않는다.

[4. 문제문장]
==================================================

해결책을 미리 넣지 않는다.

먼저 다음 요소를 표로 작성한다.

사용자:
광주권에서 통학하며
자신의 생활권과 통학버스 노선의 대응을 아직 잘 모르는 학생

사용 맥락:
등교 전에
집 근처 또는 자신이 알고 있는 장소에서
이용 가능한 통학버스를 찾는 상황

목표:
가까운 통학버스 승차지점을 찾고
어떤 버스를 언제 어디서 타야 하는지 확인

관찰된 장벽:
현재 확인한 서비스는
노선/출발지점 선택 후 정류장을 보는 구조이며,
사용자가 알고 있는 일반 장소를 기준으로
통학버스 승차지점을 역으로 탐색하는 기능은
제공된 화면에서 확인되지 않음

현재 결과:
어떤 노선과 정류장을 먼저 확인해야 하는지 판단하기 위해
여러 노선을 살펴보거나 다른 정보원을 이용해야 할 가능성

최종 문제문장 방향:

“광주권에서 통학하는 학생은
등교 전에 자신의 집 근처나 익숙한 장소에서
이용할 수 있는 통학버스를 찾으려 하지만,
현재 서비스는 통학버스 노선과 출발지점을 기준으로
정류장 정보를 제공하므로,
노선명을 모르는 사용자는
자신이 알고 있는 생활권 장소와 실제 통학버스 승차지점을
직접 대응시켜야 할 수 있다.”

자료와 워크북 문체에 맞게 자연스럽게 다듬는다.

다음 해결책은 문제문장에 넣지 않는다.

- 장소 검색
- 가까운 정류장 추천
- 지도 기반 검색
- 자동 추천

==================================================
[5. 방법론 선택]
==================================================

HCD / 디자인 씽킹 / Lean UX를 모두 비교한다.

HCD:

이번 프로젝트의 중심 접근으로 선택한다.

이유:
- 학생이 실제로 어떤 장소를 기준으로 버스를 찾는지 알아야 함
- 기존 노선 중심 탐색이 실제 문제인지 확인해야 함
- 사용자 과업 관찰과 반복 평가가 필요함
- 기존 UI가 이미 충분한 사용자도 있을 수 있음

한계:
현재 실제 사용자 관찰이 부족함.

보완:
실제 광주권 통학생에게
“집 근처에서 탈 수 있는 버스 찾기” 과업을 수행하게 해
현재 UI와 개선안을 비교한다.

디자인 씽킹:

장점:
다양한 탐색 방식
(장소 검색, 지도 탐색, 정류장 필터, 즐겨찾기 등)을
넓게 만들 수 있음.

한계:
아이디어가 곧 실제 사용자 요구를 증명하지 않음.

Lean UX:

장점:
“생활권 장소에서 통학버스 승차지점을 찾게 하면
탐색 성공률과 시간이 개선되는가?”
라는 핵심 가설을
3프레임 프로토타입으로 빠르게 검증 가능.

한계:
빠른 프로토타입만 보면
실제 위치 데이터 품질이나
숙련 사용자의 기존 흐름을 놓칠 수 있음.

최종:
HCD를 중심으로 사용하고
Lean UX의 빠른 가설 검증을 보조적으로 활용한다.

다음 반복 순서:

실제 통학생의 탐색 방식 확인
→ 기존 UI 과업 관찰
→ 요구사항·문제문장 수정
→ 저충실도 프로토타입
→ 기존/개선 조건 비교
→ 결과 분석
→ 재설계

==================================================
[6. 핵심 아이디어]
==================================================

신규 제안:

「생활권 장소 기반 통학버스 승차지점 찾기」

사용자가
통학버스 노선명을 먼저 고르는 대신

자신이 알고 있는
- 일반 버스정류장
- 지하철역
- 학교
- 아파트
- 공공시설
- 익숙한 장소

등을 검색하면

그 장소 주변의
목포대학교 통학버스 승차지점 후보를 보여 주는 UI다.

중요:

이 기능은 현재 Unibus에서 확인된 기존 기능이 아니라
새로운 UI 제안이다.

실제 검색·지오코딩·거리 계산 API까지
구현했다고 쓰지 않는다.

이번 과제에서는
저충실도 프로토타입으로
정보 구조와 사용자 흐름만 시험한다.

==================================================
[개인정보 원칙]
==================================================

‘집 주소 입력’을 기본 요구로 만들지 않는다.

정확한 집 주소를 수집할 필요 없이
사용자가 스스로

- 근처 버스정류장
- 역
- 공공시설
- 아파트 단지
- 익숙한 장소

등을 검색할 수 있게 한다.

확장 기능으로
‘현재 위치 사용’을 제안한다면
사용자 동의 후에만 사용하며
거부 시 장소 검색으로 동일 과업을 수행할 수 있어야 한다.

이번 3프레임에서는
현재 위치 권한을 필수로 하지 않는다.

==================================================
[3프레임 설계]
==================================================

3프레임은 다음 하나의 과업으로 연결한다.

--------------------------------------------------
Frame 1 — 알고 있는 장소 검색
--------------------------------------------------

상황:
광주권 등교

사용자 행동:
집 근처에서 자신이 알고 있는 장소나
일반 버스정류장 이름을 검색

예:
“○○ 버스정류장”

단,
실제 일반 버스정류장과
통학버스 정류장의 거리 관계를 검증하지 않았다면
실제 장소명을 사용해 잘못된 ‘가까운 정류장’을 만들지 않는다.

검증 가능한 실제 관계가 없으면
와이어프레임에서
‘예시 검색 장소’
또는
‘사용자가 입력한 장소’
처럼 모의값임을 명시한다.

화면:
- 등교/하교
- 지역: 광주권
- 장소/버스정류장 검색창
- 검색 버튼

확인할 가정:
사용자는 노선명보다
자신이 알고 있는 장소를 기준으로 탐색하는 흐름을
더 쉽게 이해하는가?

--------------------------------------------------
Frame 2 — 주변 통학버스 승차지점 후보
--------------------------------------------------

시스템 반응:

입력한 장소를 기준으로
가까운 통학버스 승차지점 후보를 보여 준다.

각 후보 카드:

- 통학버스 승차지점명
- 해당 정류장을 지나는 등교 버스
- 공식 시간표상의 탑승 시각
- 지도에서 위치 보기

실제 거리 계산이 검증되지 않은 상태라면
“도보 3분”, “320m” 같은 값을
사실처럼 만들지 않는다.

거리 값을 넣고 싶다면
‘프로토타입 모의값’이라고 명확하게 표시한다.

더 안전한 표현은:

- 가까운 후보 A
- 가까운 후보 B

또는
‘주변 승차지점 후보’

이다.

확인할 가정:
후보가 승차지점 단위로 제시되면
사용자가 여러 통학버스 노선을 하나씩 열어보는 것보다
더 쉽게 적절한 승차지점을 찾는가?

--------------------------------------------------
Frame 3 — 승차 정보 최종 확인
--------------------------------------------------

사용자가 후보 하나를 선택.

최종 화면에:

- 통학버스 승차지점명
- 정확한 위치를 보여 주는 지도
- 해당 지점을 지나는 버스/노선
- 공식 시간표상의 탑승 시각
- 도림캠퍼스 방향
- 주요 경유지
- 요일별 운행 조건
- 관련 변경 공지가 있다면 표시

를 제공한다.

목표는 사용자가

“어디에서”
“몇 시에”
“어떤 통학버스를”

타는지 설명할 수 있게 하는 것이다.

==================================================
[3프레임 실제 스케치]
==================================================

반드시 실제 제출 가능한
저충실도 모바일 와이어프레임을 제작한다.

파일명:

02_UI디자인방법론_통학버스_3프레임_구서준.svg

한 이미지 안에
Frame 1 / Frame 2 / Frame 3을
왼쪽→오른쪽 순으로 배치한다.

스타일:

- 모바일 화면
- 저충실도
- 단순한 박스·텍스트·아이콘
- 정보구조와 행동 흐름 중심
- 장식 최소화
- 현재 실제 Unibus 화면과
  신규 개선안을 혼동하지 않게 표시

실제 노선명·승차지점·시간을 사용할 때는
공식 PDF에서 검증한 값만 사용한다.

검증할 수 없는
‘일반 장소 → 가장 가까운 통학버스 정류장’
거리 관계는 사실처럼 만들지 않는다.

필요하면
“검색 장소: 프로토타입 예시”
라고 표시한다.

==================================================
[7. Human–AI 기능]
==================================================

AI 기능을 사용하지 않는다.

현재 문제는
장소 검색, 위치 데이터, 정류장 정보 연결,
정보구조 설계로 해결 가능한 문제다.

따라서 워크북에 따라
Human–AI 관련 항목은 ‘해당 없음’으로 처리한다.

AI 추천,
개인 생활 패턴 분석,
자동 통학 경로 생성
등은 넣지 않는다.

==================================================
[8. 검증 계획]
==================================================

실제 평가는 아직 하지 않았다.

가장 위험한 가정:

“통학버스 노선을 아직 잘 모르는 광주권 학생은
자신이 아는 생활권 장소에서
이용 가능한 통학버스 승차지점을 찾는 데
실제 어려움을 겪으며,
장소 중심 탐색 UI가 이를 줄일 수 있다.”

핵심 가설:

“사용자가 자신이 알고 있는 생활권 장소를 먼저 입력하고
주변 통학버스 승차지점 후보를 확인할 수 있게 하면,
기존 노선 중심 탐색보다
올바른 승차지점·버스·시각 확인 성공률이 높아지고
과업 완료 시간이 감소할 것이다.”

비교 조건:

B:
현재 Unibus의
노선 선택 → 정류장 목록 → 지도 확인 구조를 모사

I:
장소 검색 → 승차지점 후보 → 버스정보 확인 구조

참여자:

광주권 통학버스를 이용하거나
통학버스를 이용해 볼 가능성이 있는
목포대학교 재학생 8~10명

아직 모집하지 않았으므로
‘모집 제안값’이라고 표시한다.

참여자 선정 시
기존 Unibus 숙련도를 기록해
숙련 사용자의 차이를 함께 본다.

--------------------------------------------------
공통 과업
--------------------------------------------------

예:

“광주권에서 학교에 등교하려 한다.
제시된 생활권 장소 근처에서
이용할 수 있는 목포대학교 통학버스의
승차지점, 탑승 시각과 위치를 확인하라.”

프로토타입용 장소와 정답은
실제 지도/공식 통학버스 정류장 정보를 통해
사전에 검증 가능한 경우에만 구체적인 실명으로 만든다.

그렇지 않으면
가상 장소와 모의 데이터임을 명확히 표시한다.

--------------------------------------------------
지표 1
--------------------------------------------------

올바른 승차 정보 확인 성공률

정답 항목 예:

- 통학버스 승차지점
- 해당 버스/노선
- 탑승 시각
- 위치 또는 운행조건

목표:
I 조건 90% 이상

실측값이 아니라
설계 목표값임을 명확하게 표시한다.

--------------------------------------------------
지표 2
--------------------------------------------------

대표 과업 완료 시간

과업 시작부터
승차지점·버스·시각 확인까지 측정.

현재 실제 기준값은 없다.

따라서

I 조건의 완료 시간 중앙값을
B 조건보다 30% 이상 줄이는 것을
초기 설계 목표로 설정한다.

‘현재 평균 ○초’처럼
측정하지 않은 값을 만들지 않는다.

--------------------------------------------------
실패 조건
--------------------------------------------------

다음 중 하나가 나타나면
현재 개선안이 충분하지 않다고 판단한다.

- I의 성공률이 B보다 높지 않음
- I의 완료 시간이 줄지 않음
- 가까운 승차지점 후보의 의미를 이해하지 못함
- 장소 검색 결과와 통학버스 정류장을 혼동함
- 시간은 줄었지만 잘못된 버스 선택이 증가함
- 기존 숙련 사용자에게 과업이 지나치게 복잡해짐

시간만 줄었다는 이유로
개선 성공으로 판단하지 않는다.

==================================================
[9. 개인 비판 검토]
==================================================

1. 근거 없이 추정한 것은 무엇인가?

- 현재 노선 중심 구조가 실제 학생에게 어렵다는 점
- 학생이 노선명보다 생활권 장소 중심 검색을 선호한다는 점
- 주변 승차지점 제시가 실제 탐색을 개선한다는 점

모두 사용자 평가가 필요하다.

2. 소외될 수 있는 사용자는?

- 이미 자신의 노선을 정확히 아는 숙련 사용자
- 전체 시간표를 한눈에 비교하려는 사용자
- 검색보다 목록 탐색이 더 편한 사용자
- 위치 정보 제공을 원하지 않는 사용자

따라서 기존 노선 목록은 제거하지 않는다.

3. 기술보다 정보 품질 문제는?

- 통학버스 승차지점 위치 데이터 정확도
- 일반 장소/버스정류장 데이터와의 좌표 대응
- 운행 변경사항의 업데이트 시점
- 요일별·임시 운행 조건
- 실제 GPS 위치 정보의 정확성

4. 반대 해결안은?

새 탐색 흐름을 만들지 않고
기존 ‘노선 및 정거장’ 화면에

- 정류장명 검색
- 지역 필터
- 승차지점 검색
- 지도에서 전체 승차지점 보기

만 추가하는 방법.

장점:
기존 서비스 구조를 유지하므로
개발 범위와 학습 부담이 작다.

이 대안과
장소 기반 탐색 중 무엇이 더 나은지는
프로토타입 평가로 판단해야 한다.

==================================================
[10. 제출 전 점검]
==================================================

완성 후 워크북 체크리스트를 실제로 검수한다.

==================================================
[AI 사용 기록]
==================================================

ChatGPT Work 사용 사실을 숨기지 않는다.

사용 목적:

- 강의자료·워크북·작성예시 대조
- 실제 Unibus 화면 구조 분석
- 공식 통학버스 PDF 검토
- E01~E03 구조화
- 문제문장 검토
- HCD·디자인 씽킹·Lean UX 비교
- 3프레임 프로토타입 설계
- 검증 계획 점검

채택하지 않은 제안:

- 기존 UI가 무조건 불편하다는 전제
- 존재하지 않는 사용자 인터뷰
- 학교 커뮤니티 질문을 정량 근거처럼 사용하는 것
- 실제 거리 데이터 없는 “가장 가까운 정류장” 수치
- 실시간 도착예측
- AI 추천
- 정확한 집 주소 수집
- 예약을 대표 과업에 포함
- 기존 노선 UI 전체 제거

사람이 직접 확인·수정한 내용:

- 무엇을 측정할지
