도림통학의 기능 마감 점검을 실행해줘. 목표는 광주권↔도림캠퍼스 통학생이 아는 장소·노선명·정류장명으로 편을 찾고, 어디에서 몇 시에 타고 어디에서 내릴지 자료가 허용하는 만큼 정확하게 판단하는 거야. 이번 요청은 분석, 앱과 데이터의 수정, 검증, 기능 마감 판정까지 포함해. 이 작업이 끝나면 UI를 한 차례 따로 검토하고 프로토타입 제작을 마칠 예정이야.

프로젝트의 AGENTS.md, 현재 SYSTEM_SPEC과 DATA_RULES, P049~P053 기록을 출발점으로 삼아. 지난 진단의 숫자와 테스트 통과 기록은 현재 실행본과 대조해. 먼저 화면에서 답을 기록하고 원자료의 기대 답과 비교해. 독립 검토가 가능하면 한쪽은 현재 앱을 쓰고 다른 쪽은 공식 노선표(안) S25 p.1·3과 수록 데이터에서 기대 답을 만들어. 발견한 결함은 고친 뒤 같은 입력과 다른 노선의 반례로 다시 확인해.

1. 하교 장소 검색부터 해결해.
직전 진단에서 시간표는 광주 하교 13개 노선·19편을 모두 수록했지만, 거리 비교에 쓸 수 있는 하차 좌표는 175개 편·지점 관계 중 34개, 진월①·③·④의 3편에만 있었어. 진월①은 진월③의 같은 방향·경유 순서를 근거로 한 참고 연결이야. 화정동 사례에서는 반경 3km에 진월④ 두 지점이 나왔지만 서광주우체국·염주체육관을 지나는 송정③·⑦은 비교에서 빠졌어.
- 공개된 공식 자료에서 방향·편·하차 지점을 특정할 수 있는 추가 위치가 있는지 확인해. 보강한 값마다 출처와 대응 근거를 남겨. 등교 좌표를 뒤집거나, 같은 이름의 시설 중심점·다른 편의 핀을 그 정류장의 하차 위치로 확정하지 마.
- 장소 결과의 첫 요약에서 ‘시간표에 수록된 전체 편’, ‘위치 자료로 거리 비교 가능한 편’, ‘지금 선택한 요일·시간·반경·표시 제한에서 보여주는 결과’를 구별할 수 있게 해. 수치는 현재 데이터에서 계산해. 결과가 하나라도 있을 때도 누락 범위가 드러나야 해.
- 좌표를 더 확보하지 못해도 이용자가 할 일을 끝낼 수 있게 해. 예를 들어 이미 보고 있는 하교 결과에서 ‘서광주우체국’을 입력해 송정③·⑦의 학교 승차 위치와 출발 시각을 확인하고 원래 장소로 돌아올 수 있어야 해. 요일과 시간 조건은 유지하거나, 전체 시간표로 넓히는 순간 어떤 조건이 풀리는지 알려줘. 좌표 없는 편을 거리순에 넣거나 특정 아파트와 정류장을 임의로 짝짓지 마. 다른 동네·다른 지점에도 같은 방식이 통해야 해.
- 금요일 16시 이후 ‘샛터코아’도 확인해. 거리 후보가 0건이어도 시간표에는 진월⑤ 학교 출발 18:20이 있고 기본 운행요일은 미확인이야. ③의 금요일 15:30은 17:30을 대체하는 시각이야. ‘학교 출발’, ‘광주 하차 시각 미제공’, ‘오늘 탈 수 있는지 확인 필요’를 정확히 전달해.

2. 예시에 없는 기능 오류도 찾아서 고쳐.
양방향 38편 전체의 경유 순서·역할·시각·요일·충돌 범위는 데이터 수준에서 대조하고, 화면에서는 서로 다른 노선의 대표 과업을 골라. 정상 검색을 한 뒤 한 번에 한 조건만 바꿔서 결과가 뜻밖에 사라지거나 더 확실해 보이는 경우를 찾아. 특히 아래 흐름을 확인해.
- 노선·정류장 직접 검색: 중간 정류장과 첫 정류장 시각, ‘진월③/진월3/진월 3’, 한 편의 여러 지점 일치, 상세에서 다른 행 선택과 목록 복귀.
- 장소 검색: 동명 단지·차수·부속시설 선택, 같은 장소로 등교↔하교 전환, 부분 결과와 0건, 위치 미확보, 반경·표시 개수 및 시간 경계. 빠르게 다시 검색하거나 통신 실패 후 재시도할 때 이전 응답·선택이 새 검색을 덮는지도 봐.
- 운행 판단: 평일·금요일 대체·요일 미표기, 조건부 중간 경유와 승하차, 편 전체 충돌과 특정 지점만의 충돌. 잘못 고른 편에서 복귀하거나 새로고침한 뒤에도 화면의 선택·설명·지도가 서로 모순되지 않아야 해.
- 발견한 문제가 편·시각·위치의 오안내인지, 핵심 과업을 막는지, 가벼운 불편인지 판단해. 재현한 오안내와 흐름 단절부터 수정해. 기존 목록·상세·데이터 해석을 재사용하고, 근거 안내·오류 복구·키보드 조작에 필요한 UI 변경만 이번에 포함해. 시각적 재설계와 새 서비스 기능은 다음 단계로 넓히지 마.

3. ‘학교 확인 필요’를 구체적으로 구분해.
공개 자료나 현재 앱으로 해결할 수 있는 데이터 연결·검색·설명 오류는 이번에 처리해. 공식 자료가 서로 다르거나 특정 방향의 실제 하차 도로변·당일 운행처럼 외부 확인이 꼭 필요한 경우에는 해당 편·지점, 부족한 근거, 학교에 물어볼 정확한 질문, 그동안 앱이 제공할 수 있는 답을 기록해. 학교에 직접 연락하거나 개인 거주지를 테스트 산출물에 남기지 마.

4. 기능을 끝낼 수 있는지 판정해.
기존 서버와 자료를 보존하고 타입 검사·빌드·관련 회귀 검사를 실행해. 390px 모바일과 데스크톱에서 실제 입력→결과 비교→상세→복귀를 수행하고, 프로덕션 빌드에서도 핵심 흐름을 확인해. 실제 Kakao 연동과 모의 응답 검증을 구분해. 기존 5초 제한에서 실패했던 검사는 현재 결과를 기록하고, 제한을 늘린 실행만으로 기본 검사가 통과했다고 보고하지 마.
최종 보고 첫 줄에 ‘기능 마감 가능’ 또는 ‘기능 마감 보류’와 이유를 써. 고친 핵심 문제마다 재현 입력, 수정 전후의 답, 확인 근거를 짧게 적고 하교 거리 비교 범위의 전후 수치를 보여줘. 점검 범위에 재현 가능한 중대 오안내나 핵심 흐름 단절이 남으면 보류야. 학교 확인이 필요한 값은 한계가 보이고 대체 경로가 실제로 동작하면 그 항목을 남긴 채 기능을 마감할 수 있어. 마지막에는 이후 UI 검토에서 사람이 직접 해볼 과업 3개만 인계해. 자동 검증을 실제 통학생의 평가 결과로 보고하지 마.
