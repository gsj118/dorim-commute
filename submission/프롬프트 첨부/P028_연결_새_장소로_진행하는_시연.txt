# HCI RC1 실제 시연 리허설 — 까다로운 질문 생성·실행·반박·개선

## 0. 목표

현재 도림통학 RC1을 실제 과제 시연처럼 검증하세요.
내가 가장 중요하게 생각하는 가치는 **노선표에 없는 익숙한 건물·아파트 이름을 입력해 주변 승하차 지점·운행편·시각과 연결하는 것**입니다.

까다로운 질문을 만들고 스스로 답하는 데서 끝내지 말고, 사용자에게 보이는 브라우저에서 직접 조작하여 해결 과정을 보여주세요. 정상 기능으로 해결되는지, 설명이 부족한지, 실제 결함인지, 현재 자료로 해결할 수 없는지를 구분하세요.

이번 프롬프트를 실행하면 로컬 범위의 필요한 결함 수정과 검증까지 승인합니다. 새로운 기능 확장 MVP나 전면 디자인 개편으로 만들지 마세요.

## 1. 현재 상태와 보호할 작업

- AGENTS.md, README, RC1_REVIEW, RC1_MANIFEST, DEMO_CHALLENGE와 필요한 코드·데이터부터 확인하세요. 원본 전체 재분석은 하지 마세요.
- 이전 기준은 PDF 광주권38편, 편별 정류장 관계355, 참고 거리 적격160입니다. 현재 파일과 다르면 실제 상태와 차이를 먼저 보고하세요.
- P027의 광주수완병원·운암동롯데캐슬아파트는 이미 시연한 예시입니다. 준비 확인에 재사용할 수 있지만 새 장소 검증으로 중복 계산하지 마세요.

- 현재 코드·데이터·과업 버전을 먼저 기록하세요. 수정 후에는 새 매니페스트로 구분하고 기존 RC1 패키지와 과거 평가 자료를 덮어쓰지 마세요.

## 2. 역할과 실행 방식

총괄은 발표자이자 브라우저 조작 담당입니다. 가능하고 실익이 있으면 코드 수정에 참여하지 않는 검토자1명을 추가하여 질문과 결과를 비판하게 하세요. 여러 에이전트가 같은 브라우저나 파일을 동시에 조작하지 마세요.

검토자는 성공을 돕는 힌트보다 빠진 조건과 반례를 찾습니다. 총괄이 결과를 보여준 뒤 ‘그럼 이 경우에도 되나요?’라는 후속 질문을 붙이세요. 페르소나·역할·에이전트 수를 실제 참여자 수로 세지 마세요. 수행하지 않은 독립 검토를 수행했다고 쓰지 마세요.

아래 기본30질문을 사용하고, 실제 화면에서 발견한 문제를 바탕으로 중복 없는 질문을 최대10개 추가하세요. 전체 질문의 절반 이상은 노선표 밖 장소를 통학편과 연결하는 핵심 흐름에 집중하세요. 전체 질문은30~40개, 서로 다른 브라우저 실행 과업은12~16개 정도로 묶어 진행하세요. 한 실행이 여러 질문에 답하면 근거를 공유했음을 표시하고 별개 실험으로 부풀리지 마세요.

## 3. 기본 시연 질문30개

### A. 정류장 이름을 모르는 이용자의 요구

1. ‘노선표에 없는 광주수완병원 근처에서 출발합니다. 정류장 이름을 몰라도 어디서 몇 시에 탈지 찾아보세요.’
2. ‘운암동롯데캐슬아파트에서 등교하려 합니다. 아파트 이름으로 편과 승차 지점을 연결해 보세요.’
3. ‘방금 본 두 곳 외의 다른 생활권 건물로 해보세요. 기존 정류장 이름을 입력하는 방식으로 우회하지 마세요.’
4. ‘새로운 아파트도 해보세요. 이 이름이 앱의 정류장 데이터에 없다는 근거는 무엇인가요?’
5. ‘아파트 본체·정문·후문이 검색됩니다. 무엇을 선택했으며 거리 결과를 어떻게 해석해야 하나요?’

### B. 실제 검색에서 생기는 혼동

6. ‘비슷한 이름의 다른 지역 건물이 먼저 나옵니다. 어떤 정보로 올바른 장소인지 확인하나요?’
7. ‘짧거나 틀린 검색어로 다른 장소가 나왔습니다. 잘못 선택했다가 다시 고쳐보세요.’
8. ‘건물 이름 대신 공개 시설의 도로명주소로 찾아보세요. 장소명 검색과 어떻게 구분하나요?’
9. ‘수록 정류장에 이 건물이 없는데 검색되는 이유가 뭔가요? 장소 검색과 통학 데이터의 역할을 설명하세요.’
10. ‘다른 장소에서 후보가0건입니다. 이 주변에는 통학버스가 없다는 뜻인가요? 다음 행동을 보여주세요.’

### C. 등하교와 시간조건

11. ‘이 건물 근처로 하교하려 합니다. 등교 검색 결과를 뒤집지 말고 하교 지점·학교 승차 위치·출발시각을 찾아보세요.’
12. ‘학교 승차장 좌표가 없다는데 학교에서 어디로 가라고 안내하나요? 확인된 텍스트와 없는 좌표를 구분하세요.’
13. ‘동신고 주변으로 금요일16시 이후 하교하려 합니다. 거리후보0건과 목록의 진월⑤18:20을 함께 설명하세요.’
14. ‘이 장소에서07:15 이후에 탈 수 있는 등교편만 보고 싶습니다. 학교 출발·도착시각과 혼동하지 않게 조작해 보세요.’
15. ‘조건을 과하게 좁혀0건을 만들었다가 복구해 보세요. 장소와 다른 설정을 다시 입력해야 하나요?’

### D. 후보 비교의 의미와 한계

16. ‘반경을1km와3km로 바꾸면 무엇이 달라지나요? 반경 밖을 미운행으로 볼 수 있나요?’
17. ‘가까운 순서와 승차시각순을 바꿔보세요. 서로 다른 목적에 맞게 결과를 비교할 수 있나요?’
18. ‘같은 정류장 이름이 여러 카드로 나오는데 중복 아닌가요? 편별 좌표 차이를 숨기거나 이름만으로 합치지 말고 설명하세요.’
19. ‘가장 가까운 후보 하나를 골라주세요. 이 편을 실제 최적 통학편이라고 확정할 수 있나요?’
20. ‘직선거리300m면 몇 분 걸리며 학교에는 몇 시에 도착하나요? 계산 가능한 것과 근거가 없는 것을 구분하세요.’

### E. 현장에서 시연을 끊는 요구

21. ‘후보 상세·위치를 보고 돌아오세요. 검색어·선택 장소·요일·시간·정렬이 유지되나요?’
22. ‘같은 장소를 As-is로도 찾아보세요. 두 방식의 자료 차이를 기능 개선인 것처럼 설명하고 있지는 않나요?’
23. ‘검색이나 지도 연결에 실패하면 어떻게 하나요? 목록으로 이동하고 다시 시도하는 경로를 보여주세요.’
24. ‘인터넷이 끊겨도 된다고요? 자료를 로드한 뒤 탐색과 캐시 없는 재진입의 보장 범위를 구분하세요.’
25. ‘좁은 화면과 키보드로도 장소 선택·후보 상세·복귀가 가능한가요? 실제로 조작해 보세요.’

### F. 설계와 주장에 대한 반박

26. ‘카카오맵에서 그냥 검색하면 되는데 이 서비스가 추가로 연결해 주는 정보가 무엇인가요? 실제 예시로 답하세요.’
27. ‘이게 정말 주변의 가장 가까운 정류장인가요? 좌표가 없는 편을 빼놓고 전체 최단이라고 말한 것 아닌가요?’
28. ‘355개 정류장과160개 추천이라는 설명이 맞나요? 관계·노드·편·조건 적용 결과를 구분하세요.’
29. ‘사용자가 편해졌다는 근거가 뭔가요? AI 시연·자동시험·본인 경험과 실제 측정 자료를 구분하세요.’
30. ‘왜 확정 추천이 아니라 참고 후보인가요? 무엇이 확인되면 판정을 바꿀 수 있고, 현재도 제공할 수 있는 정보는 무엇인가요?’

## 4. 장소와 사례 선정

- 병원·공공시설·상가·아파트 등 실제 검색 결과에서 확인한 공개 장소를 사용하세요. 사용자의 집주소를 묻거나 추정하지 마세요.
- 이전 두 예시 외에 최소4곳의 새 장소를 서로 다른 생활권에서 시도하세요. 새로운 장소명은 정류장 데이터에 없는지 명칭·별칭을 확인하고 기록하세요.
- 존재하지 않는 건물명을 만들지 마세요. 검색 결과가 입력한 이름과 다르면 실제 이름과 주소를 확인하고 검색어를 바로잡으세요. 다른 장소를 선택하고 성공 사례로 바꾸지 마세요.
- 성공 사례만 고르지 말고 불일치·빈 결과·좌표 미확보·요일/시간 제외·자료 충돌 중 서로 다른 경계를 포함하세요.0건 자체가 결함은 아닙니다.
- 비교 가능한 하교 좌표가 없으면 목록/학교 승차 정보/보류 경로를 확인하세요. 등교 좌표로 대체하거나 없는 하차시각을 생성하지 마세요.
- 실제 API는 대표 장소 검색·지도 확인에 사용하고 같은 호출을 불필요하게 반복하지 마세요. 통신 오류·지연 같은 경계는 격리한 별도 모의시험으로 확인하고 실제 장애 관찰과 구분하세요.

## 5. 내가 볼 수 있는 진행 방식

질문을 한꺼번에 나열한 뒤 긴 시간 보이지 않게 작업하지 마세요. 사용자에게 보이는 브라우저에서3~4과업씩 묶어 진행하고 다음 순서를 짧게 보여주세요.

1. **평가자 요구:** ‘지금 이 조건으로 찾아보세요.’
2. **성공 기준:** 무엇을 확인하면 요구를 해결했다고 볼지 실행 전에 정합니다.
3. **발표자의 조작:** 실제 검색어·선택 장소·조건·클릭 경로를 보여줍니다.
4. **실제 관찰:** 화면에 나온 지점·편·시각·거리 또는 실패 상태를 확인합니다.
5. **추가 반박:** ‘그럼 반대 방향/다른 요일/더 늦은 시각에도 되나요?’를 붙여 확인합니다.
6. **판정:** 정상 기능으로 해결 / 설명 보완 / 재현 결함 / 자료 한계 / 환경 문제 / 미검증 중 하나로 근거와 함께 정리합니다.

공개된 결과·선택 근거·검증 사실을 설명하면 됩니다. 내부 사고 과정의 장문 공개는 요구하지 않습니다. 매 질문마다 사용자 답변을 기다리거나 다음 진행 승인을 반복 요청하지 마세요. 대표 장면에는 전후 스크린샷과 실제 입력·조건을 남기고, 마지막에 핵심 결과 화면을 열어 두세요.

브라우저에서 수행하지 못했거나 도구가 지원하지 않는 항목은 이유와 대안을 보고하세요. 소스·문서만 읽은 결과를 화면에서 시연했다고 쓰지 마세요.

## 6. 무엇을 수정할 것인가

재현 가능한 핵심 중단·잘못된 확정 안내·조건/선택 상태 손실·중요 접근성 문제는 현재 범위에서 국소 수정하세요. 문구나 배치의 혼동은 실제 화면·동작 근거와 실익이 있을 때만 보완하세요.

정상 동작이면 그대로 유지하고 실제 사용 방법을 설명하세요. 자료 부족·현재 운행 미확인·도보시간 미제공을 없애기 위해 사실을 만들거나 범위를 확장하지 마세요. 까다로운 질문 모두를 새 기능 요구로 채택하지 마세요.

수정 전 실패와 수정 후 동일 과업을 비교하고, 테스트 기대값을 결과에 맞춰 바꾸지 마세요. 수정에 따른 대표 재시연과 필요한 회귀 검사를 수행하세요. 코드가 바뀌었다면 타입·빌드·관련 단위/UI·브라우저 검사를 하며, 최종 시연은 실제 프로덕션 빌드에서도 확인하세요.


## 7. 기록과 종료

- 기존 DEMO_CHALLENGE와 RC1 검증 기록에 필요한 요약을 연결하고, 새 질문별 실제 결과·스크린샷·재현 근거는 별도 실행 근거로 보존하세요. 원본 사용자 프롬프트와 결과를 PROMPT_LOG에 남기세요.
- 각 질문에 판정과 근거를 연결하고, 아직 확인하지 못한 항목을 통과로 바꾸지 마세요. 같은 원인을 여러 결함으로 부풀리지 마세요.
- 질문 생성은30~40개, 브라우저 실행은12~16개 대표 과업을 기준으로 한 차례 수행하고 수정한 문제만 관련 재검증하세요. 새 중요 결함이 없으면 검수를 계속 추가하지 말고 마무리하세요.
- 공개 배포·푸시·유료 활성화·Kakao 앱/키 재생성·미승인 계정 변경은 하지 마세요. 다른 프로세스를 임의 종료하지 말고 기존 승인 설정을 활용하세요.
- 기존 실제 평가 기록과 공식/연구 원본은 보존하세요. 수정 뒤 자기평가를 다시 할 필요가 있는지는 변경 내용에 따라 설명하고, 이전 결과를 새 버전의 성과로 소급하지 마세요.
