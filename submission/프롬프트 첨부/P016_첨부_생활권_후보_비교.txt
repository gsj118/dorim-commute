# 목포대학교 Unibus HCI 프로젝트 — 3차 MVP 추천형 탐색 서비스 고도화 및 UX 개선

## 0. 역할 및 최종 목표

당신은 본 HCI 프로젝트의 총괄 소프트웨어 엔지니어이자 사용자 경험 설계·검증 책임자입니다.

현재까지 기존 Unibus 분석, HCI 연구, 시스템 설계, 1차 MVP 구현, Kakao Maps 연동, 실제 정류장 좌표 확보 및 장소 기반 후보 탐색 기능 구현을 완료했습니다.

이번 작업에서는 기존 기능을 보존하면서 생활권 장소 기반 통학버스 노선 후보 추천·비교 기능을 고도화하고, 실제 사용자가 필요한 노선과 정류장을 쉽게 찾을 수 있도록 사용자 경험을 개선하세요.

이번 단계의 핵심은 모든 운행조건을 완벽하게 확정하는 것이 아닙니다.

공식 자료에서 확인할 수 있는 노선·시간·위치 정보를 활용하여 이용자가 적합한 후보를 쉽게 찾고 비교하도록 만드는 것입니다.

정보의 불확실성은 숨기지 않되, 불필요하게 기능을 제한하거나 모든 후보를 동일하게 불확실하다고 표현하지 마세요.

실제 코드 수정, 데이터 확장, 실행, 테스트, 오류 수정까지 수행하세요.

설계 문서 작성만으로 작업을 종료하지 마세요.

## 3. 프로젝트 방향 보완

프로젝트명은 다음과 같이 유지합니다.

광주권 등하교 통학버스 이용정보 탐색 UI 개선

핵심 개선 기능은 다음과 같이 구체화합니다.

생활권 장소 기반 통학버스 노선 후보 추천 및 비교

초기에는 사용자의 출발지 또는 목적지에 가장 적합한 노선을 자동 추천하는 서비스를 구상했습니다.

그러나 실제 구현 과정에서 기존 Unibus 웹사이트의 일부 노선 누락, 공식 PDF와 웹 화면 간 차이, 운행요일·승하차 조건 등 검증되지 않은 정보가 존재함을 발견했습니다.

이러한 상태에서 시스템이 최적의 통학버스를 확정적으로 안내하면 오히려 사용자의 잘못된 판단을 유발할 수 있습니다.

따라서 핵심 연구 목표는 유지하되 다음 방향으로 개선합니다.

1. 사용자의 출발지 또는 목적지를 검색합니다.
2. 공식 노선표와 위치 정보로 관련 정류장·운행편을 찾습니다.
3. 위치와 시간에 따라 후보를 정렬·비교합니다.
4. 각 후보가 제시된 이유를 설명합니다.
5. 확인된 정보와 미확정 정보를 구분합니다.
6. 최종 선택은 사용자가 충분한 근거를 보고 판단하도록 지원합니다.

이것은 기존 기획을 포기하는 것이 아니라 실제 데이터 제약을 반영한 설계 개선입니다.

최초 연구자료를 소급하여 수정하거나 처음부터 이러한 방향이었다고 기록하지 마세요.

기획 변경의 원인과 판단 근거를 별도로 보존하세요.

## 4. 추천 시스템 고도화

### 4.1 기본 검색 구조

등교:
광주권에서 검색한 출발지 → 목포대학교 도림캠퍼스

하교:
목포대학교 도림캠퍼스 → 광주권에서 검색한 목적지

사용자는 다음과 같은 장소를 검색할 수 있어야 합니다.

- 아파트명
- 건물명
- 상가 및 사업장
- 학교·병원·공공기관
- 도로명주소
- 지번주소
- 주요 생활권 장소

이미 구현한 Kakao 장소 검색 기능을 재사용하세요.

### 4.2 후보 검색 및 정렬

기존 추천 알고리즘을 재사용하면서 필요한 부분만 개선하세요.

기본 처리 순서:

1. 이용 방향 확인
2. 검색 장소의 실제 좌표 확보
3. 공식 노선표의 해당 방향 운행편 조회
4. 승하차 가능한 관계 및 경유 정보 검토
5. 확인된 정류장 좌표를 이용한 거리 계산
6. 적용 가능한 운행조건 검토
7. 실제 조건에 부합하지 않는 후보 제외
8. 나머지 후보의 거리·시간정보 정렬
9. 추천 근거 및 불확실성 표시

거리순 정렬은 기본값으로 유지하세요.

시간 조건은 공식적으로 확인된 정보의 범위에서 필터 또는 보조 정렬 기준으로 활용하세요.

복잡한 임의 가중치 점수는 도입하지 마세요.

추천에 사용하는 조건과 정렬 기준을 사용자에게 설명할 수 있어야 합니다.

### 4.3 추천 반경과 후보 수

기존 추천 반경과 결과 개수 제한을 확인하세요.

반경이나 후보 개수를 결정할 때 다음을 고려하세요.

- 주변 정류장 밀도
- 도보 접근 가능성
- 후보가 지나치게 적거나 많은 문제
- 여러 노선이 동일 정류장을 사용하는 문제
- 검색 실패 시 대안 탐색

임의의 숫자를 객관적으로 검증된 최적값이라고 주장하지 마세요.

합리적인 초기값을 사용하되 설정 가능하게 만들고, 실제 테스트 결과에 따라 조정하세요.

적합한 정류장이 없을 때 지나치게 먼 정류장을 무조건 최적 후보라고 표시하지 마세요.

## 5. 후보 상태와 정보 표현

정보 부족을 이유로 모든 후보를 숨기거나 동일한 상태로 처리하지 마세요.

다음 세 가지를 구분하세요.

### A. 조건 확인 후보

현재 적용한 검색 조건에서 확인 가능한 운행편·방향·승하차 관계·시간 조건 등을 충족하는 후보입니다.

검증된 범위와 근거를 표시하세요.

이 상태가 실시간 운행 또는 실제 탑승 가능성을 보증한다는 의미는 아닙니다.

### B. 참고 후보

공식 노선표에 수록되고 정류장 위치·경유 관계 등을 확인했지만, 특정 운행요일이나 실제 승하차 조건의 일부가 불분명한 후보입니다.

실제 좌표가 있다면 직선거리와 시간표를 활용하여 정렬·비교할 수 있어야 합니다.

다만 실제 운행 확정 여부가 필요한 정보는 미확정으로 안내하세요.

### C. 조건 불일치 후보

검색 조건과 실제로 확인된 운행조건이 맞지 않는 후보입니다.

일반 결과에서 제외하되, 사용자가 필요한 경우 제외 사유를 확인할 수 있도록 검토하세요.

좌표가 없어서 거리 비교가 불가능한 운행편은 기존 목록 탐색에서 유지하세요.

정보가 미확정인 경우와 확인된 조건에 맞지 않는 경우를 혼동하지 마세요.

상태 분류와 사용자에게 보여주는 문구가 정확히 일치하도록 구현하세요.

## 6. 추천 결과 UX 개선

이번 단계에서는 사용자가 여러 후보를 비교하는 과정의 완성도를 높이세요.

검색 결과에서 다음 정보를 우선적으로 제공하세요.

1. 노선명 및 운행편
2. 승차 또는 하차 정류장
3. 검색 장소와의 직선거리
4. 확인된 운행시각
5. 등교·하교 방향
6. 추천·참고 후보 구분
7. 후보가 제시된 이유
8. 불확실하거나 추가 확인이 필요한 정보
9. 지도에서 위치 확인
10. 노선 상세로 이동

정보를 무조건 많이 보여주는 것보다 사용자의 판단에 필요한 정보를 우선 배치하세요.

### 6.1 후보 비교

여러 후보를 비교할 수 있도록 다음 요소를 검토하고 구현하세요.

- 가까운 정류장순 정렬
- 동일 정류장의 복수 운행편 묶기
- 정류장 위치와 해당 운행편의 시각 비교
- 후보별 추가 확인 사항
- 선택한 후보의 지도 강조
- 상세 화면으로 이동한 뒤 검색 결과 복귀

기존 검색어·방향·선택 장소가 불필요하게 초기화되지 않도록 하세요.

### 6.2 시간조건

하교:
학교에서 출발할 수 있는 시각을 선택적으로 입력하고, 공식적으로 확인된 학교 출발시각과 비교할 수 있도록 구현하세요.

등교:
정류장별 공식 승차시각이 확인된 경우 해당 시각을 기준으로 비교할 수 있도록 하세요.

학교 도착시각이 확인되지 않은 상태에서는 원하는 학교 도착시각을 충족한다고 확정적으로 판정하지 마세요.

사용자가 학교 도착 목표시각을 입력하더라도 해당 조건을 검증할 수 없다면 그 한계를 명시하거나 별도의 시간표 탐색 기능으로 제공하세요.

시간조건은 기본적으로 선택 항목으로 구성하여 초기 검색 부담을 줄이세요.

### 6.3 불확실성 안내

사용성 저하를 방지하도록 불확실성 안내를 설계하세요.

모든 결과에 동일한 경고를 반복하지 말고, 후보별로 실제 부족한 항목을 보여주세요.

정류장 위치, 공식 시간표, 운행요일, 특별 운행조건을 구분하세요.

확인된 사실까지 불확실하게 표현하지 마세요.

직선거리를 실제 도보거리로 표현하지 마세요.

사용자가 결과를 이해하고 다음 행동을 결정할 수 있도록 간결하게 안내하세요.

## 7. 광주권 노선 데이터 확장

현재 수록된 대표 운행편은 송정① 등교와 진월③ 하교입니다.

두 편만으로 광주권 전체 통학생의 탐색 수요를 충족하기는 어렵습니다.

따라서 2026학년도 2학기 공식 PDF를 활용하여 추가 노선과 운행편을 구축하세요.

다만 이번 단계에서는 전체 노선 전사를 추천 UX 구현의 절대 선행조건으로 두지 않습니다.

### 7.1 우선순위

1. 기존 대표편 데이터와 좌표 관계 유지
2. 공식 PDF에서 명확하게 확인 가능한 추가 운행편 선정
3. 기존에 확보한 정류장 좌표를 안전하게 재사용할 수 있는 관계 검증
4. 서로 다른 광주권 생활권을 포괄하는 운행편 확장
5. 추가 좌표가 필요한 경우 정상적인 Unibus 지도 기능으로 확인
6. 확인 가능한 범위부터 앱에 반영

단순히 노선 수만 늘리기보다 실제 검색 가능 지역의 확대를 우선하세요.

### 7.2 전사 규칙

다음 원칙을 준수하세요.

- 등교와 하교를 단순 역순으로 생성하지 않음
- 원문에 없는 운행편이나 시각 생성 금지
- 동일 이름의 다른 방향 정류장 구분
- 동일 정류장에 여러 운행편 연결 가능
- PDF와 웹사이트의 불일치 이력 보존
- 충돌하는 데이터는 임의 확정 금지
- 정류장 좌표의 출처와 확인 수준 유지
- 미수록 노선을 미운행 노선으로 표현하지 않음

추가 편의 전체 조건을 확정할 수 없어도 목록 및 참고 후보로 활용 가능한 범위를 검토하세요.

확장한 운행편 수, 지역 범위, 좌표 확보 여부를 기록하세요.

전체 PDF 전사는 필요성과 작업량을 고려하여 후속 단계로 분리할 수 있습니다.

## 8. HCI 연구 목적과의 일관성

이번 작업에서 기존 프로젝트의 다음 핵심 요구사항은 유지해야 합니다.

- 광주권 통학생 대상
- 등교·하교 모두 지원
- 기존 목록 기반 탐색 유지
- 생활권 장소 검색 기능
- 승하차 정류장 및 노선 안내
- 정보 탐색 과정의 부담 감소
- 사용자에게 필요한 근거 제공

현재 변경은 문제 정의의 변경이 아니라 해결 방식의 정교화입니다.

이를 설명할 수 있도록 기획 변경 결정 기록을 작성하거나 기존 결정 문서에 반영하세요.

다음 흐름을 남기세요.

1. 최초 기획의 문제 정의
2. 초기 자동 노선 추천 구상
3. 구현 중 발견한 공식 데이터의 한계
4. 확정 추천 방식의 위험
5. 후보 비교 중심 UX로 변경한 이유
6. 변경 전후 기능 관계
7. 실제 개선 효과를 평가할 방법

초기 제안서와 사용자 연구자료를 처음부터 수정하지 마세요.

변경 이력만 별도로 관리하세요.

기존 HCI 연구에서 확인된 사실과 새롭게 제안한 설계 가설을 구분하세요.

## 9. As-is / To-be 비교 준비

기존 Unibus의 목록 중심 탐색과 개선된 장소 기반 탐색을 향후 비교할 수 있도록 구성하세요.

현재 단계에서는 별도의 As-is 전체 화면 구현을 필수로 요구하지 않습니다.

하지만 향후 두 방식을 동일한 데이터와 대표 과업으로 비교할 수 있도록 다음을 검토하세요.

- 기존 목록 탐색의 대표 흐름
- 개선된 장소 기반 탐색의 대표 흐름
- 같은 노선·정류장 데이터를 사용하는 구조
- 과업 시작점과 종료점
- 과업 성공 여부 판정 기준
- 탐색 완료 시간 측정 기준
- 오류 및 되돌아가기 측정 가능성

기존 Unibus 화면의 누락 문제를 해결했다고 해서 실제 기존 서비스에서도 동일한 기능이 제공되었다고 표현하지 마세요.

동일한 데이터 조건을 사용한 통제된 UI 비교와 실제 원본 서비스 비교를 구분하세요.

기존 목표인 성공률 90%, 탐색시간 30% 감소는 미검증 목표로 유지하세요.

실제 사용자 실험을 수행하지 않았다면 해당 수치를 달성했다고 기록하지 마세요.

## 11. 실제 테스트 및 검증

기존 테스트를 유지하고 이번 변경사항에 대한 테스트를 추가하세요.

### 기존 기능 회귀 검사

- Kakao 실제 장소·주소 검색
- 지도와 마커 표시
- 등교·하교 목록 탐색
- 송정① 및 진월③ 상세
- 직선거리 계산 및 정렬
- URL 및 브라우저 뒤로가기
- API 오류·재시도·복구
- 모바일 반응형
- 키보드 접근성

### 신규 검증

1. 여러 후보를 거리순으로 비교할 수 있는지
2. 동일 정류장의 여러 운행편이 올바르게 연결되는지
3. 등교·하교 방향을 혼동하지 않는지
4. 시간조건이 확인된 출발·승차시각에만 적용되는지
5. 미확정 운행조건을 허위로 확정하지 않는지
6. 실제로 확인된 정보는 불필요하게 숨기지 않는지
7. 위치·시간·운행조건의 불확실성이 각각 구분되는지
8. 후보 선택 시 지도와 상세 정보가 일치하는지
9. 검색 결과와 상세 화면 사이에서 상태가 유지되는지
10. 신규 생활권 장소에서도 관련 후보를 탐색할 수 있는지
11. 좌표가 없는 정류장도 목록 탐색이 가능한지
12. 추천 후보가 없을 때 유용한 대체 탐색을 제공하는지

특히 실제 장소 기반 후보 비교 과업을 데스크톱과 모바일에서 수행하세요.

기존 대표 과업 4건은 가능한 한 유지하고, 신규 데이터가 있다면 추가 과업으로 검증하세요.

자동 접근성 검사와 육안 UI 검사를 구분하여 실시하세요.

실제 오류를 발견하면 수정하고 관련 테스트를 재실행하세요.

TypeScript 타입 검사, 프로덕션 빌드, 단위·UI 테스트, 브라우저 테스트를 수행하세요.

실제 API 및 실제 데이터 검증과 모의 테스트 결과를 구분하여 보고하세요.
